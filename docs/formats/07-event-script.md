# 事件腳本

事件不是「踩到就顯示某條字串」，而是**執行一段腳本**。直譯器與 50 個
handler 都在 `2PLAY.OVL`（重建映像 `2PLAY.img`，位址換算見
[`01`](01-overlay-and-memory-layout.md) §2.5）。

## 1. 觸發流程

```
踩到格子
  → 查事件表，取得 Index 與 Kind          （docs/formats/02 §4）
  → 從腳本區開頭跳過 Index 段（0xFF 分隔）
  → 逐 opcode 執行該段
```

跳段的程式碼在 `sub_1A606` 開頭：讀 `arg_0`，反覆呼叫 `sub_18DC8`
掃到 `0xFF`，重複 `arg_0` 次。所以**事件記錄的 `Index` 是腳本段號**，
不是字串序號。

## 2. 直譯器

`sub_1A606` 的主迴圈：

```asm
call sub_18DC8          ; 讀 opcode
sub  ah, ah
sub  ax, 1              ; switch 50 cases
cmp  ax, 31h
jbe  short loc_1A673
add  ax, ax
xchg ax, bx
jmp  cs:jpt_1A676[bx]   ; 跳表
```

腳本指標是 `word_1042A`，腳本緩衝基底 `0x6052`：

```asm
sub_18DC8:              ; 讀下一個位元組並前進
        mov     bx, word_1042A
        inc     word_1042A
        mov     al, [bx+6052h]
```

## 3. 顯示字串的三個 opcode

```
01 NN   sub_1905E  → loc_16E79  靠左
02 NN   sub_19074  → loc_16EFD  開一個 0x26×0x16 的視窗
04 NN   sub_19110  → loc_16F52  算出長度後置中
```

三者共用同一組取字串的程序：

- `sub_18FD0` 讀一個位元組 N，把字串指標 `word_154C0` 重設到區塊開頭
  （`word_1042C`）再往後跳 N 條。
- `sub_19016` 從那裡讀到 `0xFF` 為止，存進 `0x54D0`。

`04` 的置中是算出來的：`repne scasb` 量長度、`sub cx, 1Ch`（欄寬 28）、
`neg`、`shr 1`。

## 4. opcode 長度表

腳本能一路走完不需要解出全部語意 —— 只要知道每個 opcode 吃幾個參數。

長度表本身在原版是一張查表，`sub_18F64`（跳過 N 個 opcode）用它前進：

```asm
loc_18F72:
        mov     bl, [si+6052h]   ; 讀該位置的 opcode
        sub     bh, bh
        shl     bx, 1
        add     si, [bx+15E6h]   ; ← 加上該 opcode 的長度
```

`ds:15E6h` 是 DGROUP 內偏移。這張表的內容當初是從程式碼數出來的：
**長度 = 1 + handler（含它呼叫的子程序）裡 `sub_18DC8` 的呼叫次數**。
（DGROUP 的初值段後來定位到 `MM2.EXE` 尾部，`EXE 檔內偏移 = DGROUP 偏移 + 0x8630`，
所以現在也可以直接把表撈出來對。）`sub_18FD0` 內含一次，所以顯示字串類都是 2。

靜態數呼叫點會漏掉**迴圈與條件分支**：`sub_19912`（opcode `0x12`）裡的
`cmp si, 0Ah / jl` 會讀十個位元組，靜態只看得到三個呼叫點。這樣數出來的表
讓 1,363 段裡 83.7% 走到段尾。

剩下的由資料補齊 —— 每段腳本必須恰好走到段尾，這條約束把八個 opcode 的
長度定了下來，**全部 1,363 段 100% 走完**：

| opcode | 靜態數 | 修正後 | 程式碼裡的原因 |
|---|---|---|---|
| `0x12` | 4 | 13 | 迴圈讀 10 個 + `byte_10415 == 0x80` 時再讀 2 個 = 1+10+2 |
| `0x13` | 4 | 11 | 同樣的十個一組 |
| `0x15` | 5 | 4 | 有一條分支不會走到 |
| `0x21` | 1 | 4 | |
| `0x23` | 1 | 3 | |
| `0x27` | — | 1 | 跳表裡沒有對應的 call —— 保留未用 |
| `0x2a` | 9 | 10 | |
| `0x2f` | 1 | 12 | |

兩邊對得起來：擬合說 `0x12` 是 13，回頭讀 `sub_19912` 正是
「迴圈十個 + 條件兩個」。這是資料與程式碼互相驗證，不是單純把參數調到好看。

## 6. 現況

`internal/game` 逐 opcode 執行腳本，認得**六個**顯示字串的
（`01`/`02`/`03`/`04`/`05`/`06`），其餘照長度跳過。
**EVENTSI 的 1,865 個事件格裡 1,320 個（70.8%）能顯示訊息，
EVENTSO 的 818 個裡有 369 個（45.1%）** —— 野外的事件多半不是顯示訊息。
腳本本身 100% 走得完，沒顯示訊息的段是真的沒有顯示字串的 opcode：
剩下的以 `14`（事件消耗）、`2b`（條件跳躍）、`12`／`13`（固定遭遇）為大宗，
那幾種本來就不該有訊息。

未解的 opcode 一律不猜語意：長度已知就跳過，長度未知就停在那裡。

## 7. 城鎮設施：招牌與入口是兩格

設施的**招牌格只顯示名稱**，腳本就是一句 `04 NN`：

```
(7,5)  04 01   Middlegate Inn
(5,4)  04 02   S.J. Blacksmith
(7,6)  04 04   Gateway Temple
(9,7)  04 05   Turkov's Training
```

真正的**入口在相鄰的格子**，腳本是另一個固定模式：

```
(7,7)  0b 05 00  0e 04
(4,6)  0b 04 00  0e 03
(10,7) 0b 06 00  0e 02
(7,3)  0b 03 00  0e 01
```

`0x0b` 讀兩個位元組，第一個經 `sub_18EE6` 換算後交給 `sub_17036`。
`sub_18EE6` 是一張二維查表：

```asm
cmp     [bp+arg_0], 80h      ; ≥ 0x80 一律回 0x4B
jb      short loc_18EF8
mov     ax, 4Bh
...
dec     [bp+arg_0]
mov     al, byte_1039C       ; 當前城鎮編號 0–6
cmp     ax, 6                ; switch 7 cases
jmp     cs:jpt_18F08[bx]
...
mov     al, [bx+164Ch]       ; 城鎮 0 用這張
mov     al, [bx+167Ch]       ; 城鎮 1
mov     al, [bx+16ACh]       ; 城鎮 2、5
mov     al, [bx+1662h]       ; 城鎮 3
mov     al, [bx+1694h]       ; 城鎮 4、6
```

**同一個設施編號在不同城鎮會換算成不同的畫面**，這就是為什麼各城的
旅店、鐵匠鋪能共用同一套腳本模式。

五張表都在 DGROUP（`ds:164C` 起），內容見 §「五張換算表」。
**`ds` 的基底不等於 `cs`** —— 把它當成 `0x10000` 去撈，讀出來的是程式碼不是資料；
正確的換算是 `EXE 檔內偏移 = DGROUP 偏移 + 0x8630`。

## 8. 觸發條件：`Kind` 是方向遮罩

事件不是「走到就跑」。`2PLAY sub_1A8C4` 在 `Cell` 相符之後還要
`test Kind, ds:16D2[朝向位移]` —— 高 nibble 的四個位元對到北／東／南／西
（`0x80`／`0x40`／`0x20`／`0x10`），**面向不對就整筆跳過，腳本一行都不跑**。
完整推導、資料分布與 DOSBox 逐步對照在
[`02-data-files.md`](02-data-files.md)「Kind 是方向遮罩，不是類型碼」。

低 nibble 從來沒被讀過（遮罩只會是那四個值其中一個），所以那筆
`EVENTSO` 段 37 的 `Kind=0xF1` 不影響行為 —— 但**不要拿它當解析過濾器**，
那樣會讓整段消失。

opcode 本身沒有未解的了：`EVENTSI.DAT`／`EVENTSO.DAT` 用到的 49 種
全部有語意，直譯器也全部有分支（`TestEveryOpcodeInDataIsHandled` 守著）。
唯一「認得但不做」的是 `0x08`，它改的是主迴圈的讀取行為（見本檔
〈直譯器本體〉），在 remake 一次讀完整段的模型下沒有對應動作。

`0x2b`（232 段以它開頭）的旗標 `ds:0509` 語意也解了：**設定它的是戰鬥模組**，
**清掉它的是移動**，所以它的意思是「自從上一次移動之後打過架」。

## 6.5 長度表反過來佐證語意

`0x12` 與 `0x13` 是同一支 handler，差別只在參數：`0x13` 用 `arg=1` 呼叫
`0x12` 的 handler，於是 `ds:0415` 不是 `0x80`，那兩個附加位元組就不讀。
長度表給的 13 與 11 正好是 `1 + 10 + 2` 與 `1 + 10` —— 語意與長度互相對上，
兩邊都不是猜的。

## 7. 條件旗標 `ds:0509`

`0x2b` 出現 385 次，其中 **342 次是整段腳本的第一個 opcode** —— 幾乎每段
腳本都以一次條件判斷開頭。

旗標的生命週期（位址是 `2PLAY.img` 的偏移）：

| 動作 | 位置 | 說明 |
|---|---|---|
| 清除 | `0x4323` | **隊伍移動之後**。更新 `ds:0393`／`ds:0394`（隊伍 X/Y）、設 `ds:039B = 1`、`ds:6050 = 1`，然後清掉旗標 |
| 清除 | `0x43C1`、`0x5C93`、`0x5E5F` | 另外三處，脈絡待確認 |
| 設定 | `2COMBAT.img` `0x9C03`、`0xA64E`、`0xA682` | **都在戰鬥模組裡** |
| 讀取 | `0xA1EE` | `0x2b` 的 handler |
| 讀取 | `0x7ED6` | 與 `ds:6050` 一起判斷，抑制某個動作 |

設定它的三處全在**戰鬥模組**，清除它的在**移動**之後 —— 所以
`ds:0509` 的意思是「**自從上一次移動之後打過架**」。342 段腳本以
`2b N` 開頭，多半是「已經打過了就別再演一次開場」。

腳本層另有一組條件：`ds:042F`。設定它的是 `0x19`（給予物品成功與否）、
`0x32`（測試，交給 root 的 `sub_72FA`）與付款那組函式；讀它的是
`0x10`（成立就跳過）與 `0x11`（不成立就跳過）。兩組旗標互不相干。

remake 已經實作 `0x2b`／`0x10`／`0x11` 與 `ds:0509` 的完整生命週期
（`World.Flag`：遭遇發生時設、移動時清）。`ds:042F` 那組的測試指令
語意未解，所以恆為 false。

## 8. 角色欄位的讀寫：`0x15` 與 `0x18`

兩個 opcode 是同一支程式（`sub_19A02`）的兩個入口，差別只在旗標參數：

```
15 對象 欄位 遮罩        sub_19A02(0)   讀 → ds:042F |= 值 & 遮罩
18 對象 欄位 遮罩 新值   sub_19A02(1)   寫 → 欄位 = 欄位 & 遮罩 | 新值
```

`0x18` 出現 240 次、`0x15` 248 次，是腳本裡最常見的兩個 opcode。

### 對象怎麼選

```asm
ds:54C2 = ds:042F        ; 保存進來時的旗標
ds:54BD = 0              ; OR 值
ds:042F = 0
...讀完參數後...
cmp  [bp-2], 80h
jb   short 不改
mov  al, ds:54C2
mov  ds:54BD, al         ; ← 對象 bit 7 設起來時，寫入值改用保存的旗標
不改:
and  [bp-2], 7Fh
```

| 低 7 位元 | 對象 |
|---|---|
| 0 | 全隊，由最後一人往前 |
| 1–6 | 第 N 人 |
| 9 | 前一個選中的那一位（`ds:54BE`）|
| 超過隊伍人數 | 改成第 1 人 |

`ds:54BE` 的寫入端掃過全部十五個資料庫，只有三處，全在 `2PLAY`：

| 位址 | 動作 |
|---|---|
| `sub_1A082`（opcode `0x26`）| 玩家選完隊員後寫入編號 —— 主要來源 |
| `sub_199B8`（`0x199D4`）| 對象值是 9 而 `ds:54BE` 還是 0 時，退回用 `ds:54C2`（進入事件時保存的 `ds:042F`）並寫回 |
| `sub_1A8C4`（`0x1A8D5`）| 每次事件開始清成 0 |

所以「前一個選中的那一位」的生存期是**一次事件執行**，不跨事件。
對象值 9 在沒有人被選過時不會落空，它退回 `ds:042F` 的值。
opcode `0x31`（`sub_1A4BC`）另外把對象值 **8** 也對到 `ds:54BE`，
退回值同樣是 `ds:042F`。

資料裡出現的對象值是 `00`（88 次）與 `01`–`09`（各 15–19 次），
與這個表相符。

### 欄位選擇器：原版自己列出來的角色記錄欄位圖

`sub_1AA00(記錄基底, 選擇器)` 是一張 **128 項的跳表**，每一項把
「基底 + N」寫進 `ds:9FF2`、寬度寫進 `ds:9FF1`：

```asm
mov  ax, [bp+4]      ; 角色記錄基底
add  ax, 62h         ; ← 就是這個 N
jmp  共用尾巴        ; mov ds:9FF2, ax
```

128 項裡 126 項是這個形狀，另外兩項（`0x00`／`0x01`）指向 `sub_1B0B2`，
不是單純的位移。寬度不是 1 的由函式開頭的 `cmp`/`je` 挑出來：
`0x31`／`0x3E` 是 4 bytes，`0x20`／`0x28`／`0x35`／`0x38`／`0x3A`／`0x3C` 是 2 bytes。

`cmd/mm2data` 從玩家自備的 `2PLAY.OVL` 產生 `data/fields.json`
（重建映像時 OVL 載入到偏移 `0x7E10`，整個檔逐位元組相符）。

這張表把先前逐項推出來的角色記錄欄位一次全部對上了：

| 選擇器 | 記錄偏移 | 欄位 |
|---|---|---|
| `0x02`–`0x0b` | +0…+9 | 名稱（10 字）|
| `0x0c`–`0x0f` | +12…+15 | 性別／陣營／種族／職業 |
| `0x10`–`0x15` | +16…+21 | 力量／智慧／人格／速度／準確度／運氣（耐力不在區塊裡，見 02 §5）|
| `0x16`–`0x1d` | +22…+29 | 八種抗性 |
| `0x1e` | +30 | 盜行 |
| `0x22`–`0x27`、`0x2b`–`0x2d` | +106…+114 | 屬性的當前值那一區 |
| `0x28`／`0x29` | +88 | 法力（word／byte）|
| `0x2f` | +33 | 年齡 |
| `0x31`–`0x34` | +98 | 經驗值（dword）|
| `0x35`／`0x36` | +90 | 法力上限 |
| `0x38`／`0x39` | +92 | 寶石 |
| `0x3a`／`0x3b` | +94 | 生命 |
| `0x3c`／`0x3d` | +96 | 基礎生命上限（有效上限另在 +116，見 02 §5） |
| `0x3e`–`0x40` | +102 | 黃金（dword）|
| `0x41`–`0x44` | +36…+39 | 防護等級／食物／狀況／運氣 |
| `0x45`–`0x68` | +40…+75 | 物品的六組平行陣列 |
| `0x69`–`0x6c` | +76…+79 | 近戰骰面／近戰加成／射擊骰面／射擊加成 |

是 `0x7b`（+125，48 次）、`0x7d`（+127，17 次）、`0x75`（+122，12 次）——
數量與「全遊戲的任務進度」相符。存檔一直原樣保留這一段，所以雖然語意
未解，往返仍然正確。

### `0x16`：隊伍有沒有這件物品

```asm
mov  si, sub_17162(第 N 人)   ; 角色記錄
cmp  [bx+si+3Ah], dl          ; 背包的六格
je   命中
cmp  [bx+si+28h], dl          ; 已裝備的六格
jne  下一格
命中:
inc  ds:042F
```

`+0x28` = 40、`+0x3A` = 58，正是先前從 `sub_CE12` 推出來的物品區起點 ——
**兩條獨立的路徑指向同一個排法**。找到人就停，不會把整隊掃完。

腳本查的物品編號是 `0x32` 與 `0xD5`–`0xE6`，都落在物品表的高編號段，
形狀就是任務道具。

## 9. 換地圖：`0x0c`

```
0c 目標 座標
```

```asm
test [bp-2], 40h          ; 目標 bit 6
je   不隨機
call rand(1, 14h)         ; 隨機地圖
add  al, 5
cmp  al, 11h
jb   不加
add  [bp-2], 10h          ; 跳過 0x11–0x20 那一段
不加:
or   [bp-2], 80h
不隨機:
cmp  [bp-2], 80h
jb   有座標
call rand(1, 0FFh)        ; 隨機座標
有座標:
mov  ds:0393, 座標 and 0Fh   ; X
mov  ds:0394, 座標 shr 4     ; Y
and  [bp-2], 3Fh             ; 地圖編號
call sub_1B5EA(地圖, X, Y)
```

### X 與 Y 誰是誰

不是猜的。`sub_142DE`（前進一步）把 `sub_1428C` 給的兩個增量分別加到
`ds:0393` 與 `ds:0394`，而 `sub_1428C` 依朝向給：

| 朝向 | 第一個增量（→ `ds:0393`）| 第二個增量（→ `ds:0394`）|
|---|---|---|
| `'N'` | 0 | +1 |
| `'S'` | 0 | −1 |
| `'E'` | +1 | 0 |
| `'W'` | −1 | 0 |

所以 `ds:0393` 是 X、`ds:0394` 是 Y，而且**北是 +Y** —— 與「第 0 列在南邊」
一致，也與 remake 的 `Facing.Delta()` 逐項相同。

### 驗收

腳本裡寫死的傳送目標有 **57 種，全部落在 60 張地圖之內**，另有 10 次隨機傳送。
`& 0x3F` 取錯的話立刻會出現 60 以上的目標。

### 沒指定落點時

`sub_1B5EA` 的 X 參數是 `0xFF` 時改用 `ATTRIB.DAT` 的 `+14`
（一樣是低 nibble = X、高 nibble = Y）。**`0x0c` 走不到這條** ——
它給的 X 是 `座標 & 0x0F`，永遠在 0–15。會用到的是別的換圖路徑
（走到地圖邊緣接鄰圖之類），那些還沒解。

地圖 0 的 `+14` 是 `0x57` → (7,5)，走過去正是「中門旅店」那一格。

## 10. 欄位加減：`0x1f` 與 `0x20`

```
1f 對象 欄位 寫回長度 值低 值中 值高    加
20 對象 欄位 寫回長度 值低 值中 值高    扣
```

「對象」與「欄位」的規則同 §8。值是 **3 個位元組的小端序**：
`sub_18DF8` 先呼叫 `sub_18DD8` 讀兩個湊成 word，再讀第三個當高位。
對象的 bit 7 設起來時，運算元改用進來時的 `ds:042F`，那三個位元組跳過
（原版直接 `add ds:042A, 3` 前進腳本指標）。

運算的寬度來自選擇器（`ds:9FF1`，1／2／4）；**寫回幾個位元組則是第三個
參數**（原版 `repnz movs` 的長度，值 3 會先變成 4，值 0 表示不寫）。

### 扣不動時不寫回

```asm
cmp  ds:9FF0, ...        ; 目前值
jbe  正常相減
mov  byte ptr [bp-6], 0
mov  ds:042F, 0          ; ← 結果清 0
jmp  寫回段
寫回段:
cmp  ds:042F, 0
je   跳過                ; ← 結果是 0 就整段不寫
```

所以「付不出來」不會順手把欄位歸零。

**付款不是另一組 opcode，就是 `0x20`。** 它把 `ds:042F` 設成成敗，
而 `0x10`／`0x11` 讀的正是那個位元組 —— 三者是同一條路徑的三段。

### 對象 0 是「每個人各自加減」

不是全隊湊總額：`0x19EE6` 那段對 `ds:0426` 個成員各呼叫一次
`sub_19CB8`，每次用**同一個**數值。

`sub_19716` 讀一個子命令：1–7 依值跳到不同設施 overlay；指定的其他代碼
交給特殊設施分流，轉派到腳本庫：

| 子命令 | overlay | 設施 | 五座城鎮的招牌 |
|---|---|---|---|
| 1 | 5 = `1RETINN` | **旅店** | Carriage Inn、Tundaran Arms Inn |
| 2 | 7 = `2MISC2` | **訓練基地** | Turkov's Training、Island Training、Training Academy |
| 3 | 12 = `2BRAIN` | **酒館** | Slaughtered Lamb、Boar's Tongue Tavern |
| 4 | 14 = `2TEMPLE` (`0xCA88`) | **神殿** | Gateway Temple、Eleusinian Temple、White Dove Temple |
| 5 | 14 = `2TEMPLE` (`0xCB9C`) | **法師公會** | Sleepy's Mage Guild、Blackrock Mage Guild |
| 6 | 13 = `2SMITH` | **鐵匠** | Drewnhald Ironworks、Thundrax Weaponry、Bestway Blacksmith |
| 7 | 12 = `2BRAIN` (`0xC7E2`) | **大腦淨化** | Brain Detoxification |
| 8 | 12 = `2BRAIN` (`0xC130`) | **競技賽** | 入口自成一格，三座城各一個 |

代碼 9 以上分兩條路：一部分轉派腳本庫（見下表），其餘直接進 `2CAVES` 的
特殊裝置（傳送機、滑梯陷阱、年代之門、捐獻換經驗、馬戲團），

對照怎麼定的：**五座城鎮各有一個 `0e 01`…`0e 06`，一個不多一個不少**，
而每一格四周的招牌都同一類。訓練基地走 `2MISC2` 這件事有旁證 ——
升級所需經驗的表 `sub_CC8C` 就在那個 overlay 裡。

> **證據狀態（2026-08-12）。**下列特殊轉派已由 `2PLAY.img` 位址空間的
> `sub_19716`、`sub_1956E` 與 `loc_196F6` 交叉追到，屬於**已證實**。

### 特殊設施：轉派至腳本庫

`sub_19716` 讀完 `0x0e` 的代碼後結束目前的事件段；特殊設施分流會以該代碼
選出腳本庫段與 1 起算 selector，再由 `loc_196F6` 載入並執行。範圍如下：

| 代碼範圍 | 腳本庫段 | selector 基準 |
|---|---:|---:|
| `09`–`10` | 60 | `08` |
| `11`–`37` | 61 | `10` |
| `38`–`4b` | 62 | `37` |
| `4c`–`54` | 63 | `4b` |
| `56`–`5b` | 64 | `55` |
| `5c`–`5e` | 65 | `5b` |
| `65`–`69` | 66 | `64` |
| `6a`–`7c` | 67 | `69` |
| `97`–`98` | 68 | `96` |
| `e3`–`f3` | 69 | `e2` |
| `f4`–`fb` | 70 | `f3` |

selector = 代碼 − 基準；腳本庫經解析後採零起算，因此 selector 1 對
`Scripts[0]`。例如 Middlegate 西側 `(0,5)` 的事件記錄 `Cell=80, Index=21`
先正常執行 `Scripts[21] = 0e 11`，再被轉派至段 61 的 `Scripts[0]`；這條
腳本顯示「付 10 金傳送至 Sandsobar」並以 `0x09` 停住等待 Y/N。這正是 remake
曾經缺失、造成問題不會在正確時機出現的引擎路徑。

證據輸入為 `2PLAY.OVL`，SHA-256
`7078f30f87f9f25f8c296dc9207d70957c785b0ed83ad763e20e4012a82d2202`；
重建影像的 IDA 位址空間中：`sub_19716 @ 0x19716`、`sub_1956E @ 0x1956E`、
`loc_196F6 @ 0x196F6`。這是資料流與輸入暫停的證據，**不**表示特殊設施
overlay 的逐畫面 UI 已完成 parity。

remake 因此改用子命令認設施，**而且不能再看招牌字串** —— 招牌格與入口格
是分開的兩格。Middlegate 的旅店招牌在 (7,5)、入口（`0e 01`）在 (7,3)；
神殿招牌在 (7,6)、入口（`0e 04`）在 (7,7)。拿招牌判會在招牌格就把人
送進設施，走一趟會進去兩次。

## 12. 全域變數：`0x17`／`0x1a`／`0x22`

```
17 選擇器 ??   結果 = *全域[選擇器]     （第二個參數讀了沒用）
1a 選擇器 值   *全域[選擇器] = 值
22 下限 上限   ds:03CA 落在範圍內就把結果設成 1
```

`sub_18E22` 把選擇器換成 DGROUP 位址。它不是一張表，是一串
`cmp`／`jne`：

| 選擇器 | 位址 |
|---|---|
| `0x00`–`0x17` | `0x03F6 + N` —— **連續 24 個位元組的劇情旗標** |
| `0x23` | `0x03D8` |
| `0x27`–`0x2A` | `0x03DC`–`0x03DF` |
| `0x2B` | `0x03E0` |
| `0x2C` | `0x03E1` |
| `0x32` | `0x03EA` |
| `0x33` | `0x03F1` |
| `0x3B`–`0x3E` | `0x03F2`–`0x03F5` |
| `0x80`–`0x83` | `0x03EC`–`0x03EF` |
| `0x84` | `0x03CA` |

腳本實際用到 30 種選擇器，全部對得到位址。

### `ds:03CA` 是世紀

`0x22` 在腳本裡出現 43 次，**兩個參數的值域是 5–9** —— 正是 MM2 時間旅行
涵蓋的世紀範圍，而 `STR.DAT` 裡也有 `You shouldn't be here until you save
the King in the 9th century.` 這樣的句子。同一個值也可以用選擇器 `0x84`
讀寫。等級：**強推論**。

劇情狀態因此分兩處：**全域的 24 個位元組**（這裡）與**每個角色記錄尾端的
12 個位元組**（`+118`–`+129`，見 §8）。存檔兩邊都要存。

## 13. `0x28` 又印證了一次物品區的排法

`sub_1A126` 掃的是記錄 `+0x3A`（背包編號），找到就呼叫 root 的
`sub_13766(記錄, 格號)`。那支函式把**三個平行陣列**一起往前補：

```asm
al = [di+3Bh]   ;  編號  +58
[bx+3Ah] = al
al = [di+41h]   ;  充能  +64
[bx+40h] = al
al = [bx+si+46h] ; 屬性  +70
[bx+46h] = al
```

`+0x3A` = 58、`+0x40` = 64、`+0x46` = 70 —— 正是先前從 `sub_CE12`
推出來、又被 `0x16` 的掃描印證過的那三個起點。**第三條獨立路徑，
同一個排法。**

## 14. 顯示圖片：`0x0b`

`sub_18EE6(參數)`：

```
參數 >= 0x80 → 圖號 75
否則 參數減一，再依場景碼 ds:039C（0–6）挑一張表查
```

五張表在 DGROUP 裡是連續的：

| 場景 | 表 |
|---|---|
| 0 | `ds:164C` |
| 3 | `ds:1662` |
| 1 | `ds:167C` |
| 4、6 | `ds:1694` |
| 2、5 | `ds:16AC` |

起點相距 22／26／24／24，而腳本的參數最大到 24 —— 所以**場景 0 的第 23、
24 項讀的其實是場景 3 那張表的頭兩個位元組**。`sub_18EE6` 沒有上界檢查，
原版就是這樣讀的，remake 照抄（每張表都取 26 項）。

表裡的值是 `monsters.16` 的圖號（1–75），腳本用到 21 種。高號那幾張正是
房舍、城堡、店家、寶箱 —— 與 §2 的 contact sheet 末尾對得上。

場景碼 `ds:039C` 由 `sub_1B1D4` 從 `ATTRIB.DAT` 的 `+4` 算出來，
換算方式還沒解；室內圖的 `+4` 低 nibble 全是 0，所以城鎮與地城都走第 0 張表。

## 謎題：`0x2f` 與 `0x30`

這一對是全表唯一會向玩家要求**打字**的機制：

	2f              ; 讀十個字進 ds:54C4
	30 XX×10        ; 與腳本裡的十個位元組比對，結果進 ds:042F

`0x30` 長 **11 個位元組**，是整張表最長的一條 —— 答案直接內嵌在腳本裡，
沒有另外的字串表。

編碼是 `明文 = 0x11A − 位元組`（`2PLAY` 的 `0x1A47C`：`sub ax, 11Ah` 之後
`neg ax`），`0xFA` 還原成空白，是十格固定長度的填充。全部七題解出來是：

| 位置 | 提問 | 答案 |
|---|---|---|
| `EVENTSI` 段 53 | What is the access code? | `46`／`23` |
| `EVENTSI` 段 54 | 同上 | `64`／`32` |
| `EVENTSO` 段 6 | 「我是你的守護天馬。我的名字是什麼？」| `MEENU` |
| `EVENTSO` 段 9 | 「馬克丟了什麼？」（Death Spider）| `KEYS` |
| `EVENTSO` 段 64 | 六塊巨石的祭壇問「通關密語？」| `DRUIDS` |

**這幾題的謎底靠英文文字遊戲**（`What has Mark lost?` → `KEYS`、
六塊巨石 → 德魯伊），翻成中文之後線索與答案對不起來，玩家永遠解不開。
remake 因此把答案附在提問後面 —— 而答案是**從腳本解出來的**，不是另外
建一張表，資料改了它就跟著改（`World.TextExpect`）。

結局的中止碼不走這條路：控制室在 `2SMITH` 裡，把玩家打的十個字拿去跟
`ds:45FC` 的 `"WAFE      "` 比對，另外還要隊伍裡有人的記錄 `+129` bit 5
是 1。密碼電文解開之後是泰拉憲法的序言（`STR.DAT` 302–305）。

長度不是推的：`data/opcodes.json` 的第 48 項就是 11。
一度把它記成 2，直到用兩位元組的腳本測試整條 opcode 都沒被執行 ——
**長度表錯了的症狀是「什麼都沒發生」，不是「行為錯誤」**，
因為直譯器讀不到完整的運算元就停在那裡。

## `0x24` 與 `0x25`：全隊湊錢

兩條的形狀相同，只差扣哪一欄：

	讀一個 16 位元運算元（低位在前）＝ 金額
	把全隊的該欄位加總
	總和 < 金額 → ds:042F = 0，**一毛都不動**
	否則依序扣到湊滿 → ds:042F = 1

`0x24` 扣金錢（`+102`，32 位元加總，運算元的高位補 0）、
`0x25` 扣寶石（`+92`，16 位元）。`0x25` 逐位元組讀兩次再自己組 word
（`(hi << 8) + lo`），`0x24` 走 `sub_18DD8` 一次讀完 —— 兩種寫法，
同一個位元組序。

**先加總比對、通過才進扣款迴圈** —— 所以「付到一半發現不夠」
不會發生，這是原版就有的保證，不是 remake 加的。

### `ds:0416`：隊伍位置對應的名冊索引

加總與扣款都跳過 `ds:0416[i] >= 24` 的位置。名冊只有 24 筆，
所以那一排是**每個隊伍位置對應到名冊的哪一筆**，超出範圍就是空位。

## `0x2d`：隊伍成員條件

	bit 7 → 比種族（記錄 +14）
	bit 6 → 比性別（記錄 +12）
	bit 5 → 找「對上的」；沒設就是找「沒對上的」
	低 nibble → 值 A

**種族與性別都沒要比時比的是職業（記錄 +15）。** 而且比的是**兩個值**：
值 A 是第一個運算元的低 nibble（`0x1A365` 的前置比對），值 B 在種族與性別
都沒設時取自第二個運算元的低 nibble（`0x1A27C`），否則與 A 相同。
**任一個對上就算這個人符合。**

兩個值不是推的，台詞直接講明：`2d 03 05` 那一格印
`I cannot help anyone but Clerics and their Robber assistants.` ——
3 是牧師、5 是盜賊。八個職業考驗一律 `2d 0N 05`，第二個值固定 5 也是
同一件事：**盜賊隨行是允許的**。

bit 5 同樣有資料佐證：`2d 40 00`（比性別、值 0 ＝ 男、bit 5 沒設）問的是
「隊伍裡有沒有女性」，`2d 24 00`（bit 5 設、職業 4）問的是「有沒有巫師」。
八個考驗的閘門沒有 bit 5，所以**成立代表擋下來**（隊伍裡有不符合的人）。

程序開頭先把 `ds:042F` 清成 0，找到一個符合的人就成立。比較會互相覆寫：
旗標同時成立時最後寫進結果的是種族。資料裡沒有「性別 ＋ 種族」的組合，
所以這個順序不影響任何一條既有腳本。

## `0x2e`：教法術

	運算元 1 bit 7 → 牧師系（職業 3 牧師、1 聖騎士）
	          否則 → 巫師系（職業 4 巫師、2 弓箭手）
	運算元 1 低七位 → 寫哪一個位元組：記錄 +81 + (值 - 110)
	運算元 2 → OR 進去的位元遮罩

原版的算式是 `值 - 6Eh + 51h`，也就是 `值 - 29`；`值 = 110` 時正好
落在 `+81` —— 那是「會不會某條法術」的位元圖。

**兩個職業一組**與施法能力對得上：巫師與弓箭手共用巫師系、
牧師與聖騎士共用牧師系。這個配對是從程式碼讀出來的（預設 4／2，
bit 7 打開變成 3／1），與 `CanCast` 那份名單互相印證。

位元是 **OR** 進去的，不是覆蓋 —— 教一條不會洗掉已經會的。

## `0x31` 與「對象」的完整約定

`0x31`（長 4）的前半把對象與值解出來：

	ds:0430 |= 2
	對象 = 運算元 1（一個位元組）
	值   = 運算元 2–3（word）
	對象 >= 80h → 對象 &= 7Fh，**值改用 ds:042F**
	對象 == 0   → 全隊（ds:0426 人）
	否則 對象--
	    對象 == 8（原值 9）→ 對象 = ds:54BE
	                         為 0 就退回 ds:042F
	                         非 0 再減一
	    對象 > ds:0426     → 對象 = 0
	對選定的每個人呼叫 sub_13928(記錄, 值, …)
	sub_1732A() 非 0 → ds:0395 = 1（要求重畫）

這段補上了 `sub_19A02` 那個約定裡一直缺的一塊：**「9」在 `ds:54BE`
為 0 時退回條件暫存器的值**，不是退回第 1 人。填 `ds:54BE` 的程式碼
仍未找到，所以引擎目前照舊當成第 1 人 —— 但已經知道正確的退路
長什麼樣，找到之後改一行就好。

`sub_13928` 的前段是抗性判定：

	狀況 >= 80h（重症）→ 直接跳過
	擲 rand(1, 100)
	擲值 < 記錄 +22 + ds:03D6 → 完全擋下

那個加總正好是「抗性百分比 ＋ 全隊抗性加成」（`ds:03D6` 是
神聖之光那組全域計數器之一）。**`+22` 是抗性這件事因此有了第二個
獨立的用處** —— 在此之前只有欄位表這一個來源，而屬性區的寬度之爭
剛好也繞著這一格打轉。

抗性 100 擋的是 `rand(1,100) < 100`，也就是擲出 100 才會被打中 ——
是 99%，不是 100%。

## `0x2a`：待領的獎賞

	3 bytes → 金錢（與 0x1f／0x20 同一種 3 位元組小端序）→ ds:695C（32 位元）
	2 bytes → 寶石 → ds:695A
	3 × 3 bytes → 三件物品 → ds:6950／ds:6956／ds:6953
	ds:0434 = 0FFh   ; 標成「有東西待領」

三件物品用**三個平行陣列**存，與角色記錄的背包（`+58`／`+64`／`+70`）
同一種排法。真正發給隊伍的程式碼在別處，由 `ds:0434` 觸發。

長度先前記成 9，實際是 15 —— `data/opcodes.json` 一直是對的。
把運算元逐項加起來（3 + 2 + 9 = 14，加 opcode 本身 15）正好吻合，
這是驗長度最直接的辦法：**能把每個位元組都指派出去，長度就對了**。

## 直譯器本體：`ds:9E48`／`ds:9F7C`／`ds:50FF`

追 `0x08`（`sub_1940E`）追到了直譯器的三個核心位址：

	ds:9E48  腳本緩衝區
	ds:9F7C  目前讀到的位置（word）
	ds:50FF  讀取模式

主迴圈在 `0x15719`：

	al = ds:9E48[ds:9F7C]
	if al == 0FFh:
	    if ds:50FF == 0FDh:      ; 特殊模式
	        ds:9F7C = 0          ; **位置歸零，重頭再讀**
	        al = ds:9E48[0]
	if al 的 bit 7 = 1:
	    al = rand(1, al and 7Fh) ; 高位元表示「這個位元組是隨機的」

`0x08` 做的就是把模式切成 `0FDh`（再呼叫 `sub_193B8(1)`）——
所以它是**讓腳本從頭再跑一次**的機關，不是一般的動作 opcode。

順帶解出兩件事：終止碼是 `0FFh`，而**腳本位元組的 bit 7 打開時，
實際值是 `rand(1, 低七位)`** —— 腳本可以內嵌隨機數。

模式旗標還有 `0FFh` 這個值（`0x157AE` 比對），語意未解。
`0x08` 本身沒有實作 —— 它改的是直譯器的讀取行為，
要動整條主迴圈才有意義。

## `0x23`：日期條件與「今天」的存放方式

	今天 = ds:03A2[ds:03CA × 2]
	運算元 1 == 0B5h → 單數日才成立
	運算元 1 == 0B6h → 偶數日才成立
	否則             → 今天落在閉區間 [運算元 1, 運算元 2] 才成立

`ds:03A2` 是**一排計數器**、`ds:03CA` 選其中一格。索引 9 指到的正是
`ds:03B4` —— 自然之門（`sub_1C7DA`）把 `ds:03B4` 寫死在程式碼裡，
所以它必須先確認 `ds:03CA == 9`，否則讀到的就不是「目前的日子」。
那條法術在第 150 天把索引改成 8（也就是換讀 `ds:03B2`），
於是自己的前提不再成立 —— 時限就是這樣實作的。

## `0x21`：地圖可以在遊戲中被改寫

	運算元 1 → 格子索引（低 nibble X、高 nibble Y）
	運算元 2 → ds:59D6[格]（第一個平面 ＝ Terrain）
	運算元 3 → ds:5AD6[格]（第二個平面 ＝ Attr）
	ds:0430 |= 1              ; 標記地圖被改過

`ds:59D6` 與 `ds:5AD6` 相隔 `0x100`，正是 `MAP.DAT` 一張圖的兩個
256 bytes 平面依序載入記憶體的結果 —— 所以第二個運算元對 Terrain、
第三個對 Attr，順序由檔案佈局決定，不必另外推。

**這是牆在遊戲中改變的機制**（暗門、事件打通的通道）。先前把地圖
當成唯讀資料，`0x21` 說明了原版並非如此。

## `0x26` 補上了「對象 9」缺的那一半

`sub_1A082` 迴圈讀按鍵直到選到為止：

	1–9        → 隊員編號（減一之後是索引）
	超出人數    → 無效，重來
	狀況 >= 81h → 死亡／石化那一類，無效，重來
	ESC (1Bh)  → 取消

選中的人存進 `ds:54BE` —— **那正是「對象 9」讀的那一格**。
在此之前 `scriptTargets` 只能把 9 當成第 1 人並標為假設；
現在填它的來源找到了，退路也完整：

	ds:54BE → 條件暫存器 ds:042F → 第 1 人

三條 opcode（`0x26` 填、`0x31` 讀並寫出完整退路、`sub_19A02` 給約定）
湊起來才拼出這個機制。

## 最後兩項：`0x00` 與 `0x27`

兩項都不是「還沒實作的動作」：

**`0x00` 是結束標記。** 它是長度表裡**唯一**長度為 0 的一項
（`data/opcodes.json` 逐項掃過）。原版靠這個 0 讓直譯器停下來，
不需要另外的終止判斷 —— remake 的 `run()` 在 `OpLen < 1` 時
直接收工，行為一致。

跳表裡 `0x00`／`0x01` 那兩格指向 `sub_1B0B2`，那支做的是
「這個記錄指標是名冊裡的第幾筆」（以 `130` 也就是記錄長度為步長掃
48 筆，結果進 `ds:9FF0`）—— 是共用的查詢程序，不是事件動作。
跳表的未用格指到一支現成的函式，是連結器排出來的結果，沒有語意。

**`0x27` 在跳表裡沒有對應的 call。** 長度是 1（只有 opcode 本身），
所以直譯器會跳過它。保留未用。

至此 **`EVENTSI.DAT`／`EVENTSO.DAT` 用到的 opcode 全部有解**。
