# MAP.DAT — 地圖

```
+0x0000  uint16 = 0x0078      索引表長度（120 bytes）
+0x0000  uint16[60]           每張地圖的檔案內偏移
+0x0078  地圖段 × 60          每段是一個 LZW 段，解出固定 512 bytes
```

索引嚴格遞增，最後一段延伸到檔尾。60 段全部解壓成功，長度一律 512。

## 1. 512 bytes = 兩層 16×16

```
+0x000  地形層  16×16，每格 1 byte
+0x100  屬性層  16×16，每格 1 byte
```

格位置是 **row-major**：格 n 在第 `n/16` 列、第 `n%16` 行，與事件表的 `Cell` 欄位同一套座標。

**第 0 列在南邊**，y 由南往北。依據見 §5。

## 2. 屬性層的 bit 7 = 這格有事件

**每一個事件格都在屬性層設了最高位（`attr[cell] & 0x80`）。**

驗證方式是拿事件表的 `Cell` 欄位（見 [`02-data-files.md`](02-data-files.md) §4）
與地圖屬性層取交集：

| MAP 段 | 事件數 | 設了 bit 7 的格數 | 交集 | 事件格有 bit 7 | bit 7 格有事件 |
|---|---|---|---|---|---|
| 0 Middlegate | 42 | 56 | 42 | **100%** | 75% |
| 1 Atlantium | 57 | 67 | 57 | **100%** | 85% |
| 2 Tundara | 69 | 75 | 69 | **100%** | 92% |
| 3 Vulcania | 41 | 70 | 41 | **100%** | 59% |
| 4 Sansobar | 50 | 64 | 50 | **100%** | 78% |

正向是 100%、五個段無一例外；反向不成立 —— 有些設了 bit 7 的格子沒有對應的
事件記錄，那些應該是牆或其他不經事件表處理的特殊格。等級：**已證實**
（`sub_15E68` 的 `and al, 55h` 把 bit 7/5/3/1 整個遮掉，證實它不參與牆的判定；
事件消耗的 opcode `0x14` 清的就是這個位元）。

## 3. MAP 段 k 對應 EVENTSI 段 k

上表同時確認了地圖與事件檔的段編號是同一套：**只有 MAP 段 0 對 EVENTSI 段 0
的事件格出現富集**（值 8 富集 5.3 倍、值 12 富集 4.4 倍），其餘 59 段都沒有。
把段編號錯開一格，富集就消失。

前五段依序是 Middlegate、Atlantium、Tundara、Vulcania、Sansobar，
與 `MM2.EXE` 尾部的城鎮列表同序。

## 4. 牆：每格四個位元

屬性層每個 byte 帶四個方向的牆：

```
bit 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0
      北       東       南       西      ← 1 = 有牆
  ↑       ↑       ↑       ↑
  另一個平面
```

移動判定是 `attr & (1 << bit) == 0` 才能走，出界一律當成有牆。

### 位元寬度來自程式碼

`sub_1423E` 依朝向設定遮罩與位移量：

| `ds:3CFh` | `ds:59C6h` 遮罩 | `ds:59C7h` 位移 |
|---|---|---|
| `'N'` | `C0` | 6 |
| `'E'` | `30` | 4 |
| `'S'` | `0C` | 2 |
| `'W'` | `03` | 0 |

`sub_15E68` 拿這組遮罩取值後再 `and 55h`（`0101_0101`）—— 只留每個
2-bit 欄位的**低**位元，也就是 bit 6/4/2/0。另一段程式碼先
`shr byte ptr [bp-2], 1` 再套同一組遮罩，取的是高位元 bit 7/5/3/1。
**所以那是兩個獨立的平面，形狀相同，牆只用低位元那一個。**

兩層在記憶體的位置由 root `sub_13A64`（開門，見下文）給出：

```asm
mov al, ds:394h      ; Y
shl si, 4            ; Y*16
mov al, ds:393h      ; X
add si, ax           ; si = Y*16 + X
mov al, [si+59D6h]   ; 第一層基底
...
mov [si+5AD6h], al   ; 第二層基底 = 59D6h + 0x100
```

### 位元與方位的對應來自資料自洽

**牆有兩面**：格 (x,y) 的東側位元必須等於格 (x+1,y) 的西側位元，
南北同理。這條不需要任何 oracle，資料自己就能檢驗。

24 種排列 × 兩層 × 高低位元跑下來：

| 排列 | 層 | 位元 | 自洽率 |
|---|---|---|---|
| **N=bit6 E=bit4 S=bit2 W=bit0** | **屬性層** | **低** | **93.8%** |
| N=bit4 E=bit2 S=bit0 W=bit6 | 屬性層 | 高 | 86.7% |
| （其餘 190 種） | | | ≤ 86.6% |

隨機期望 50%。93.8% 不是 100% 的原因是野外地圖不靠牆分隔，
而地圖邊界本來就不受這條約束。

自洽性只定得出「哪四個位元互為對面」，定不出哪個是北 —— 把 N/S 對調、
E/W 對調，同一組數字照樣成立。方位由 §5 的手冊地圖定錨。

### 判定式出自移動處理

`sub_142DE`（前進一步）先問 `sub_15E68` 能不能走：

```asm
call    sub_15E68
cmp     ax, 0FFFFh
jz      short loc_142F6   ; 回傳 -1 → 往下走，改座標
push    ax
call    sub_14478         ; 非 -1 → 撞到東西
```

而 `sub_15E68` 回傳 -1 的條件就是

```asm
mov     al, ds:59C8h      ; 當前格的屬性
and     al, ds:59C6h      ; 該方向的遮罩
and     al, 55h
or      al, al
jnz     short loc_15E8C
mov     ax, 0FFFFh        ; 沒有那個位元 → 可以走
```

`ds:509h`（腳本的條件旗標）在每次移動成功後被清成 0，
所以事件腳本裡的條件跳躍 `0x2b` 預設走「不跳」那條路徑。

### 三重旁證

1. **城鎮是封閉的。** Middlegate 最外圈朝外的 64 面全部有牆，一面不漏。
   對應錯了會漏出好幾個洞。寫成 `TestMiddlegateIsEnclosed`。
2. **牆線圖是一座城。** 照這個解讀畫出來，外圍封閉、內部是房間與走道、
   事件格都貼著牆 —— 城鎮該有的樣子。
3. **第一人稱視角畫得出來。** `TOWN.16` 的側牆寬度累加是 24 → 56 → 80 → 96，
   剛好等於同深度正牆的左緣（`(208-160)/2`、`(208-96)/2`、`(208-48)/2`、
   `(208-16)/2`）。素材配置與牆的判定互相對得上，走一趟走廊畫面就成立。

### 高位元平面

bit 7/5/3/1 **不是方向的性質，是整格的旗標**：bit 7 有事件、bit 3 不能休息、
bit 1 不能施法、bit 5 這一格吃照明。全部的讀取點與資料量見本檔後段
「屬性層的奇數位元」。這也是它們對向一致率只有 86.5%（牆位元 99.7%）的原因。


- **地形層每個 byte 的語意。** 把高 nibble 當 tile 索引 render 出來，
  野外段有可辨識的地理結構（大片草地、土路、山脈、對角海岸線），
  城鎮段則是每格不同（合理，城鎮每格都是不同建築）。但實際的 tile 對應表未定。
- 後 55 段對應哪些地城與野外區域。

下一步用原版 oracle 逐格移動截圖對照（見
[`docs/playtest/01`](../playtest/01-oracle-timeline.md) §5），
不要再用統計富集度硬猜其餘位元。

## 5. 座標系：第 0 列在南邊

手冊附的城鎮地圖把座標軸畫在**左下角**，y 由下往上。圖上每個設施標了
字母代號，右頁列出對應的店家名稱 —— 那些名稱正是事件腳本顯示的字串，
所以可以逐個對照。

拿手冊圖上的位置與事件表的格編號比對（`y = 格編號 / 16`）：

| 設施 | 事件表 | 手冊圖 |
|---|---|---|
| Gateway Temple 神廟 | (7, 6) | (7, 6) |
| Mountaineer 登山技能 | (3, 12) | (3, 12) |
| Middlegate Inn 旅店 | (7, 5) | (7, 4) |
| Slaughtered Lamb 食品店 | (5, 6) | (6, 6) |
| Arena 競技場 | (13, 6) | (12, 6) |
| Sleepy's Mage Guild 法師公會 | (7, 13) | (8, 13) |

**十處抽驗，y 有八處完全相同**（x 的落差是從掃描圖目測讀座標的誤差，
不是資料問題）。如果第 0 列在北，y 會系統性地差成 `15 - y`，
十處全部對不上。

這同時讓反組譯對上了：`sub_1423E` 給 `'N'` 的遮罩是 `0xC0`，也就是 bit 6。
先前靠自洽性把 bit 6 標成「南」，是因為 y 軸方向設反了；
方位改過來之後，程式碼、資料自洽性、手冊地圖三邊一致。

米德格特在世界地圖的位置也印在同一頁：**區域 C2，X=7 Y=3**。

## 6. 地形層那組位元：牆是實牆還是門

屬性層的 `bit 6/4/2/0` 是「這個方向有沒有牆」（見上文）。**地形層同一組位元
分辨那面牆是實牆還是門。**

判準是對向一致性 —— 牆有兩面，相鄰兩格對這面牆的記載必須一致：

| 檢驗 | 一致率 |
|---|---|
| 屬性層 `bit 6/4/2/0`（已知的牆規則）| 93.8% |
| 地形層 `bit 6/4/2/0`，全部格子 | 85.4% |
| 地形層 `bit 6/4/2/0`，**只看有牆的面** | **91.7%** |
| 地形層 `bit 7/5/3/1` | 81.7% |
| 地形層每方向 2 bit | 71.8% |

「只看有牆的面」是關鍵：沒有牆的地方那個位元沒有意義，把它算進去會稀釋
一致率。限定在有牆的面之後，91.7% 與牆規則自己的 93.8% 同一個量級。

21,092 個牆面裡 16,486 個（78.2%）位元是 1。**位元 0 的是少數，而且成群**：

```
地圖 0（中門）379 面牆，只有 7 面沒標記：
  (4,1,S) (5,1,S) (6,1,S)     ← 連成一排
  (10,3,N) (10,4,S)           ← 同一面牆的兩側
  (13,5,N) (14,6,S)
地圖 2  20 面沒標記，其中 12 面排成 y=1 每隔一格一個 —— 一排店門的形狀
地圖 1   6 面，五面在外圈，且成對出現
```

原版的碰撞訊息本來就是分開的兩句：`Solid!`（DGROUP `0x4E0F`）與
`Locked!`（`0x4E16`），對得上「實牆」與「門」兩種。指令表裡也有
`B Bash Door`（撞門）與 `U Unlock`（開鎖）。

### 原版的通行判定：確認了一半，另一半留下複雜化

`2PLAY.img` 的 `sub_5E68` 是前進前的通行檢查，回傳訊息序號或 `0xFFFF`（可走）：

```asm
mov  al, ds:59C8h
and  al, ds:59C6h         ; ← **兩個東西相 AND**
and  al, 55h              ; ← 0b01010101，正是牆位元 (6,4,2,0)
or   al, al
jnz  有牆
mov  ax, 0FFFFh           ; 沒牆 → 可通行
...
有牆：
mov  al, ds:59CAh
mov  cl, ds:59C7h
shr  ax, cl
and  ax, 3                ; ← 每個方向 2 位元
cmp  ax, 3
je   設為 1               ; 值 3 → 訊息 1（Solid!）
```

開鎖那支（`2MISC.img` `0xC130`）用同一套：取 `(格子位元組 >> 方向位移) & 3`，
`!= 2` 就印「這不是門」——**值 2 就是門**。

訊息表 `ds:4E4C` 六筆依序是 `Barrier!` / `Solid!` / `Locked!` /
`Not Locked!` / `Success!` / `Impassable!`。

**已證實**：

- 牆位元就是 (6,4,2,0)（`and al, 55h`）
- 每個方向另有一個位元組成 2 位元值，`3` = 實牆、`2` = 門
- 撞門與開鎖的入口條件是那個 2 位元值等於 2

**未證實：那兩個位元分別取自哪裡。** 最直觀的讀法是「同一個位元組的
bit(2d) 與 bit(2d+1)」，但那個讀法**被自己的後果否證**：照它算，
21,092 面牆裡有 19,572 面是門（92.8%），荒謬。

`and al, ds:59C6h` 那一行把**兩個東西相 AND** 才得到牆，形狀與
「兩個平面各出一個位元」一致 —— 也就是本節前面用對向一致性推出的讀法
（屬性層位元 ＝ 有牆、地形層同位置位元 ＝ 實牆/門）。那個讀法的一致率
91.7%，高於同位元組高位元的 86.0%，門的數量也合理（中門 379 面牆裡 7 面）。

`ds:59C6` 已經追到了：它是**方向遮罩**，隨朝向設成
`0xC0`（北，位移 6）／`0x30`（東，4）／`0x0C`（南，2）／`0x03`（西，0）——
每個方向佔相鄰兩個位元，而 `and 55h` 從中只留低位元。這證實了牆位元是
(6,4,2,0)，也證實了「每方向 2 位元」的欄位配置。

沒追到的是 `ds:59C8` 與 `ds:59CA` 各自的來源。五種讀法都量過，
用對向一致性排序：

| 讀法 | 一致率 |
|---|---|
| Attr 低位元（有沒有牆）| **93.8%** |
| Terrain 同位元（實牆/門），只看有牆的面 | **91.7%** |
| Attr 高位元（實牆/門），只看有牆的面 | 86.0% |
| Attr 整個 2 位元值 | 81.0% |
| Terrain 整個 2 位元值，只看有牆的面 | 68.8% |

前兩名遠高於其餘三種。而 Attr 層整個 2 位元值的分佈也合理
（0 可通行 60.7%、1 實牆 31.9%、2 門 5.0%、3 實牆 2.5%），
所以「runtime 那個位元組是載入時把兩層打包成 2 位元欄位」是最省事的解釋，
打包方式為 `(Attr 位元 << 1) | Terrain 位元` —— 正好給出 `3` = 實牆、
`2` = 門，與程式碼一致。

remake 的 `Map.WallKind` 就是照這個讀法，等級**強推論**。要定案得追
`sub_160ED` 載入地圖時有沒有做這個打包。

## 撞門

`2MISC.img` 的 `0xC130` 起。入口條件是那個 2 位元值等於 2（門），
成功率在 `0xC19C`：

```
力量 = 隊伍第一人的當前力量（記錄 +0x6B）
若 隊伍超過一人：再加上第二人的
擲   = rand(10, 109) / 10        → 1–10
若 擲 == 5：直接成功              ← 與門難度無關的保底
否則：力量 + 擲 >= ds:5998 才成功
```

`ds:5998` 落在地圖屬性那 64 bytes 的 `+18`（`ds:5986` 是起點），
所以 **`ATTRIB.DAT` 的 `+18` 是撞門的難度門檻**。值全是十的倍數、0–100：

```
五座城鎮   10, 30, 20, 40, 30      ← 中門（起始城鎮）最低
野外二十張 全部 0                   ← 沒有門
地城       20–100，隨深度上升
```

remake 的 `Session.BashDoor` 照這個公式做。

## 開鎖

`2MISC.img` 的 `0xC2B2`：

```
擲 = rand(1, 100)
擲 < 96 且 盜行 >= 擲  → 成功（跳 0xC326，印訊息 4 = Success!）
否則：再擲一次 rand(1,100) 與 ds:5999 比，走陷阱那條
      （0xC306 之後設 ds:0430 = 3）
```

盜行取自記錄 `+0x1E`（= +30）—— **這是那個欄位的第三個獨立佐證**
（前兩個是「只有賊與忍者非零」與《軟體世界》的欄位表）。

「擲 < 96」是上限保護：擲到 96 以上一律失敗，盜行再高也一樣。

`ds:5999` 是地圖屬性的 `+19`，形狀與 `+18` 一致（十的倍數、野外全 0）。
兩個欄位互相自洽：**撞門難度為 0 的地圖，鎖難度也是 0** —— 沒有門的地方
兩個都用不到，寫成測試 `TestLockDifficulty`。

開鎖失敗時會觸發陷阱：`Session.Unlock` 走 `Session.Trap()`，
與地圖陷阱、寶箱陷阱共用同一條傷害公式（見 [`08-combat.md`](08-combat.md)）。



順帶：同一段的 `sub_428C` 把朝向（存成 ASCII 字母 `N`/`S`/`E`/`W`）換成
座標增量，`N` 給的是 `dx=0, dy=+1` —— **再次證實 row 0 是南**。

## 執行時的地圖緩衝區：誰載入、載入什麼

`2PLAY sub_1BE24` 是唯一的地圖載入端，由 `byte_10399`（上次載入的地圖編號）
守門 —— **地圖編號沒變就整支跳過**，所以同一張圖內走動不會重載任何一層。

```asm
al = byte_10399
cmp byte ptr word_10392, al      ; word_10392 低位元組 = 當前地圖編號
jz  ret                          ; 一樣 → 不重載
byte_10399 = 當前地圖編號
sub_160D0(0x5AD6, 當前地圖)      ; ← 屬性層，記錄內偏移 0x100
sub_160B4(0x59D6, 當前地圖)      ; ← 地形層，記錄內偏移 0
sub_160B4(0x5BD6, ds:598B)       ;   北鄰圖地形層
sub_160B4(0x5CD6, ds:598D)       ;   南鄰圖地形層
sub_160B4(0x5DD8, ds:598C)       ;   東鄰圖地形層
sub_160B4(0x5ED8, ds:598E)       ;   西鄰圖地形層
```

六個緩衝區各 256 bytes。**鄰圖只載地形層，沒有屬性層** —— 第一人稱視野往前
看四格會跨到鄰圖，那時只需要知道有沒有牆。

`sub_160B4` 與 `sub_160D0` 是同一支 `sub_160ED` 的兩個入口，差別只在第三個
參數（記錄內起始偏移 `0` 或 `0x100`）：

```asm
開 MAP.DAT（檔名緩衝 ds:52D2）
lseek(地圖編號 × 2)  ; 地圖編號先 and 0x3Fh
read 2 bytes         → 該地圖記錄的檔案內偏移
lseek(那個偏移); read 4 bytes  ; LZW 段頭
DOS 配置 0x20 段 = 512 bytes
sub_12242            ; LZW 解壓整筆記錄進那 512 bytes
rep movsw cx=0x80    ; 從 [記錄 + 0 或 0x100] 搬 256 bytes 到目的緩衝區
釋放那 512 bytes
```

所以 **`ds:5AD6` 就是地圖檔記錄的第二個 256 bytes**（§1 的 `+0x100` 屬性層），
不是執行時算出來的。同一筆記錄被解壓兩次，一次取前半一次取後半。

### 開門是唯一會改寫屬性層的一般路徑

root `sub_13A64`（overlay 走 thunk `0x1765A`）：

```asm
si = 隊伍Y * 16 + 隊伍X
al = [si + 59D6h]        ; 地形層當前格
and al, ds:59C6h         ; 遮出目前朝向的那兩個位元
shr al, 1                ; 兩位元值往低位移一格：門(2) → 牆位元(1)
xor al, ds:59C8h         ; 與當前格的屬性位元組 XOR
mov [si + 5AD6h], al     ; 寫回屬性層 → 該方向的牆位元被翻掉
mov ds:59C8h, al         ; 同步更新當前格快取
```

**唯二呼叫點都在 `2MISC`**：撞門成功（`0x1C20F`）與開鎖成功（`0x1C326`）。
全部十五個資料庫掃過 `call` 目標，沒有第三處；root 自己也不呼叫它。
所以這不是「每走一步」做的事，是開門專用。

`ds:59C8` 因此是**當前格屬性位元組的快取**（`sub_1B4E0` 每步從
`[bx+5AD6h]` 重讀），開門那一刻順手改掉，不是沿路累積的值。

### 開門狀態的生存期

屬性層只在**地圖編號改變**時從 `MAP.DAT` 重讀，而載入器只讀不寫
（`sub_160ED` 用 `int 21h` 的 `3Dh`／`42h`／`3Fh`／`48h`／`49h`，沒有 `40h`）。
記憶體裡的那 256 bytes 也沒有任何一處被搬回檔案或存檔緩衝區 ——
`ds:5AD6` 這個位址在全部十五個資料庫只出現在 §上文列出的那幾處。

- 同一張圖內：開過的門保持開著。
- 換到別張圖再回來：屬性層整個重讀 → **門關回去，事件 bit 7 也回來**。
- 存檔重載：讀檔後地圖編號會經過 `sub_1BE24`，同樣是重讀。

opcode `0x14` 清 `0x5AD6` 的 bit 7 標記「事件用過了」，生存期與門相同。
remake 若把「事件只觸發一次」做成永久旗標，**離圖再回來的行為就與原版不同**。

### 自動地圖的走訪位元另存一份

`sub_1BE92` 是唯一持久的那一份：

```asm
ax = [X*2 + 1760h]               ; 位元遮罩查表，X → 1 << X
arr[地圖編號 * 32 + Y * 2] |= ax  ; 基底 ds:968C（IDA 位址算式寫成 [bx+si-6974h]）
```

60 張 × 32 bytes = 1,920 bytes，每張圖 16 列 × 16 位元。**它不隨換圖重載**，
所以走過的格子會一直記著 —— 這與門／事件旗標是兩套不同生存期的狀態。

## 定案：室內與室外是兩套模型

`sub_5E68` 依 `ds:039D` 分兩條路 —— 這是先前一直對不上的原因，
因為統計把兩種地圖混在一起量了。

分開之後訊號非常乾淨（判準用 `ATTRIB.DAT` 的 `+18` 非零 ＝ 室內，
三十六張室內、二十四張野外）：

| 量測 | 室內 36 張 | 野外 24 張 |
|---|---|---|
| Attr 低位元（有沒有牆）| **98.2%** | 87.1% |
| Terrain 低位元 | **99.8%** | 63.7% |
| Terrain 同位元（實牆/門），只看有牆的面 | **99.7%** | — |

室內圖上，有牆的面裡 98.2% 的地形層位元是 1（實牆）、1.8% 是 0（門）——
283 面，約每張八面。先前量到的 91.7% 與 21.8% 的門，都是野外那二十四張
拉出來的：野外沒有門，它的地形層放的是地形碼不是牆位元。

**所以規則是**（僅室內）：

```
Attr    bit 6/4/2/0  = 這個方向有沒有牆
Terrain 同一個位元   = 1 實牆、0 門
```

### 室外那一套

`sub_5E68` 的 `0x5EB4` 之後：

```
類別 = sub_5F40(地形碼)     ; 碼 & 0x1F 之後查 ds:52B2 的 32 項表
類別 1 → n = sub_36A6(0x0B) ; n < 2 → 訊息 5 = Impassable!
類別 3 → n = sub_36A6(0x0D) ; n < 2 → 訊息 5 = Impassable!
類別 4 且 ds:16DA == 0x0A → 訊息 6 = Can't swim!
```

`sub_36A6(n)` 數的是**隊伍裡具備第二技能 n 的人數**。技能編號與手冊
一字不差：`0x0B` = 11 = 登山家、`0x0D` = 13 = 探險家，而「兩人以上」
正是手冊寫的條件（「隊伍中有二人或二人以上具有此技能時可穿越」）——
原版的判斷就是 `si < 2`。

分類表（`ds:52B2`，32 項）：

```
0:0  1:1  2:1  3:2  4:3  5:4 … 12:4  13–27:0  28:4  29–31:0
```

| 類別 | 意義 | 通過條件 |
|---|---|---|
| 0 | 可通行 | — |
| 1 | 山區 | 隊伍裡兩名**登山家** |
| 2 | 語意未定 | 野外圖上一格都沒有 |
| 3 | 森林 | 隊伍裡兩名**探險家** |
| 4 | 水域 | 還要看 `ds:16DA` 與 `ds:03D9`（船／水上行走之類），未解 |

**地形碼取自 `Attr` 層的低 5 位元**，不是 `Terrain` 層。判準是分佈：

| 來源 | 可通行 | 山區 | 類別 2 | 森林 | 水域 |
|---|---|---|---|---|---|
| **Attr & 0x1F** | **74.0%** | 5.2% | 0% | 5.3% | **15.5%** |
| Terrain & 0x1F | 22.4% | 12.0% | 4.3% | 8.5% | **52.8%** |

一張陸地世界圖不會有一半是水。remake 的 `Session.EnterOutdoor` 照這一套做，
水域一律擋住（那兩個旗標還沒解）。

**牆位元只在室內成立。** 野外圖的屬性層低 5 位元是地形碼，而牆位元取的是
bit 6/4/2/0 —— 其中 0、2、4 落在地形碼裡。拿牆的讀法去讀野外，
「森林」（碼 4）會被讀成「西邊有牆」。`Map.CanMove` 因此只在室內查牆位元。

### 追 `ds:59CA` 排除的三個可能

| 假設 | 結果 |
|---|---|
| `ds:59C8` 就是當前格的位元組 | **否**。`0x3A64` 顯示它是沿路 XOR 累積的值 |
| `ds:59CA` 由某段程式碼顯式寫入 | **否**。十四個映像掃過，只有 root 的兩處**讀取**（`0x5EC6` 與 `0x5F87`，都帶索引），沒有任何寫入 |
| `ds:59CA` 是 DGROUP 的靜態初值 | **否**。EXE 尾部那一塊（`ds:59C6`–`ds:59D5`）十六個位元組全是 0 |

同時釘死的是 `0x5986` 那一塊：`sub_6171` 用 `rep movsw` 複製 **`cx = 0x20`
（64 bytes）** 到 `di = 0x5986`，來源是 `地圖編號 × 64` —— 證實 `ATTRIB.DAT`
的記錄長度就是 64，落點就是 `0x5986`，`+18`／`+19` 的位址因此也確定。

所以 `0x59C6`–`0x59D5` 是十六個位元組的暫存區：`0x59C6`／`0x59C7` 每次轉向
寫入（方向遮罩與位移）、`0x59C8` 是走路的累積值、`0x59CA` 起是一個帶索引
讀取的小陣列，填它的程式碼還沒找到。找到那一段，門的兩個位元來源就清楚了。

## 地圖分群表（`ds:16E0`／`ds:16E8`／`ds:16F0`）

`sub_1B410(地圖號)` 拿地圖號去比對 **7 個區間**，回傳一個群代碼
（沒命中回 7）：

	si = 0..6：
	    if ds:16E8[si] <= 地圖號 <= ds:16F0[si]：
	        回傳 ds:16E0[si]

三張表的內容：

| 群代碼 | 地圖區間 |
|---|---|
| 0 | 0–4 |
| 3 | 5–16 |
| 1 | 17–32 |
| 6 | 33–40 |
| 4 | 41–44 |
| 5 | 45–54 |
| 2 | 55–59 |

**這是分類不是重新編號** —— 傳進去的地圖號原樣使用，回傳的是它屬於
哪一群。區間切點與事件檔的室內／室外分佈完全吻合
（`0–4` 室內、`5–16` 室外、`17–32` 室內、`33–44` 室外…），
所以群代碼多半對應素材檔或磁片分組。

順帶確認一件事：**腳本裡的地圖編號與 `ATTRIB`／`MAP.DAT` 是同一個
編號空間**，中間沒有轉換層。


## 兩個位元不同源

`sub_15E68` 的室內分支把三個位址讀在一起：

```
ds:59C6   方向遮罩   北 0xC0、東 0x30、南 0x0C、西 0x03   （`sub_1423E` 依朝向設定）
ds:59C7   位移量     北 6、東 4、南 2、西 0
ds:59C8   屬性層的那一格
ds:59CA   地形層的那一格
```

```
al = ds:59C8 & ds:59C6 & 0x55      ; 只留偶數位元 —— 擋不擋路
若為 0            → 走得過去
種類 = ds:59CA >> ds:59C7 & 3      ; 兩個位元一起取
種類 == 3         → 當成 1
拿種類去查 ds:4E4C 的訊息表
```

**擋不擋路來自屬性層的一個位元，是哪一種來自地形層的兩個位元。**
`ds:4E4C` 那張表是：

| 值 | 訊息 |
|---|---|
| 0 | `Barrier!` |
| 1 | `Solid!` |
| 2 | `Locked!` |
| 3 | `Not Locked!` |
| 4 | `Success!` |
| 5 | `Impassable!` |
| 6 | `Can't swim!` |

室內三十六張的實測分佈：**實牆 98.2%、門 1.4%、屏障 0.5%**（共 15,303 面）。

## 屬性層的高位元

`and al, 55h` 把 bit 7/5/3/1 整個遮掉，所以**它們不參與牆的判定**。
它們是**整格的旗標**，不是方向的性質 —— 這也解釋了為什麼對向一致率只有
86.5%（牆位元是 99.7%）。

**讀它們的地方不是平面，是當前格的快取。** `2PLAY` 的 `sub_1B4E0` 每步做
`al = [bx+5AD6h]; mov byte_159C8, al`，之後所有旗標檢查都對 `ds:59C8` 做。
只掃平面（`ds:5AD6`）當然找不到讀取點 —— 那正是這三個位元掛了很久的原因。

| 位元 | 語意 | 讀取處 | 資料 |
|---|---|---|---|
| 7 | 這一格有事件 | `or ...80h` / `and ...7Fh` / `cmp ...80h` | 五座城 100% |
| 5 | **這一格吃照明** | root `0x150CE`（走一步扣一點）與 `sub_13FFC` `0x1402A`（沒照明就不畫視圖）的 `test ds:59C8h, 20h` | 125 格、6 張圖 |
| 3 | **這一格不能休息** | `2MISC` `test byte_159C8, 8` → `Too dangerous!`（`ds:2A5C`）而不是 `Rest here? (Y/N)`（`ds:2A6B`）| 950 格、12 張圖 |
| 1 | **這一格不能施法** | `2CAST1`×3、`2CAST2`×3、`2COMBAT`×1 的 `test byte_159C8, 2` → `*** Spell Failed ***` | 206 格、7 張圖 |

**bit 5 的兩個讀取點都在 root**，而且都寫成 `ds:59C8h`：

- `0x150CE`（走一步之後推時間那一支）：`步數 == 1` 且這一格有 bit 5 且
  `ds:03D5`（照明計數）不為 0 → `dec ds:03D5`，再重畫狀態列。
- `sub_13FFC` `0x1402A`（畫第一人稱之前）：照明計數為 0 時，這一格有 bit 5
  就整塊不畫，改印 `Darkness`。

125 格分佈在 6 張圖（2、4、17、22、58、59），**每一格都有牆**，而且排成
封閉的輪廓 —— 地圖 59 的 26 格是完整的 4×5 矩形外框、地圖 22 的 8 格是
三面牆的房間。形狀與「吃照明」相容：那是要花光源走過去的一段路。

> **掃描要連 root 一起掃，而且要掃位移不是字面。** overlay 裡 IDA 把這個
> 位址命名成 `byte_159C8`，root 裡沒有名字、寫成 `ds:59C8h` ——
> 只比對前者就會漏掉 root 的兩條，而漏掉的長相與「沒有人讀」一模一樣。

> 兩個平面的分工也順便釘死了：`ds:59D6` 是**地形層**（`shr` 之後 `and 3`
> 取兩個位元判種類），`ds:5AD6` 是**屬性層**（`and 方向遮罩` 之後
> `test 55h` 只看偶數位元）。`ds:5BD6`／`ds:5CD6`／`ds:5DD8`／`ds:5ED8`
> 是相鄰地圖的平面，由 `sub_1BE24` 一起載入。
