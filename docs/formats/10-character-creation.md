# 角色創建

輸入檔：`MM2.EXE`（`1MENU2.OVL` 與 `1MENU1.OVL` 共用的那一段，
兩份映像在 `0x8A00`–`0x8A60` 逐位元組相同）。

## 屬性擲骰（`sub_189F8`）

	參數 = 指向一塊 7 個位元組的屬性區
	把那 7 個位元組清成 0（rep stosw ×3 + stosb）
	重複 3 輪：
	    對 7 格各做一次：
	        值 = rand(10, 79) / 10      ; 整數除法
	        該格 += 值

`rand(10, 79) / 10` 的商是 **1–7 均勻分佈** —— 十個十位數區間各含
十個值，除以 10 之後每個商各佔十分之一。原版沒有 `1d7`，
這是用既有的 `rand(下限, 上限)` 湊出來的。

所以**每個屬性是 3d7，值域 3–21**。七格全部一起擲，沒有重骰、
沒有分配點數。

擲完接著呼叫 `sub_18952`（算職業資格）與 `sub_188B2`（畫上去）。

## 職業資格（`sub_18952`）

	參數 = (七格屬性, 八格輸出)
	cl 從 0 跑到 7，每一輪用 cl 查跳表 jpt_18975（`0x189CE`，八筆 word）
	各 case 檢查指定的幾格是否都達門檻，結果寫進 輸出[cl]（1 或 0）

八個 case 與門檻（`0x0D` = 13、`0x0F` = 15），屬性索引就是畫面上的 A–G：

| case | 職業 | 條件 |
|---|---|---|
| 0 | 騎士 | `[0] 力量 >= 15` |
| 1 | 聖騎士 | `[0] 力量`、`[2] 人格`、`[3] 耐力` 都 `>= 13` |
| 2 | 弓箭手 | `[1] 智力`、`[5] 準確度` 都 `>= 13` |
| 3 | 牧師 | `[2] 人格 >= 13` |
| 4 | 巫師 | `[1] 智力 >= 13` |
| 5 | 盜賊 | `[6] 運氣 >= 13` |
| 6 | 忍者 | `[4] 速度`、`[5] 準確度` 都 `>= 13` |
| 7 | 蠻族 | `[3] 耐力 >= 15` |

**這張表同時定死了兩個順序**：屬性是力量／智力／人格／耐力／速度／準確度／運氣，
職業是騎士／聖騎士／弓箭手／牧師／巫師／盜賊／忍者／蠻族。八條門檻與手冊的
職業說明逐條相同，兩邊互為獨立佐證。

`internal/game/create.go` 的 `classReq` 與這八條逐條一致。

## 畫面（`sub_188B2`）

	參數 = (七格屬性, 八格資格表或 0)
	七格屬性：游標移到 (20, 12+i)，用寬度 2 印出數值
	資格表非 0 時再跑八格：游標移到 (25, 12+i)
	    可選 → 印職業編號 i+1（寬度 1）
	    不可選 → 印一個空白

所以**畫面上不能選的職業從一開始就不亮**，不是選了才擋回來。
兩支函式合起來就是「擲完 → 算資格 → 畫出來」這條鏈。

## 那七格不是記錄的屬性區

擲骰程序處理七格，而角色記錄的屬性區是**六格**（`+16`–`+21`）。
兩者不衝突：那七格是**創建時的暫存**，沒進區塊的那一項（耐力）另外存到
`+39`／`+115`。對應關係由 `sub_18624` 的寫入處定死，見
[`02-data-files.md`](02-data-files.md) §5。

判準是名冊四十筆的分佈（`TestAttrBlockWidth`）：

| 位移 | 範圍 | 平均 | 落在 3–21 |
|---|---|---|---|
| `+16` | 7–35 | 17.4 | 34/40 |
| `+17` | 3–90 | 15.0 | 36/40 |
| `+18` | 2–27 | 12.9 | 36/40 |
| `+19` | 7–60 | 16.8 | 36/40 |
| `+20` | 6–29 | 16.9 | 36/40 |
| `+21` | 7–75 | 17.4 | 33/40 |
| `+22` | 0–53 | **6.0** | **1/40** |

`+16`–`+21` 六格形狀一致，`+22` 明顯是另一回事（多數為 0）。
擲骰產生 3–21，練過的角色會超出上限，但**下界不會低於 3** ——
`+22` 有一大半是 0，它從來沒被擲骰填過。

手冊列七項屬性、記錄只放六格連續，耐力單獨放 `+39`／`+115` ——
`sub_189EE` 的七格暫存正好解釋了這個安排怎麼來的。
