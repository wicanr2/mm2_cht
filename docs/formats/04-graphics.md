# .16 圖形格式

26 個 `.16` 檔全部是 LZW 段（見 [`03-lzw-compression.md`](03-lzw-compression.md)），
段頭宣告長度與實際解出長度全部相符。

實作：[`tools/mm216.py`](../../tools/mm216.py)，輸出 PNG 與 contact sheet。

## 1. 一般 .16：影像集

LZW 解開之後：

```
uint16  count            影像數
uint32  offsets[count]   相對解壓緩衝開頭的絕對偏移
                         offsets[0] 恆等於 2 + count*4（即檔頭長度）

每張影像：
uint16  width            像素
uint16  height
        4bpp packed 像素，每 byte 兩個像素，高 nibble 在左
        （每張影像結尾與下一個 offset 之間固定空 4 bytes，用途未定）
```

影像邊界一律以 `offsets` 為準，不要用寬高回推 —— 那 4 bytes 會讓計算差一截。

`offsets[0] = 2 + count*4` 這條在 count = 1、2、5、36 的檔案上都成立，
是判斷檔頭解讀正確的自我驗證條件。

### 驗證

| 檔案 | 影像 | 尺寸 | 結果 |
|---|---|---|---|
| `NWCP.16` | 1 | 320×82 | 開場畫面 "New World Computing Presents..."，地球與行星正確 |
| `DISK.16` | 1 | 88×67 | 磁碟圖示，上面的 "Might & Magic II" 標題清晰 |
| `TOWNF.16` | 1 | 208×60 | — |
| `TOWNT.16` | 36 | 24×43 起 | 火炬，藍色石牆配色。分組見下 |
| `CAVET.16` | 36 | 同上 | 同一組火炬，綠色洞穴配色 |

`NWCP.16` 的字母有規律的紅白橫條，那是 EGA 16 色的 dithering，不是解析錯誤 ——
同一支解析器解出的 `DISK.16` 是乾淨的實心色塊。

### 調色盤

**EGA 標準 16 色，原版沒有換掉。** 等級：**已證實**。

證據是原版實測而非推論：DOSBox 跑原版到標題畫面截圖，擷取 EGA 的 320×200
區域統計顏色 —— 用到 15 種顏色，**65,600 個像素 100% 落在 EGA 標準 16 色內**
（缺的那一種是 `#AAAAAA`）。

```bash

```

## 2. MONSTERS.16：索引式，段內另一套子格式

168,257 bytes，結構與其他 `.16` 不同 —— 它自己帶一張索引表：

```
uint32  offsets[75]      第一筆 = 300 = 索引表長度；其中 16 筆為 0（空槽）
        59 個 LZW 段
```

檔頭 `2C 01 00 00` 的形狀與 LZW 段頭（uint16 長度 + uint16 0）**完全一樣**，
無法靠形狀分辨。判準是解開之後 `offsets[0] == 2 + count*4` 是否成立 ——
`MONSTERS.16` 直接當單段解會得到 345 bytes 的垃圾。

段內：

```
uint16  count            影格數
uint16  offsets[count]   ← uint16，不是 uint32
        動畫表（見 §2.3）
每個影格：uint8 x, uint8 y, uint8 width, uint8 height
        RLE 像素（見 §2.2）
```

影格 0 一律是 84×86 的基準圖，其餘是疊在它上面的動畫零件，各自帶 `x`/`y` 偏移。
59 個槽共 433 個影格。

### 2.1 圖號怎麼變成槽號：空槽是往後借，不是壞資料

`MONSTERS.DAT` 記錄 `+21` 的低 7 位元是圖號（1–60）。整條鏈在
`2COMBAT.img` 與 root：

```
2COMBAT 0xA3A1  call sub_7036(ds:9E2B)     ; 圖號
root    0x264A  dec [bp+4]                 ; 索引 = 圖號 − 1
                call sub_6818(索引)
root    0x6818  open ds:04C2               ; → "monsters.16"
                read 0x12C bytes → ds:9E48 ; 300 bytes 的索引表
                si = 索引 × 4
                dx = word[9E48+si]；cx = word[9E48+si+2]
                dx | cx == 0 → si += 4、索引 += 1
                                索引 < 0x4B 就再試，否則索引歸零重來
```

**圖號指到空槽不是錯誤，是往後借下一張圖，掃到第 75 項回繞。**
所以「老守財奴」（圖號 7，索引 6 是空的）與「哥布林」（圖號 8）共用同一張。
只看檔案猜不出這條 —— 空槽長得跟壞掉的資料一模一樣，而 16 個空槽裡有
12 個是真的有怪物指過去的。等級：**已證實**（程式碼直接寫著）。

`ds:04C2` 存的是檔名字串的 DGROUP 偏移 `0x01DD`，該處的字串正是
`monsters.16`。

### 2.2 像素編碼

```
每個位元組一段：高 nibble + 1 = 長度（1–16），低 nibble = 顏色（0–15）
列優先鋪滿 w × h，鋪滿就停
```

背景色是 **5**（EGA 標準調色盤的洋紅）：59 張基準圖的左上角全部是 5。
`0xF5`（16 個像素的背景）是全檔第二常見的位元組，共 20,761 次。

驗收條件是 433 個影格逐張解出剛好 `w × h` 個像素：279 張剛好用完位元組，
其餘最後一段稍微超出，超出的部分丟掉。渲染出來的 59 張基準圖是可辨識的
蜘蛛、甲蟲群、龍、骷髏、騎士、城堡與寶箱。等級：**已證實**。

> **驗收條件本身也要驗。** 這條規則一度被自己的驗收方式判成 0/433：
> 影格與下一個偏移之間還有幾個位元組的填充，把整段吃完再比對像素數，
> 每一張都會多出一點，於是「逐張吻合」永遠是 0。
> 總量比值 1.020 早就在喊「差 2%」，但被讀成「接近 1 是巧合」。

`tools/mm216.py workplace/orig/MM2/MONSTERS.16 <outdir> -v` 會輸出 433 張 PNG
與一張 59 格的 contact sheet。權威實作在 `internal/assets/gfx/monsters.go`。

### 2.3 動畫表

檔頭與第一個影格之間：

```
（影格, 停留）… FF （影格, 停留）… FF … FF
```

**`FF` 是每一段的結束標記，不是分隔符** —— 第一個 `FF` 之前那段就是第一個
動畫段，沒有「表頭」這種東西。表以一個空段（也就是連續兩個 `FF`）收尾。
照這個讀法切，59 個槽共 **240 段**，**每一段的長度都是偶數，零例外**
（先前算 181 段是把每個槽的第一段當表頭扣掉了）。

第一段是播放腳本（見下），其餘 181 段才是動畫序列。
停留值集中在 5/10/20/15/25/30，是影格數。
槽 0（12 個影格）的動畫序列用影格 {0,2,4}、{0,5,7}、{0,6,8}、{0,9,10,11}。

#### 第一段不是動畫，是播放腳本

第一段的每一對是**（段編號, 停留）**，不是（影格, 停留）。走它的是 root
`0x15715` 起的迴圈：

```asm
bx = ds:9F7C                 ; 腳本游標
al = [bx+9E48h]              ; 段編號位元組
...
or  al, al
jns 15743                    ; bit 7 沒設 → 直接當段編號
and ax, 7Fh
push ax; push 1
call sub_11C88               ; ← 亂數產生器：ax = rand(1, 低7位)
15743:
call sub_15772               ; 從表頭往前跳過 ax 個 FF，之後逐對讀（影格, 停留）
```

`sub_15772` 讀到 `FF` 就把段指標設回 `0FFFFh` 並回傳 0，外層迴圈於是
`inc ds:9F7C` 兩次、讀下一對，繼續播下一段。

所以 **bit 7 ＝「隨機挑一段」**，低 7 位是段編號（帶 bit 7 時當上限）。

資料側零例外：59 個槽共 **136 個腳本項**，其中 **31 項帶 bit 7**，
**段編號一律落在 1..段數-1**。帶 bit 7 那 31 項的停留值也一律是 0。

先前把第一段當動畫序列讀，會得到 47、131、134 這種「越界影格」——
那些是段編號。槽 24／35／39 的「編號正好等於影格數」也是同一回事。

#### 影格編號越界不是壞資料

`sub_15772` 在 `0x1578E` 拿影格編號與 `ds:9F76`（影格數）比，
**大於等於就 `xor al, al` 用影格 0**。所以動畫序列裡出現超過影格數的編號
是原版允許的寫法，不必當成解析錯誤。

#### 槽 9 的動畫表是壞的，原版在執行時修補它

`MONSTERS.16` 索引 9 的動畫表第一段是 `2F 0A 10 3B 06 04 83 00`，
套 (影格, 停留) 讀會得到 47 號影格 —— 而那個槽只有 6 個影格。
第三段還有一個編號 6，同樣越界。

root `0x12711` 起有一段只對索引 9 成立的特判：

```asm
cmp word ptr [bp+4], 9
jnz  短路
mov  cx, 12h
mov  di, 9E48h
mov  si, 4B92h
repne movsw          ; 從 ds:4B92 搬 36 bytes 到 ds:9E48
```

`ds:4B92` 那 36 bytes 是：

```
01 01 02 01 03 01 ff | 01 05 02 05 01 05 00 05 ff |
03 05 04 05 05 05 00 05 05 05 00 05 ff | 01 05 02 05 00 05 ff
```

與檔案裡的那張表**逐位元組比對**：中間第二段的 22 bytes 完全相同，
差別只有兩處 —— 壞掉的第一段換成 `(1,1),(2,1),(3,1)`，
第三段那個越界的 `06` 換成 `02`。

**這是 New World Computing 對自家壞資料的執行時修補**，寫死在程式裡。
先前記成「一步越界，沒有解釋」的那筆，解釋就是這個。

#### 影格在驅動、播放在 EXE

`sub_16818` 把整段解壓進一塊自己配置的記憶體，回傳遠指標存進
`ds:0386`／`ds:0388`。那個遠指標在全部十五個資料庫裡**只有四處參照**：
寫入、推進驅動呼叫、以及 `sub_12734` 清掉它。**沒有任何 EXE 或 overlay
的程式碼走訪那塊緩衝區** —— 整段交給顯示驅動（`sub_11CDA`，功能碼 `0x16`），
驅動把動畫表搬到 `ds:9E48` 之後，播放才由 EXE 這邊接手。

`EGA.DRV` 檔案偏移 `0x1233` 那一支開頭就讀 `word[0]`（影格數）
並配置 `影格數 × 0x1200` bytes。`0x1200` = 4,608 = 12 bytes × 96 列 × 4 平面，
所以驅動端把每個影格展開成 **96×96 的四平面 EGA 點陣**（等級：**強推論**，
乘數與配置大小是已證實，96×96 的拆法是算出來的）。

動畫的**播放**則在 `MM2.EXE` 這邊：驅動把表搬到 `ds:9E48`，root
`0x15715`／`sub_15772` 走它（見上文）。所以「表由誰解析」要分兩層看 ——
影格像素在驅動，播放邏輯在 EXE。

反組譯 `.DRV` 要注意兩件事：`-Tbinary` 載進來預設全是資料，要自己種進入點
（跳表每筆 `E9 rel16`，目標 = 該筆位址 + 3 + rel16）；而且 IDA 9.4 會把段
設成 32-bit，**不改成 16-bit 會反出看起來完全合理卻每條都錯的指令**
（`b8 0d 00 cd 10` 會變成一條 `mov eax, 10CD000Dh`）。
兩件事都包在 `tools/ida_code.py`。

### 2.4 解碼在哪裡執行

影像的解碼與繪製走 `ds:0x4A24` 那個 far pointer 進顯示驅動，不在
`MM2.EXE` 或十四個 overlay 裡。每種顯示卡一份驅動（`CGA`／`EGA`／`HGA`／
`MCGA`／`TGA`），各自實作解碼與寫入視訊記憶體。

`EGA.DRV` 是 COM 檔，開頭是 **36 個 `jmp near`** 的跳表，功能碼 × 3 就是
跳表偏移（`0x1DA3` 那段 `shl bx,1` / `add` 正是 ×3）。反組譯用
`tools/ida_code.py`（種進入點 ＋ 把段設成 16-bit）。

跳表第 22 項（功能碼 `0x16`，檔案偏移 `0x1233`）**一支做兩件事**：
開頭讀傳進來那個段的 `word[0]`（影格數）並配置 `影格數 × 0x1200` bytes，
接著是**字型展開** —— `si` 由 `0x20` 跑到 `0x7F`（可列印 ASCII），
每個字元查 `cs:[si*2+0x72]` 取指標、把 6 個 word 的 1bpp 圖樣展開成
EGA 四個平面。所以「第 22 項是字型展開」與「第 22 項載入精靈集」
兩句都對，是同一支的前後兩段。

remake 不需要那條路徑 —— 像素編碼已經從資料本身解出來並用畫面驗過了。

## 3. 檔頭有兩型

兩型的長度都是 `2 + count*4`，`offsets[0]` 也都等於那個長度，所以不能靠長度分辨。

```
A 型   uint16 count + uint32 offsets[count]
       TOWNT、CAVET、DISK、NWCP、SKY、TOWNF…

B 型   uint16 count + uint16 offsetsA[count] + uint16 offsetsB[count]
       MASTER、DESERT、OCEAN、SWAMP、TUNDRA、OUTDOOR1-3
```

判準是「當 uint32 讀出來的偏移是否遞增且落在緩衝內」。A 型的檔案在 uint32
的高位 word 剛好都是 0（`146, 0, 670, 0, 1050, 0, …`），B 型這樣讀會得到
幾百萬的巨值。B 型的兩組偏移在緩衝裡是**交錯**的，要合併排序後才能用相鄰值
界定影像邊界。

套用後每個檔案解出的張數都等於 `count`：MASTER 15、DESERT 20、TUNDRA 20、
OUTDOOR1 8、TOWNT 36、NWCP 1。

### 標題畫面：截圖 oracle 反推

`MASTER.16` 的 320×196 標題畫面是這樣定位的，過程可以當這類問題的範本：

1. 原版跑到標題畫面截圖，把每個像素依 EGA 調色盤轉回 4-bit index；
2. 取截圖第 40 行的 320 個像素、packed 成 160 bytes，在解出的 42,392 bytes
   裡直接搜尋 —— 命中 offset 17,428，唯一；
3. 取第 100 行同樣做，命中 27,028。差 9,600 = 60 行 × 160 bytes，與行距相符；
4. 回推第 0 行應在 `17428 - 40×160 = 11028`，而該處往前 4 bytes 讀出的
   `uint16 w, uint16 h` 正是 **320 × 196**；
5. 像素 31,360 bytes 從 11,028 到 42,388，加上影像尾的 4 bytes 剛好是檔尾 42,392。

**驗證**：用解出的資料 render 成 PNG，與原版截圖逐像素比對，
**62,672 / 62,720 相同（99.92%）**。48 個相異像素集中在 (169–172, 164–165)
一小塊，是原版在標題上疊的動畫元素。

這條路徑（已知解碼器 + 已知輸出 → 反推資料位置）比從檔頭位元組猜快得多，
在有原版可跑的情況下應該優先用。

## 3.5 場景素材：牆、地板、火炬

檔名表在 `ds:04CE` 起的指標陣列，三種室內場景各佔四格：

	townf.16  townt.16  townb.16  town.16
	cavef.16  cavet.16  caveb.16  cave.16
	castlef.16 castlet.16 castleb.16 castle.16

字尾 `F` 是地板、`T` 是火炬、`B` 未解、無字尾的是牆。

`TOWN.16` 的 **32 張是 16 張 × 兩種變體**：前 16 張是石牆，後 16 張是
**同一組牆但畫上門**。這對得上 `Map.WallKind` 的 1（實牆）與 2（門）。
每一組 16 張的前 12 張是「正牆 ×4 深度、左側牆 ×4、右側牆 ×4」：

| | 深度 0 | 深度 1 | 深度 2 | 深度 3 |
|---|---|---|---|---|
| 正牆 | 160×92 | 96×56 | 48×28 | 16×10 |
| 左側牆 | 24×120 | 32×94 | 24×56 | 16×28 |
| 右側牆 | 24×120 | 32×94 | 24×56 | 16×28 |

12/13（24×92）與 14/15（56×56）是**正牆兩側的補牆**：正牆比視圖窄，
兩側露出來的部分由這一對填滿。判準是寬度加起來剛好是視圖寬 ——
`24+160+24 = 208`（正牆深度 0）、`56+96+56 = 208`（深度 1）。
深度 2／3 的正牆更窄，沒有對應的補牆。

補牆一律用石牆那一組，即使正牆是門：同一張截圖裡門版的影格 30／31
在同一個位置只有 62–68%，石牆版是 95.7%。

### 牆的透空色是 8，不是 0

側牆矩形四角那兩塊楔形是「這裡看得到後面」，不是灰色的牆。
把影格 4 對回原版截圖（`shots/diff-shot.png`，(8,0) 面東），
327 個不符的像素**全部**是「樣板 8 → 截圖是天空或地板」，沒有例外。
換成以 8 當透空色之後，同一張影格取 100%。

**透空色不是全域的，是看貼圖**：同一個色號 8 在地板貼圖裡是真的顏色
（灰白相間的格子，原版一張畫面裡出現三千多次）。`render.BlitKey` 因此
把透空色當參數，牆傳 8、其他傳 0。

`cmd/mm2match` 的 `-key` 也是同一件事 —— 比對器與繪圖器要用同一套規則，
不然「位置對了但分數只有 86%」會被誤讀成位置錯了。

### `TOWNT.16` 的 36 張：三組 × 三個深度 × 四張

一組四張是「一張含燈桿的底圖 + 三張只有火焰的動畫」，動畫張與底圖共用
左上角、只蓋掉上半部，燈桿不重畫。**第三張與底圖相同**（樣板比對兩張都
取 100%），所以火焰是「靜、動、動、回靜」。

三組分別是左側牆、右側牆、正牆 —— 前兩組的燈桿斜著畫，第三組直立。

位置用 `cmd/mm2match` 把每一張影格滑過 126 張原版截圖定出來。判準是
**每一張影格在整批截圖裡只有唯一一個 100% 的落點**，不是「找得到一個
還不錯的位置」：

| 組 | 影格 | 深度 0 | 深度 1 | 深度 2 |
|---|---|---|---|---|
| 左側牆 | 0–11 | (8,42) | (40,56) | **(64,59)** |
| 右側牆 | 12–23 | (192,42) | (160,56) | 沒出現 |
| 正牆 | 24–35 | (104,44) | (8,54)／(200,54) | (104,60) |

兩個要記著的例外：

- **右側牆深度 2（影格 20–23）在 126 張截圖裡一次都沒出現。** 用左右鏡射
  補（`FPW − x − w`），這條規則在深度 0 與 1 上都成立，所以是強推論。
- **正牆深度 1（影格 28–31）量到的落點在視圖最左與最右，不在中央。**
  出處是神殿（`shots/c3.png`）與酒館（`shots/u06.png`）那兩張整幅插畫，
  不是走廊算出來的位置。x 照另外兩階中央對齊補，y 用量到的 46。

### 火炬不是每面牆都有

`shots/p5.png` 的左邊三個深度都是牆，只有深度 2 那一面點著火炬；
`shots/22-fpv2.png` 是深度 0 左右各一盞、深度 1 沒有。所以觸發條件存在，

## 戰鬥畫面的版面：從程式碼能拿到多少

不必等截圖也能定出一部分。`2COMBAT.img` `0x1A384` 這一段：

	if ds:9F84 != ds:9E2B:            ; 目前載入的圖號 ≠ 這隻怪的圖號
	    sub_1704E(-1, 0, 0)           ; 卸載
	    sub_17036(ds:9E2B)            ; 載入新的
	多留 = (ds:0508 > 10) ? 1 : 0      ; 場上怪物數
	下緣 = 多留 × 3 + 名單行數 + 2
	sub_16DD2(16h, 1, 26h, 下緣)

`sub_16DD2` 的四個參數在另一處是 `(1, 0Eh, 0Dh, …)`，形狀一致 ——
**(左, 上, 右, 下)，單位是文字格**。320×200 的 EGA 畫面是 40×25 格，
`26h` ＝ 38 落在右邊界內，當成「右緣」講得通，當成「寬度」會超出。
語意是**強推論**，值是已證實。

所以怪物訊息面板在**第 22–38 欄、第 1 列起**，而且
**場上超過 10 隻時多留 3 列** —— 這條規則本身就說明原版一屏最多
顯示到某個數量，排版不是無限延伸。

`ds:9F84`（目前載入的圖號）與 `ds:9E2B`（這隻怪的圖號）只在不同時
才重載，所以**同一屏的怪物共用一張圖** —— 這也限制了版面：
一次戰鬥畫面上的怪物是同一種。

### 繪圖入口 `sub_1704E(種類, x, y)`

已知三個呼叫點：

| 位址 | 參數 | 情境 |
|---|---|---|
| `0x1A395` | `(0FFFFh, 0, 0)` | 換怪物圖之前先清掉 |
| `0x1A76D` | `(0FFFFh, 0, 0)` | 同上 |
| `0x1A115` | `(0, 16, 12)` | 緊接在「隨機挑一名隊員」（`ds:9FCF = rand(1, 人數) - 1`）之後 |

`0FFFFh` 是「清除」。`(0, 16, 12)` 那一組**不是怪物精靈的座標** ——
它前面剛挑完隊員，是攻擊動畫那條路徑。精靈的位置由下一節的實機截圖量出來。

### 戰鬥畫面（實機截圖，`shots/x5.png`）

拍到了。版面與先前的推測**不一樣**：

	┌─ 第一人稱視圖 ─────┬─ 怪物名單（黃框）──┐
	│                    │ Skeleton           │
	│      ▓▓▓▓          │ Skeleton  × 10 行  │
	│      ▓▓▓▓          │ …                  │
	│   （單一精靈）      │ +3 more Skeletons  │
	├────────────────────┴────────────────────┤
	│ Options: A-Attack B-Bribe H-Hide R-Run  │
	├─────────────────────────────────────────┤
	│ 1) VOOHOO  …  隊伍列表                   │
	└─────────────────────────────────────────┘

**只畫一隻精靈。** 十三隻骷髏在畫面上只有一個精靈圖，
右邊那一欄用**文字列出名稱**（滿十行之後接 `+N more …`）。
先前 `internal/view/combat.go` 假設「由中央往兩側等距排 N 隻」，
方向就錯了 —— 原版根本不按數量排精靈。

這也解釋了為什麼 `2COMBAT` 只在 `ds:9F84 != ds:9E2B` 時才重載圖：
一屏只有一張圖要顯示，不是每隻各自載。

量到的位置（原始 320×200 座標）：

| 區塊 | 範圍 |
|---|---|
| 精靈 | 約 x 60–150、y 20–130（底邊貼視圖底部）|
| 怪物名單（黃框）| x 約 178–310、y 3–130 |
| 指令列 | y 133–147，`Options: A-Attack B-Bribe H-Hide R-Run` |
| 隊伍列表 | y 149–187（與平時相同）|

名單框的邊框是**黃色**，與平時的紅框不同 —— 顏色本身帶狀態資訊。
