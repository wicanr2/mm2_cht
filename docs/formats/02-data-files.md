# 資料檔格式

輸入檔見 [`docs/inventory.md`](../inventory.md) 的 SHA-256。
探測工具：`tools/probe_dat.py`（產生記錄長度候選，候選一律要另外驗證）。

## 總覽

| 檔案 | bytes | 熵 | 狀態 |
|---|---|---|---|
| `ITEMS.DAT` | 5,120 | 5.40 | **已解**，見 §1 |
| `MM2.CH` | 1,024 | 4.36 | **已解**，見 §2 |
| `MAP.DAT` | 18,748 | 7.50 | 索引已解，60 段全部解壓成功，見 §3 |
| `EVENTSI.DAT` | 49,609 | 7.72 | 索引已解，71 段解壓成功，見 §4 |
| `EVENTSO.DAT` | 25,797 | 7.72 | 同上 |
| `DEFAULT.DAT` | 780 | 2.55 | 6 × 130 bytes 角色記錄，見 §5 |
| `ROSTER.DAT` | 8,293 | 2.30 | 同格式，筆數未定，見 §5 |
| `SPELLS.DAT` | 192 | 4.87 | **未壓縮**，192 bytes = 96 × 2，見 §9 |
| `MONSTERS.DAT` | 5,702 | 7.56 | **已解**：26 × 256，數值欄位是位元欄位，見 §6 |
| `ATTRIB.DAT` | 1,768 | 7.41 | **已解**：64 × 60，每張地圖一筆，見 §8 |
| `STR.DAT` | 4,700 | 7.80 | **已解**：LZW + 每 byte −4，NUL 分隔單字表 |
| `.16` × 26 | — | — | **已解**（怪物圖的 RLE 除外），見 [`04-graphics.md`](04-graphics.md) |

高熵的那幾個共用同一套 LZW，段頭一律是「uint16 解壓後長度 + **uint16 0**」。
第二個 word 為 0 是判斷 LZW 段的可靠特徵 —— `SPELLS.DAT`、`ITEMS.DAT`、
`ROSTER.DAT`、`DEFAULT.DAT` 的開頭形狀很像段頭但第二個 word 不是 0，
它們是未壓縮的明文。見 [`03-lzw-compression.md`](03-lzw-compression.md)。

## 1. ITEMS.DAT — 道具表

**stride 20，256 筆**，無檔頭。

| 偏移 | 長度 | 內容 |
|---|---|---|
| +0x00 | 12 | 名稱，空格填充 |
| +0x0C | 1 | 0x00（256 筆全部如此） |
| +0x0D | 1 | **禁用職業的位元遮罩**（職業 0 是 bit7）|
| +0x0E | 2 | **特殊能力**，語意未解（一般武器是 0）|
| +0x10 | 1 | **傷害骰面數**（護甲類放的是防護加成）|
| +0x11 | 1 | 0（256 筆全部如此）|
| +0x12 | 2 | **價格**，uint16 |

256 筆的第 12 個位元組全是 0，名稱欄位邊界因此確定。

`+0x10` 的定位不是猜的：`2CMDS.img` 的 `sub_CE12` 把裝備換算成戰鬥數值時，
以 `20 × 物品編號` 索引記憶體裡的物品表，取的正是那一欄，寫進角色記錄的
`+76`（近戰骰面）或 `+78`（射擊骰面）。

```
Small Club 2   Dagger 4   Long Sword 8   Katana 10   Dyno Katana 20
```

價格同樣對得上：Small Club 1、Dagger 8、Long Sword 50、Katana 150。

### 分類是編號的範圍

`sub_CE12` 呼叫四個判斷式（`sub_D00E`／`D026`／`D03E`／`D056`）決定要往哪
一欄寫，它們都是單純的範圍比較：

| 編號 | 分類 | 首件 | 末件 |
|---|---|---|---|
| 1–91 | 近戰武器 | Small Club | Sun Naginata |
| 92–114 | 射擊武器 | Blowpipe | Black Key |
| 115–126 | 盾牌 | Small Shield | Gold Shield |
| 127–154 | 護甲 | Padded Armor | G Plate Mail |
| 155–159 | 頭盔 | Helm | Gold Helm |
| 160–255 | 其他 | Magic Herbs | Useless Item |

（射擊武器那一段的尾巴混進了幾把鑰匙，但原版的範圍就是這樣寫的。）

```
  0  BLANK          00 f0 00 00 00 00 00
  1  Small Club     00 00 00 02 00 01 00
  2  Small Knife    10 00 00 03 00 05 00
  4  Dagger         10 00 00 04 00 08 00
100  Quiet Sling    18 bf bd 05 00 dc 05
255  Useless Item   00 f0 00 00 00 01 00
```

### `+0x0D` 是「禁用」不是「可用」

裝備指令（`2CMDS.img` `0x1CA01`，印 `Equip Which (A-F)?` 的那一支）：

```
物品位址 = 20 × 記錄[+58+槽] + 0x6960
屬性     = 記錄[+70+槽]
if 屬性 == 0FFh:                                  錯誤 3
if 物品[+0Dh] & ds:3408[職業]:                    錯誤 4   ← 職業
if 屬性>>6 != 0 且 ds:3404[屬性>>6] != 記錄[+106]: 錯誤 5   ← 陣營
if 物品[+0Eh] == 0F0h:                            錯誤 14
```

`test` 之後**非零才是錯誤**，所以那個遮罩列的是**不能用的職業**。
`ds:3408 = [80,40,20,10,08,04,02,01]` —— **職業 0 是最高位**。

資料只有這個讀法說得通：**41 件近戰刀劍類全部設了牧師那個位元、
零例外**，棍棒類一個位元都沒設；Ring Mail 禁巫師與野蠻人。
反過來讀的話牧師就只能用刀劍。

`ds:3404 = [0,2,0,1]` 是附魔層 → 陣營，層 0 表示沒有陣營限制。

`+0x10` 與 `+0x12` 是遞增的 word（傷害／價格），由 `sub_CE12` 的用法定死。

### 執行時的位置：`ds:6960`

`2SMITH.img` 的 `0xC192` 用 `20 × 物品編號 + 6960h` 算出一筆記錄的
位址，所以**解壓後的 `ITEMS.DAT` 整份就躺在 `ds:6960`**，
每筆 20 bytes、名稱在最前面 —— 與 `internal/assets/items` 的
`RecordSize = 20` 一致。

那一段在 `MM2.EXE` 的 DGROUP 初值裡是全 0，是開機時才讀進去的。

## 2. MM2.CH — 8×8 點陣字型

1,024 bytes = **8 bytes/字元 × 128 字元**，每 byte 一列，MSB 在左。

字碼 32–127 是標準 ASCII 字形（已 render 驗證 `!"#$%&'`、`@ABCDEFG`、`` `abcdefg`` 全部對位）。
字碼 0–31 放的是自訂繪圖符號（框線、箭頭、方塊、菱形），不是控制字元。

中文化要換掉的就是這條渲染路徑：原版每個字元固定 8×8，中文需要獨立的高解析點陣層
（見 `CLAUDE.md` §6）。

## 3. MAP.DAT — 地圖

```
+0x0000  uint16 = 0x0078      索引表長度（120 bytes）
+0x0000  uint16[60]           每張地圖的檔案內偏移
+0x0078  地圖段 × 60
```

索引嚴格遞增，最後一段延伸到檔尾。段長 121–476 bytes，平均 310。

每段開頭 4 bytes 是 LZW 段頭，`uint16 = 0x0200 = 512` 為解壓後長度。
60 段全部解壓成功且長度一律 512 = 16×16 格 × 2 bytes。

解出的 512 bytes 內部結構（哪一半是地形、哪一半是屬性）尚未確定。

## 4. EVENTSI.DAT / EVENTSO.DAT — 事件表

兩個檔都以 **uint32 偏移表**開頭（71 筆，`0x11C` bytes）：

```
EVENTSI.DAT  +0x00: 0000011C 000005DD 00000AA5 00000F92 00001428 0000...
EVENTSO.DAT  +0x00: 00000000 ×4, 0000011C 0000049D 00000933 00000DC5 ...
```

`EVENTSO.DAT` 前四筆是 0（空槽）。第一個非零偏移都是 0x011C = 284 = 71 × 4，
與索引表長度自洽。段體是 LZW，已可解開。

`EVENTSI.DAT` 前三段解出的內容是地點名，依序對應 Middlegate、Atlantium、Tundara，
與 `MM2.EXE` 尾部的城鎮列表同序：

```
段 0  Middlegate Inn / S.J. Blacksmith / Slaughtered Lamb / Gateway Temple / Turkov's Training
段 1  Carriage Inn / Drewnhald Ironworks / Boar's Tongue Tavern / Island Training
段 2  Tundaran Arms Inn / Lucky Dog Saloon / Thundrax Weaponry / White Dove Temple
```

載入常式依旗標把檔名第 7 個字元填成 `i` 或 `o`（`mov cl,'i'` / `mov cl,'o'`，
寫進 `[bx+6]`），證實 I/O 就是同一個載入路徑的兩個變體。

### 執行時的位置與字串讀取機制

解壓後的段被複製到 `SS:0x6052`，長度固定 `0x47E` words = 2,300 bytes
（`mov ax, ss` / `mov di, 6052h` / `mov cx, 47Eh` / `rep movsw`）。

`2PLAY.OVL` 有兩支常式操作它。**`sub_19016` 逐位元組讀字串**：

```asm
mov si, word_154C0        ; 目前的字串指標
mov al, [si+6052h]
inc si
cmp al, 0FFh              ; 0xFF 結束
jz  done
and [bp+var_2], 7Fh       ; 清掉 bit7
cmp [bp+var_2], 40h       ; 是 '@' 就換成 0x0A（換行）
```

**`sub_18FD0` 跳到第 N 條字串**：從目前位置往後掃過 N 個 `0xFF`，
把指標寫回 `word_154C0`。**字串是順序存取的，沒有隨機索引表** ——
這也解釋了為什麼在資料裡找不到字串偏移陣列。

`and 0x7F` 在目前這份資料上是 no-op：1,308 條字串沒有任何位元組帶 bit7。

### 段的佈局

`2PLAY.OVL` 的 `sub_1A85C` 給出完整佈局：從偏移 0 開始每次讀 3 個位元組，
三個都為 0 才跳出；接著讀兩個位元組組成 `skip`，用「事件表結束 + skip」
算出字串區起點（`word_1042C`），「事件表結束 + 2」是腳本區起點（`word_155BC`）。

```
事件表      3 bytes/筆，以 00 00 00 結束
uint16      skip
腳本區      事件表結束 +2 起，0xFF 分隔的變長序列
字串區      事件表結束 + skip 起，0xFF 分隔
```

事件記錄的三個欄位：

| 欄位 | 觀察 |
|---|---|
| Cell | 格位置，0–255 對應 16×16；同一段內嚴格遞增 |
| Index | 1 起算，上限與該段的事件筆數相當 —— 推定為腳本或字串序號 |
| Kind | 值都是 16 的倍數，**低 nibble 恆為 0**；高 nibble 是類型（觀察到 1–F） |

Middlegate（EVENTSI 段 0）：42 筆事件、34 條字串，第一筆事件在第 8 格。

`skip` 可以是 0（EVENTSI 段 60、EVENTSO 段 64），表示沒有腳本區、
字串區緊接事件表 —— 原版就是直接 `word_1042C = si + skip`，不做下限檢查。

### 兩套佈局

編號 60 以上的段**沒有事件表**，走另一套：

```
uint16   skip
0xFF
腳本區    0xFF 分隔
字串區    skip 指到的地方起，0xFF 分隔
```

它們不對應地圖，是**腳本庫**：程式碼把 `ds:0392` 暫時換成該段號、
載入、用完換回來（`2PLAY.img` `0x196F6` 存舊值 → 換成 `0x43`／`0x46`
之類 → 呼叫 `sub_1743E` → 換回來）。城鎮與野外那些「付 N 金幣送你
去某地 (y/n)」的共用互動就住在這裡 —— 中門西側 (0,5) 那個
「傳送到 Sandsobar」在 `EVENTSI` 段 61。

認出來的判準是位置不是內容：`raw[2] == 0xFF`（`skip` 之後立刻是分隔符），
而事件表佈局的第三個位元組是 Kind，不會是 `0xFF`。

### 事件表的結構條件只有一條

**Cell 在段內嚴格遞增**，加上「掃得到 `00 00 00` 終止」與
「`skip` 落在段內」，三者就足以認出佈局。

**不要拿「Kind 低 nibble 恆為 0」當判準。** 那是從已經解得開的段
觀察來的統計，而整份資料有一筆反例：`EVENTSO` 段 37 的格 98
（`Kind = 0xF1`）。拿它當過濾器，會為了一個位元丟掉一整段 ——
段 37 放寬之後解出 47 筆事件、14 條腳本，字串是可讀的英文
（「A small oasis. You find 40 food.」之類）。低 nibble 的語意仍未知。

兩件事一起做完之後，**71 個非空段全部解得開，一段未解都沒有**。

**130 bytes/筆**。`DEFAULT.DAT` = 780 = 6 × 130，六個預設角色；
`ROSTER.DAT` 8,293 bytes = 130 × 63 + 103，尾端 103 bytes 不成一筆。

### 職業與屬性順序怎麼定的

兩者互相定錨：`+0x0F` 在六個預設角色裡剛好是 0、1、2、3、4、5，
而每個角色屬性的**峰值都落在自己職業該高的那一項**：

| 角色 | `+0x0F` | 屬性 | 峰值 |
|---|---|---|---|
| Sir Felgar | 0 騎士 | 21,10,9,15,17,12 | 力量 21 |
| Terwin III | 1 聖騎士 | 21,10,14,15,15,10 | 力量 21 |
| Sure Valla | 2 弓箭手 | 17,16,8,19,21,12 | 速度 21 |
| Gene Eric | 3 牧師 | 12,10,20,11,18,18 | 性格 20 |
| Cassandra | 4 巫師 | 12,21,7,20,20,8 | 智力 21 |
| The Hermit | 5 盜賊 | 18,15,6,15,17,21 | 準確 21 |

六個全中。單看一個可能是巧合，六個同時對上才是證據。
寫成 `TestStatOrderMatchesClass`。

三條獨立的合理性檢驗一起通過，欄位位置才站得住：屬性都落在 3–25、
六人的 HP 都等於上限、當前屬性都等於基礎屬性（預設角色不該帶增減益）、
年齡都在 14–60。錯開一個位元組就會踩到其中一條。

### 性別、陣營、種族怎麼定的

- **性別**：`+0x0C` 為 1 的正好是 Sure Valla 與 Cassandra 兩位。
- **陣營**：`+0x0D` 為 0 的是遊俠 Terwin III 與牧師 Gene Eric，
  而手冊說**遊俠必須是善良陣營** —— 所以 0 是善良。
- **種族**：`+0x0E` 的值域 0–4，順序照手冊第 23–24 頁的選單。
  定錨靠手冊的屬性修正：半獸人「+1 力量耐力、−1 智慧人格運氣」，
  而值為 4 的 Sir Felgar 正是力量 21、智慧 10、人格 9；
  精靈「+1 智慧準確度」，值為 1 的 Cassandra 智慧 21、The Hermit
  準確度 21。六個角色的修正方向都對得上。

### 等級、年齡、食物怎麼定的

靠 `ROSTER.DAT` 那四十個練過的角色，比只有六個一級新角色的
`DEFAULT.DAT` 有力得多：

| 偏移 | 名冊值域 | 判準 |
|---|---|---|
| +32 等級 | 1–25 | 四十筆全部落在合理範圍 |
| +33 年齡 | 18–42 | 預設角色全是 18，與手冊 p.34 的人物資料截圖 `Age=18` 一致 |
| +37 食物 | 0–40 | 上限 40，與手冊給的食物上限相同；四十筆裡有二十四筆是滿的 |

### 這批偏移是怎麼一次拿到的

root 的人物資料畫面繪製函式（`2PLAY.img` `0x2A00` 起那一大段）對每個欄位
呼叫一次 `sub_29DE(欄位序號, 值)`，把序號與偏移一次全列了出來：

```
序號 1 → +0x5E(94,word)   2 → +0x74(116)   3 → +0x21(33)    4 → +0x6B(107)
     5 → +0x58(88,word)   6 → +0x5A(90)    7 → +0x62(98,dword)
     8 → +0x6C(108)       9 → +0x6D(109)   a → +0x24(36)    b → +0x72(114)
     c → +0x66(102,dword) d → +0x73(115)   e → +0x5C(92,word)
     f → +0x6E(110)      10 → +0x1E(30)   11 → +0x25(37)   12 → +0x6F(111)
    13 → +0x70(112)      14/15 → +0x50(80)
```

語意再用名冊的四十筆判：`+113` 與等級欄逐筆相同、`+114` 只有 0 與 1 而且
只有施法職業非零、`+115` 的值域與其他屬性同量級（且與 `+39` 逐筆相同，
兩者是同一項屬性的基礎與當前）、`+116` 與 `+96` 逐筆相同。

### 抗性與盜行

`+22`…`+29` 那八個位元組的值只有 0／5／10／30／35／60，而且**依種族分群**，
與手冊的種族修正逐條吻合：

| 種族 | 魔法 | 火焰 | 電擊 | 寒冰 | 沈睡 | 毒素 |
|---|---|---|---|---|---|---|
| 人類 | 0 | 5 | 5 | 5 | 58 | 58 |
| 精靈 | 1 | 0 | 0 | 0 | 30 | 5 |
| 矮人 | 0 | 10 | 10 | 10 | 0 | 60 |
| 侏儒 | 35 | 0 | 0 | 0 | 0 | 0 |
| 半獸人 | 0 | 5 | 5 | 5 | 30 | 30 |

手冊寫侏儒有魔法抗力、矮人有毒抗力、半獸人「對睡眠法術及毒藥有少許抗力」
—— 三條全中。順序照介面上那份清單
（`Energy / Fire / Sleep / Electricity / Poison / Cold / Acid`，
但記錄裡的排法是魔法在前）。

`+30` 只有六筆非零，職業全是賊或忍者 —— 那是**盜行**，不是每個人都有的欄位。

### 物品區是六組平行陣列，不是「編號一整排、屬性一整排」

`2CMDS.img` 的 `sub_CE12` 以 `記錄 + 基底` 取 `+0x28`（編號）與 `+0x34`（屬性），
基底是 0（已裝備）或 18（背包）；`2PLAY.img` 的 `0x9B44`（給予物品）則直接寫
`+0x3A`／`+0x40`／`+0x46` —— 那正是背包那三欄。兩支不相干的程序對上同一個排法。

驗證：名冊裡有裝備的角色，把已裝備欄的近戰武器拿去查物品表得到的骰面數，
與記錄裡 `+76` 存的值**逐筆相同**。`+76` 是原版寫進存檔的、換算是照原版程式碼
自己算的，兩個獨立來源。排法只要抓錯一欄就對不上。

黃金另有直接證據：`2PLAY.img` 的 `sub_5188` 把全隊的 `+102` 加總、夠付就
扣掉並設旗標 `ds:042F`；`DEFAULT.DAT` 裡 200 金幣全在第一個角色身上，
正是原版起始隊伍的配置。同一組還有兩支同型函式，分別處理 `+92`（寶石）
與 `+37`（食物）—— 第三個正是先前就定位好的食物欄，互相佐證。

寫回這些欄位之後，`DEFAULT.DAT` 與 `ROSTER.DAT` 的位元組完全一致往返
仍然成立，這也是欄位寬度沒抓錯的旁證。

### 還沒定位

第二技能、裝備欄、背包。畫面繪製的序號 `0x10`（+30）與 `0x14`／`0x15`
（+80）指向那一帶，但值稀疏（多數為 0），還沒判出語意。

`+33` 與經驗等級的相關性是 **+1.00** —— 這批名冊角色都是同一種練法，
所以年齡剛好跟著等級走。相關性本身不能證明它是年齡，
是「預設角色全 18」加上手冊截圖才定案的。

### SP 怎麼定的

`+88`/`+90` 只有牧師與巫師非零（各 7 點），武士、遊俠、弓箭手、賊都是 0 ——
手冊說遊俠與弓箭手要到高經驗等級才有法力，而預設角色都是第一級。

### 未解

`+0x16`–`+0x26`、
`+0x28` 之後的大片區域（技能、裝備、道具欄、經驗值、金錢）。
`Character.Raw` 原樣保留整筆 130 bytes，未解的欄位寫回時不會掉。

## 6. MONSTERS.DAT — 怪物表

解壓後 6,656 bytes = **26 × 256**。

| 偏移 | 長度 | 內容 |
|---|---|---|
| +0x00 | 14 | 名稱，空格填充 |
| +0x0E | 12 | 數值，語意未解 |

### 名稱每個位元組加了 0x80

檔案裡存的不是 `Goblin` 而是 `c7 ef e2 ec e9 ee` —— 每個位元組都加了
`0x80`。所以直接 grep 怪物名什麼都找不到，`MONSTERS.DAT` 一度被當成
「沒有字串的純數值檔」。減掉 `0x80` 之後 256 筆全部是乾淨的 ASCII，
一筆不漏。

stride 取 26 而不是 52 或 64（都能整除），依據是名稱欄位要在每筆的
同一個位置對齊：換成 52，一筆裡就會出現兩個名字。

### 排序

前幾筆是雜兵，最後五筆是四位元素領主與最終首腦：

```
[  0] Creepy Crawler   [  3] Kobold        [ 17] Orc
[251] Shalwend         [252] Pyrannaste    [253] Acwalandar
[254] Gralkor          [255] Sheltem
```

`Shalwend`／`Pyrannaste`／`Acwalandar`／`Gralkor` 正是四元素位面的
領主（事件文字裡各自喊「竟敢闖進我的位面」），`Sheltem` 是最終首腦。
排序與劇情一致，寫成 `TestMonsterAnchors`。

### 數值欄位是位元欄位

+0x0E 之後那 12 個位元組**不是直接的數值**：低位是基數、高位是 10 的冪次
的倍率索引。直接拿原始位元組當數值用會算出荒謬的結果 —— 第一版把 +0x0F
（值域 37–255）當等級，四百次攻擊命中零次。

解包規則抄自 `2COMBAT.img` 的 `sub_3B80`（倍率表在 DGROUP `ds:4DB8`，
值是 `1, 10, 100, 1000`）：

| 位元組 | 欄位 | 規則 |
|---|---|---|
| +0x0E | 生命點數 | `((b & 0x3F) + 1) × 倍率[b >> 6]` |
| +0x0F | 經驗值 | `((b & 0x1F) + 1) × 倍率[(b >> 5) & 3]`，`b > 0x7F` 再 × 1000 |
| +0x11 | 群體大小上限 | `(b & 0x0F) + 1`，bit4 再 × 10；bits 5–6 是士氣層、bit7 是「會增生」|
| +0x14 | 每回合攻擊次數 | `(b & 0x0F) + 1`；高 nibble +1 是每輪最多行動幾次 |
| +0x15 | `MONSTERS.16` 的段號 | `b & 0x7F` |
| +0x16 | 防護等級 | `(b & 0x1F) + 1`，bit5 再 × 10；bit6「重排時跳過牠」、bit7 未解 |
| +0x17 | 傷害骰面數 | `(b & 0x1F) + 1`，bit5 再 × 10（乘完超過 25 就固定 250）；bit6 火抗、bit7 電抗 |
| +0x18 | **速度** | `(b & 0x1F) + 1`，bit5 同上；bit6 冷抗、bit7 酸抗 |
| +0x19 | 抗魔法與三格抗性 | bits 5–7 `& 7` 查 `ds:4DC0`；bit0/1/2 是三格抗性 |

段號那一欄的判準是**用法不是值域**：`2COMBAT.img` 的 `0xA384` 拿 `ds:9E2B`
與「目前載入的段號」比，不同才呼叫載入 —— 數值欄位不會這樣用。
256 隻共用 58 個相異值（範圍 1–60），而 `MONSTERS.16` 正好 59 個段。

### 抗性那七格：位址就是索引

七格抗性攤在 `ds:9E36` 起的**連續七個位元組**，`sub_18674(屬性-1)` 直接
`ds:9E36[索引] != 0` —— 有旗標就完全免疫，沒有機率可言。位址與索引
一一對應，所以來源位元不必猜：

| 索引 | 屬性 | 位址 | 來源 | 全表隻數 |
|---|---|---|---|---|
| 0 | 火 | `ds:9E36` | `+0x17` bit6 | 105 |
| 1 | 電 | `ds:9E37` | `+0x17` bit7 | 68 |
| 2 | 冷 | `ds:9E38` | `+0x18` bit6 | 101 |
| 3 | 酸 | `ds:9E39` | `+0x18` bit7 | 59 |
| 4 | 睡 | `ds:9E3A` | `+0x19` bit1 | 214 |
| 5 | 法術狀態 | `ds:9E3B` | `+0x19` bit0 | 172 |
| 6 | 未定 | `ds:9E3C` | `+0x19` bit2 | 8 |

名字是獨立的判準，四格全部落點：四隻名字帶 Fire 的怪物全部有火抗、
零例外；Frost Dragon 與 The Snowbeast 都有冷抗；Acidic Blob 有酸抗；
Lightning Bugs 有電抗。

**`ds:9E34`／`ds:9E35` 不在這個陣列裡** —— 位址在基底之下，
來源是 `+0x16` 的 bit7／bit6，是另外兩個旗標。挑相鄰位元組的
相鄰位元看起來一樣合理，靠的就是「位址即索引」這條把它們分開。

### 抗魔法的梯度

`+0x19` 的高三位 `& 7` 查 `ds:4DC0`（`0, 10, 20, 35, 50, 75, 90, 100`）。
八個階層的平均難度層一路遞增：

```
階層  0    1    2    3    4    5    6    7
層均 5.9  6.1  7.2  9.1 11.1 10.4 11.2 13.7
隻數 116   21   36   37   27   10    6    3
```

三隻 100% 的全在最頂端。**這個梯度就是欄位認對了的證據** ——
換一個位元組來讀，梯度立刻散掉，而且只用得到七個階層。

剩下未解的：`+0x16` bit7（進 `ds:9E34`，在 2COMBAT 裡只有寫沒有讀）、
以及 `ds:9E20`–`ds:9E3F` 裡幾個只被累加、沒找到讀取端的計數器。

驗算（`TestUnpackedStats`）：

```
  2 Sewer Rat        HP      8  經驗       150  攻擊  1  骰  12
 50 Crazed Dwarf     HP     45  經驗      1200  攻擊  2  骰  20
250 Mega Dragon      HP  64000  經驗  32000000  攻擊 16  骰 250
255 Sheltem          HP    500  經驗    500000  攻擊  8  骰  60
```

難度梯度與劇情一致，量級也與社群流傳的數值相符。

### 難度層

怪物編號的高 nibble（0–15）就是難度層，命中門檻表 `ds:103A` 用它索引：

```
40, 45, 50, 55, 60, 65, 70, 75, 80, 90, 100, 120, 150, 250, 100, 200
```

命中率（百分比）＝ 門檻 − 目標的防護等級；目標防護高於門檻時固定 5%。
出自 `2COMBAT.img` 的 `sub_8398`，完整流程見 [`docs/formats/08`](08-combat.md)。

## 7. 隨機數產生器

`sub_11C88` 是全遊戲共用的亂數來源，種子在 `ds:4A14h`（16-bit）。

```asm
mov     ax, ds:4A14h
add     ax, 9248h
ror     ax, 1  ×3
xor     ax, 9248h
add     ax, 11h
mov     ds:4A14h, ax
and     ax, 7FFFh
...
sub     cx, bx          ; cx = hi - lo
inc     cx
xor     dx, dx
idiv    cx              ; dx = 餘數
add     dx, bx          ; + lo
```

介面是 `rand(lo, hi)`，兩端都含。三個邊界處理：`hi` 為 0 時當成 1、
`lo` 大於 `hi` 時對調、範圍大小是 `hi-lo+1`。

播種在 `sub_11CCC`：`int 21h` AH=2Ch 取 DOS 時間，把 DX（秒與百分秒）
與 CX（時與分）加進種子。緊接 `sub_11C88` 之後還有一個只做
`mov ds:4A14h, ax` 的小程序，那是直接設種子用的。

**這是能重播原版行為的前提** —— 同一顆種子必然給出同一串數列，
所以 remake 用同一套算法，戰鬥、遭遇、寶物的隨機結果就與原版一致，
存檔把種子一併寫進去也能重播。實作在 `internal/game/rng.go`。

## 8. ATTRIB.DAT — 每張地圖的屬性

解壓後 3,840 bytes = **64 × 60**，一張地圖一筆。

定錨靠第一個位元組：六十筆的 `+0` 剛好是 0…59，一個不差。
這也是 stride 只能是 64 的理由 —— 3,840 能被 15、16、26 整除，
但換成那些數字，`+0` 的遞增序列立刻散掉。

| 偏移 | 內容 |
|---|---|
| +0 | 地圖編號，等於自己的索引 |
| +4 | 低 nibble 是**場景（貼圖組）碼**：室內全是 0，野外是 9／10／11／12 |
| +5 | **北**邊的鄰接地圖 |
| +6 | **東**邊的鄰接地圖 |
| +7 | **南**邊的鄰接地圖 |
| +8 | **西**邊的鄰接地圖 |
| +9 | **遭遇機率的分母**：每走一步擲 `rand(1, N)`，擲出 1 才遇敵 |
| +13 | **戰鬥中溜跑的成功率**（百分比，10 的倍數）。城鎮一律 100 |
| +14 | **預設進入座標**：低 nibble = X、高 nibble = Y，`0xFF` 表示沒有 |
| +18 | **撞門的難度門檻** |
| +19 | **開鎖失敗那一擲的門檻**：`rand(1,100)` 大於它才觸發陷阱 |
| +20 | **陷阱傷害的左移量**（1–6）：傷害 = 基礎[場景] << 這個值 |
| +32…+63 | 位元圖，用途未定 |

### `+14`：換圖時沒指定落點就用它

`sub_1B5EA` 收到的 X 參數是 `0xFF` 時，改讀 `ds:5994`
（＝ ATTRIB 記錄搬到 `0x5986` 之後的 `+14`）並拆成兩個 nibble；
`sub_5E68` 的 `0x15E36` 是同一段邏輯。60 張裡 58 張有值。

地圖 0（Middlegate）的值是 `0x57` → **(7,5)**，走過去正是「中門旅店」
那一格 —— 而 MM2 就是從旅店開局。事件腳本的傳送（opcode `0x0c`）
走不到這條路徑，它給的 X 永遠在 0–15。

### 鄰接怎麼定的

**鄰接是雙向的**：往東走到的那張圖，往西要走得回來。

| 配對 | 互指的張數 |
|---|---|
| **+5 ↔ +7** | **60/60** |
| **+6 ↔ +8** | **60/60** |
| +5 ↔ +6、+5 ↔ +8、+6 ↔ +7、+7 ↔ +8 | 40/60 |

兩軸都是六十張全中，交叉配對只有 40/60 —— 差距夠大，不是巧合。

方位由 `sub_1B75E`（走出邊界時換圖）定死，不必靠世界地圖回推：

```asm
cmp  ds:0393, 10h     ; X 溢位（走出東邊）
mov  al, ds:598C      ; → ATTRIB +6
cmp  ds:0393, 0FFh    ; X 掉到 -1（走出西邊）
mov  al, ds:598E      ; → ATTRIB +8
cmp  ds:0394, 10h     ; Y 溢位（走出北邊，因為北是 +Y）
mov  al, ds:598B      ; → ATTRIB +5
cmp  ds:0394, 0FFh    ; Y 掉到 -1（走出南邊）
mov  al, ds:598D      ; → ATTRIB +7
and  ds:0393, 0Fh     ; 再把座標繞到對邊
and  ds:0394, 0Fh
```

所以 **`+5` 是北、`+7` 是南**。`& 0x0F` 讓 16 變 0、-1 變 15，
也就是從對邊進來。

### `+9`：遭遇機率的分母

`sub_17EB9` 每走一步做一次：

```asm
mov  al, ds:598F      ; ATTRIB +9
push ax
push 1
call rand             ; rand(1, N)
cmp  結果, 1
jne  不遇敵
```

前面還有一行 `cmp ds:59C8, 80h / jae 跳過` —— **踩在事件格上不擲**。

五座城鎮是 200 或 100，野外多半 100，全體落在 50–250。

### 開鎖陷阱（`+19`／`+20`）

`2MISC.OVL` 的 `0xC2B2`：

```
擲 = rand(1,100)
擲 < 96 且 盜行 >= 擲 → 成功
否則：
  擲2 = rand(1,100)
  +19 >= 擲2 → 只是失敗
  +19 <  擲2 → 觸發陷阱
      種類 = rand(1,100) & 3
      訊息 = ds:28F2[場景 × 16 + 種類 × 4]
      傷害 = ds:2946[場景] << +20      基礎表 = 3, 4, 4, 5, 6
```

四種陷阱依訊息內容是**電擊／火焰／毒氣／尖刺**，五種場景各有一組措辭，
共 20 條（全部已在譯文檔裡）。觸發時先印 `Explosion!`。

場景由 `sub_1CA00` 把 `+4` 的低 nibble 換算（0→0、3→1、1→2、4/6→3、
其餘→4）。**有鎖的地圖全是室內，而室內的 `+4` 低 nibble 全是 0**，
所以實際上一律走場景 0（基礎傷害 3）。地圖 0 的 `+20` 是 1 → 6 點傷害，
最深的地城是 5–6 → 96–192 點。

`sub_1C390` 對職業 5（賊）與 6（忍者）多呼叫一次 `sub_1C338`，
那一段還沒解；抗性有沒有減免也未解。

### 三個旁證

1. **五座主要城鎮（0–4）四面都指向自己**，走到邊界不會接到別張圖。
2. **第 5 張之後有 20 張與別圖相連** —— 手冊的世界地圖正好是
   A1–E4 二十張野外區。
3. 城鎮以外的其餘 35 張也是自封的，那些是地城與洞窟 —— 只能由入口進出。

### `+22`／`+24`／`+26`：地面出口與法術禁令

`ds:5986` 是地圖屬性那 64 bytes 在記憶體裡的起點（撞門那條用
`ds:5998` ＝ `+18` 定出來的）。往後數：

| 位移 | 記憶體 | 內容 |
|---|---|---|
| `+22` | `ds:599C` | 地面返回座標（低 nibble X、高 nibble Y）|
| `+24` | `ds:599E` | 地面地圖編號 |
| `+26` | `ds:59A0` | 禁止哪些法術的位元組 |

資料本身把這三格的語意釘死了：**二十四張野外圖的 `+22` 全是 0、
`+24` 全等於自己**；三十六張室內圖的 `+22` 全非 0、`+24` 指向一張
野外圖。傳送到地面（`sub_1C92A`）就是讀這兩格，`+22` 為 0 時整條
法術失敗 —— 站在野外用它沒有意義，資料自己擋掉了。

例外五張：野外 41–44 的 `+24` 是 0、室內 59 的 `+22` 是 0，
與相鄰地圖比對看得出是沒用到的空欄位。

`+26` 的位元對應見 `docs/formats/09-spells.md`。城鎮（圖 0–4）是 0，
同座城的地下層是 `0x80`，圖 23 是 `0xFA` —— 幾乎所有傳送與位移類
都被擋掉。

### `+13`：戰鬥中溜跑的成功率

讀取端在 `2COMBAT.img` 的 `0x19162`，而那支函式（`sub_1914A`）是
戰鬥指令跳表 `0x19578` 裡 `R` 那一格：

```
[bp-2] = rand(1, 100)
if [bp-2] >= ds:5993:  直接 ret        ; ds:5993 ＝ ATTRIB +13，跑失敗
ds:547E = 1
ds:0426--                              ; 隊伍人數減一
把最後一格搬進空出來的那一格           ; ds:0416（word）與 ds:548C（byte）
ds:549D 夾回新的人數
ds:9FCF = 0
if ds:0426 != 0: sub_19F44()
```

**跑掉的是下指令的那一個人**（`ds:9FD2`，開戰時歸零的那個角色索引，
與怪物側的 `ds:9FD0` 對稱），不是整隊 —— 其他人留在場上繼續打。

值全是十的倍數，六十張地圖分佈：

| 值 | 20 | 30 | 40 | 50 | 60 | 70 | 80 | 90 | 100 |
|---|---|---|---|---|---|---|---|---|---|
| 張數 | 2 | 6 | 9 | 11 | 3 | 6 | 15 | 2 | 6 |

**五座城鎮（圖 0–4）都是 100** —— 在城裡打不贏一定跑得掉。
野外 20–90，地城 20–100。

移除的寫法與怪物那邊**不同**：怪物是整批往前搬（`sub_18A22`），
角色是拿最後一格補洞，所以戰鬥中的隊伍順序會變。

## 9. SPELLS.DAT — 施法代價

192 bytes = 96 × 2。載入位置由 `1MENU1.OVL` 的 `0x1C770` 給出：

```asm
push 0C0h          ; 192 bytes
push 0
push 7D60h         ; → DGROUP ds:7D60
push 1A75h         ; "spells.dat"
call sub_16FB6
```

### 前 48 筆是巫師，不是牧師

root 的 `sub_15644`：

```asm
bx = 角色記錄
cmp  byte [bx+0Fh], 2      ; 職業 2 = 弓箭手
je   不加
cmp  byte [bx+0Fh], 4      ; 職業 4 = 巫師
je   不加
add  [bp-4], 30h           ; ← 其餘職業（牧師那一系）序號 +48
不加:
ax = [bp-4] * 2 + 7D60h
```

所以**檔案的前 48 筆給弓箭手與巫師，後 48 筆給牧師系**。
`data/spells.json`（抄自手冊）的順序相反，`cmd/mm2data` 產生
`spellcosts.json` 時已經對調。

### 兩個位元組的欄位

```
A 低 nibble   寶石消耗
A 高 nibble   旗標，未解
B 位元 0–3    固定法力消耗
B 位元 4–6    每施法者等級的法力消耗
B 位元 7      旗標，未解（12 條有）
```

施法要付的法力 = `固定 + 每等級 × 施法者等級`。

**驗證**：與手冊逐條比對，可解析的 92 條裡法力 84 條相符、寶石 87 條相符。
對不上的兩類都有解釋 ——

- 八條是手冊自己把固定消耗標成「N SP／L」（魔網、衰弱心智術、時間扭曲、
  分裂術、死亡之指、粉碎術、陷敵術、能量補充術）。手冊已知自身不一致，
  裁決以程式為準。
- 五條的寶石消耗超過 15（20／50／100），一個 nibble 放不下，
  高位怎麼編碼還沒解。

等級：**已證實**（載入位址、兩半的分派、位元欄位都直接讀自程式碼）。

## 9.1 SPELLS.DAT — 尚未解出的部分

192 bytes 明文，而法術正好 96 條（牧師 48 + 巫師 48），所以是
**每條法術 2 bytes**。前 96 bytes 對牧師、後 96 對巫師，
兩半的位元組樣式相似（`40 01`、`80 01` 這類反覆出現）。

拆成兩個 byte 欄位之後：

| 欄位 | 值域 | 觀察 |
|---|---|---|
| A | 0–191 | 高 nibble 常見 0/4/8 |
| B | 1–192 | 低 nibble 與手冊的法術等級相符 **29/48** |

**29/48 不足以定案。** 不符的四處（索引 2、7、13、14）欄 B 分別是
`0x10`、`0xA0`、`0x10`、`0x10` —— 高 nibble 一有值，低 nibble 就是 0。
看得出是位元欄位而不是單純的數值，但欄位邊界還沒切出來。

另一個可能是 `SPELLS.DAT` 的排列順序根本不是手冊的顯示順序，
那樣逐位比對本來就對不上。要定案得先找出程式怎麼索引這張表 ——
入口是 `2CAST1.OVL` / `2CAST2.OVL`，還沒反組譯過。

## 附錄：與 1989 年《軟體世界》欄位表的對照

第 10 期（1989）的「魔法門 II 無敵常勝軍」附了一張 `ROSTER.DAT` 的欄位偏移表。
它的偏移比本文件大 `0x0C`（雜誌的 hex dump 從檔案第一筆的姓名起算）。
扣掉之後，本專案**獨立**從反組譯與名冊資料解出的七個欄位全部對上：

| 雜誌 | −0x0C | 雜誌說 | 本專案解出的 |
|---|---|---|---|
| `0C～15` | +0 | 姓名 | 姓名（10 bytes）|
| `2A` | +30 | 盜行能力 | 盜行 |
| `30` | +36 | 防護級數 | 防護等級 |
| `32` | +38 | 身體狀況 | 狀況位元遮罩 |
| `34～39` | +40 | 裝備 | 已裝備的物品編號 |
| `72～75` | +102 | 黃金 | 黃金（uint32）|
| `80` | +116 | 最高健康點數 | 生命上限的另一份 |

七比七。這張表也補上了三個本專案沒解出來的欄位：`+46`／`+64` 的可使用次數、
`+80` 的第二技能、`+81` 的已學法術 —— 後兩者已用名冊資料獨立驗過
（施法職業與非施法職業的法術位元、第二技能的兩 nibble 值域）。

### 兩處與名冊資料衝突，以名冊為準

雜誌說 `77～7C`（= +107…+112）的順序是「力量、人格、智慧、速度、準確度、運氣」、
`7F`（= +115）是「耐力」。名冊資料不支持：

- `+108` 逐筆等於基礎屬性的 `+17`。而 `+17` 是**智慧**——由職業峰值定死：
  牧師 Gene Eric 的基礎屬性峰值在 index 2（人格），巫師 Cassandra 在 index 1（智慧），
  所以基礎區塊是「力量、智慧、人格、耐力、速度、準確度」。雜誌把 `+108` 說成人格。
- `+115` 逐筆等於 `+39`，而 `+39` 與基礎區塊的耐力欄（`+19`）**不相同**。
  若 `+115` 是當前耐力，它的基礎應該是 `+19`。

**一手資料（原始檔案的內容）贏二手推論（雜誌的整理）。**

## 商店（`2SMITH.OVL`）

兩個進入點：

| 位址 | 作用 |
|---|---|
| `0xC130` | 對 `ds:583E` 指到的角色的 `+102`（金錢）做 **32 位元加法**，值由呼叫端的兩個 word 給 |
| `0xC150` | 把角色背包的三排各 6 bytes 複製到工作區，再建一份名稱指標表 |

`0xC150` 複製的三排是：

	ds:57BA ← 記錄 +58（背包物品編號）
	ds:5840 ← 記錄 +64（背包充能）
	ds:580E ← 記錄 +70（背包屬性）

**商店在副本上作業**，不是直接改角色記錄 —— 這決定了「反悔」與
「交易失敗」的語意：沒寫回去就等於沒發生。

`ds:583E` 是目前角色的記錄指標（與戰鬥用的 `ds:5DD6` 是同一種東西，
不同場景用不同的一格）。

名稱指標表是 `20 × 物品編號 + 6960h`，六格對應背包六個槽位。

### 定價（`0xC80A`）

只看兩件事：物品記錄 `+18` 的基礎價，與屬性欄（`+70`）低六位的
附魔等級。

	空槽（+58 == 0）→ 0

	鑑定（ds:582A == 6）：
	    附魔等級 0 → 10
	    否則      → 100 × 等級

	買賣：
	    值 = 記錄 +18
	    等級每一級：值 × 2
	    等級非 0：值 += 1000 × 等級
	    技能 = 這個人有沒有第 10 項第二技能
	    賣（ds:582A == 5）：值 ÷ 2；沒技能再 ÷ 2
	    買：有技能才 ÷ 2

**加倍在前、加常數在後** —— 順序反了差很多（三級附魔的
`基礎 × 8 + 3000` 與 `(基礎 + 3000) × 8` 差一個量級）。

「第 10 項技能」的位置確定，譯名是強推論 —— 手冊的第二技能表
還沒逐項對過。

### 進貨：一個 0–25 的洗牌（`0xD19C`）

	清空 26 格的「抽過了」標記
	重複 26 次：
	    n = rand(1, 26) - 1
	    n 抽過了就重擲
	    標記[n] = 1
	    ds:584E[次序] = n

產出的是 **0–25 的一個排列**，不是「從清單裡挑幾件」——
二十六格全都會被填滿，差別只在順序。

### 這個排列沒有人讀

位元組序列 `4E 58`（小端序的 `584Eh`）在**十四個 overlay 映像裡
總共只出現一次**，就是那條寫入指令 `mov [si+584Eh], al` 本身。
`MM2.EXE` 的 DGROUP 初值段裡也找不到 `584Eh` —— 沒有任何指標變數
指向它，所以「用暫存器間接定址讀取」這條路也不成立。

**結論：`ds:584E` 只寫不讀，那個排列算完就丟。** 是被砍掉的功能
留下的死碼。

（掃描時要同時比對 `[si+584Eh]` 與 `[bx-A7B2h]` 兩種印法 ——
objdump 對絕對定址印正數、對索引定址印負的有號位移，
同一個位址在反組譯文字裡有兩張臉。直接掃位元組序列可以繞過這件事。）

### 貨架：四類商店 × 五座城 × 六件

`0xC93E` 用 `ds:0392`（地圖編號）× 6 當位移，從一對表各抄 6 bytes
進工作區。表在 `ds:43C8` 起連續八張 30 bytes，**兩張一組共四組**：

| 組 | 編號表 | 附屬表 | 編號範圍 |
|---|---|---|---|
| 0 | `ds:43C8` | `ds:43E6` | 4–24 |
| 1 | `ds:4404` | `ds:4422` | 115–155 |
| 2 | `ds:4440` | `ds:445E` | 160–211 |
| 3 | `ds:447C` | `ds:449A` | 9–97 |

每張 30 bytes ＝ 5 座城 × 6 件。第一張是物品編號，第二張是附屬值 ——
組 0／1／3 的值域是 0–12（附魔等級），組 2 出現 20／25／35／50／250
（充能次數的量級）。

一百二十件貨的編號**全部對得上 `ITEMS.DAT` 裡有名字、有價格的物品**
（`TestShopStock`）。城就是地圖 0–4，與城市傳送術的編號一致。

進貨的洗牌（`sub_1D19C`）產生 0–25 的排列，與這 6 件的貨架
**不是同一件事** —— 那個排列只寫不讀（見上），是死碼。
商店實際賣什麼完全由這張貨架表決定。
