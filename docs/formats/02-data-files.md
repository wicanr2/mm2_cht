# 資料檔格式

輸入檔見 [`docs/inventory.md`](../inventory.md) 的 SHA-256。
探測工具：`tools/probe_dat.py`（產生記錄長度候選，候選一律要另外驗證）。

## 總覽

| 檔案 | bytes | 熵 | 狀態 |
|---|---|---|---|
| `ITEMS.DAT` | 5,120 | 5.40 | **已解**，見 §1 |
| `MM2.CH` | 1,024 | 4.36 | **已解**，見 §2 |
| `MAP.DAT` | 18,748 | 7.50 | 索引已解，60 段全部解壓成功，見 §3 |
| `EVENTSI.DAT` | 49,609 | 7.72 | 索引已解，71 段解壓成功，見 §4 |
| `EVENTSO.DAT` | 25,797 | 7.72 | 同上 |
| `DEFAULT.DAT` | 780 | 2.55 | 6 × 130 bytes 角色記錄，見 §5 |
| `ROSTER.DAT` | 8,293 | 2.30 | 同格式，筆數未定，見 §5 |
| `SPELLS.DAT` | 192 | 4.87 | **未壓縮**，192 bytes 明文，內部結構未解 |
| `MONSTERS.DAT` | 5,702 | 7.56 | **已解**：26 × 256，見 §6 |
| `ATTRIB.DAT` | 1,768 | 7.41 | 解壓後 3,840 bytes，內部結構未解 |
| `STR.DAT` | 4,700 | 7.80 | **已解**：LZW + 每 byte −4，NUL 分隔單字表 |
| `.16` × 26 | — | — | **已解**（怪物圖的 RLE 除外），見 [`04-graphics.md`](04-graphics.md) |

高熵的那幾個共用同一套 LZW，段頭一律是「uint16 解壓後長度 + **uint16 0**」。
第二個 word 為 0 是判斷 LZW 段的可靠特徵 —— `SPELLS.DAT`、`ITEMS.DAT`、
`ROSTER.DAT`、`DEFAULT.DAT` 的開頭形狀很像段頭但第二個 word 不是 0，
它們是未壓縮的明文。見 [`03-lzw-compression.md`](03-lzw-compression.md)。

## 1. ITEMS.DAT — 道具表

**stride 20，256 筆**，無檔頭。

| 偏移 | 長度 | 內容 |
|---|---|---|
| +0x00 | 12 | 名稱，空格填充 |
| +0x0C | 1 | 0x00（256 筆全部如此） |
| +0x0D | 7 | 屬性 |

256 筆的第 12 個位元組全是 0，名稱欄位邊界因此確定。

```
  0  BLANK          00 f0 00 00 00 00 00
  1  Small Club     00 00 00 02 00 01 00
  2  Small Knife    10 00 00 03 00 05 00
  4  Dagger         10 00 00 04 00 08 00
100  Quiet Sling    18 bf bd 05 00 dc 05
255  Useless Item   00 f0 00 00 00 01 00
```

+0x0D 觀察到 `00`/`0x10`/`0x18`（類別或裝備部位），+0x10 與 +0x12 是遞增的 word
（傷害／價格一類）。欄位語意**待驗**——要對照原版的鑑定畫面或商店價目確認，
欄位名不是證據。

## 2. MM2.CH — 8×8 點陣字型

1,024 bytes = **8 bytes/字元 × 128 字元**，每 byte 一列，MSB 在左。

字碼 32–127 是標準 ASCII 字形（已 render 驗證 `!"#$%&'`、`@ABCDEFG`、`` `abcdefg`` 全部對位）。
字碼 0–31 放的是自訂繪圖符號（框線、箭頭、方塊、菱形），不是控制字元。

中文化要換掉的就是這條渲染路徑：原版每個字元固定 8×8，中文需要獨立的高解析點陣層
（見 `CLAUDE.md` §6）。

## 3. MAP.DAT — 地圖

```
+0x0000  uint16 = 0x0078      索引表長度（120 bytes）
+0x0000  uint16[60]           每張地圖的檔案內偏移
+0x0078  地圖段 × 60
```

索引嚴格遞增，最後一段延伸到檔尾。段長 121–476 bytes，平均 310。

每段開頭 4 bytes 是 LZW 段頭，`uint16 = 0x0200 = 512` 為解壓後長度。
60 段全部解壓成功且長度一律 512 = 16×16 格 × 2 bytes。

解出的 512 bytes 內部結構（哪一半是地形、哪一半是屬性）尚未確定。

## 4. EVENTSI.DAT / EVENTSO.DAT — 事件表

兩個檔都以 **uint32 偏移表**開頭（71 筆，`0x11C` bytes）：

```
EVENTSI.DAT  +0x00: 0000011C 000005DD 00000AA5 00000F92 00001428 0000...
EVENTSO.DAT  +0x00: 00000000 ×4, 0000011C 0000049D 00000933 00000DC5 ...
```

`EVENTSO.DAT` 前四筆是 0（空槽）。第一個非零偏移都是 0x011C = 284 = 71 × 4，
與索引表長度自洽。段體是 LZW，已可解開。

`EVENTSI.DAT` 前三段解出的內容是地點名，依序對應 Middlegate、Atlantium、Tundara，
與 `MM2.EXE` 尾部的城鎮列表同序：

```
段 0  Middlegate Inn / S.J. Blacksmith / Slaughtered Lamb / Gateway Temple / Turkov's Training
段 1  Carriage Inn / Drewnhald Ironworks / Boar's Tongue Tavern / Island Training
段 2  Tundaran Arms Inn / Lucky Dog Saloon / Thundrax Weaponry / White Dove Temple
```

載入常式依旗標把檔名第 7 個字元填成 `i` 或 `o`（`mov cl,'i'` / `mov cl,'o'`，
寫進 `[bx+6]`），證實 I/O 就是同一個載入路徑的兩個變體。

### 執行時的位置與字串讀取機制

解壓後的段被複製到 `SS:0x6052`，長度固定 `0x47E` words = 2,300 bytes
（`mov ax, ss` / `mov di, 6052h` / `mov cx, 47Eh` / `rep movsw`）。

`2PLAY.OVL` 有兩支常式操作它。**`sub_19016` 逐位元組讀字串**：

```asm
mov si, word_154C0        ; 目前的字串指標
mov al, [si+6052h]
inc si
cmp al, 0FFh              ; 0xFF 結束
jz  done
and [bp+var_2], 7Fh       ; 清掉 bit7
cmp [bp+var_2], 40h       ; 是 '@' 就換成 0x0A（換行）
```

**`sub_18FD0` 跳到第 N 條字串**：從目前位置往後掃過 N 個 `0xFF`，
把指標寫回 `word_154C0`。**字串是順序存取的，沒有隨機索引表** ——
這也解釋了為什麼在資料裡找不到字串偏移陣列。

`and 0x7F` 在目前這份資料上是 no-op：1,308 條字串沒有任何位元組帶 bit7。

### 段的佈局

`2PLAY.OVL` 的 `sub_1A85C` 給出完整佈局：從偏移 0 開始每次讀 3 個位元組，
三個都為 0 才跳出；接著讀兩個位元組組成 `skip`，用「事件表結束 + skip」
算出字串區起點（`word_1042C`），「事件表結束 + 2」是腳本區起點（`word_155BC`）。

```
事件表      3 bytes/筆，以 00 00 00 結束
uint16      skip
腳本區      事件表結束 +2 起，0xFF 分隔的變長序列
字串區      事件表結束 + skip 起，0xFF 分隔
```

事件記錄的三個欄位：

| 欄位 | 觀察 |
|---|---|
| Cell | 格位置，0–255 對應 16×16；同一段內嚴格遞增 |
| Index | 1 起算，上限與該段的事件筆數相當 —— 推定為腳本或字串序號 |
| Kind | 值都是 16 的倍數，**低 nibble 恆為 0**；高 nibble 是類型（觀察到 1–F） |

Middlegate（EVENTSI 段 0）：42 筆事件、34 條字串，第一筆事件在第 8 格。

`skip` 可以是 0（EVENTSI 段 60、EVENTSO 段 64），表示沒有腳本區、
字串區緊接事件表 —— 原版就是直接 `word_1042C = si + skip`，不做下限檢查。

### 12 段不符合這個佈局

「Kind 低 nibble 為 0」與「Cell 遞增」是從資料觀察來的一致性條件，
拿來當「這一段是不是事件表佈局」的判準。**EVENTSI 有 8/44 段、
EVENTSO 有 4/27 段不符合**，編號都偏後（63、67、65、68…）。

這些段標記成 `Irregular`：只抽字串（中文化需要），事件表與腳本區維持未解。
不硬套佈局、不猜欄位 —— 硬套會產生 `Kind=0xFF` 這種明顯不合理的記錄。

## 5. DEFAULT.DAT / ROSTER.DAT — 角色記錄

**130 bytes/筆**。`DEFAULT.DAT` = 780 = 6 × 130，六個預設角色；
`ROSTER.DAT` 8,293 bytes = 130 × 63 + 103，尾端 103 bytes 不成一筆。

### 已定位的欄位

| 偏移 | 長度 | 內容 |
|---|---|---|
| +0x00 | 10 | 名稱，空格填充，第 11 個位元組是 `00` |
| +0x0C | 1 | **性別** 0=男 1=女 |
| +0x0D | 1 | **陣營** 0=善良 1=中立 2=邪惡 |
| +0x0E | 1 | **種族** 0–4：人類／精靈／矮人／侏儒／半獸人 |
| +0x0F | 1 | **職業** 0–7 |
| +0x10 | 6 | **六個屬性**：力量、智力、性格、耐力、速度、準確 |
| +0x27 | 1 | 年齡 |
| +88 | 2 | 目前 SP（uint16） |
| +90 | 2 | SP 上限（uint16） |
| +94 | 2 | 目前 HP（uint16） |
| +96 | 2 | HP 上限（uint16） |
| +107 | 6 | 屬性的第二份 —— 受增減益影響後的當前值 |

### 職業與屬性順序怎麼定的

兩者互相定錨：`+0x0F` 在六個預設角色裡剛好是 0、1、2、3、4、5，
而每個角色屬性的**峰值都落在自己職業該高的那一項**：

| 角色 | `+0x0F` | 屬性 | 峰值 |
|---|---|---|---|
| Sir Felgar | 0 騎士 | 21,10,9,15,17,12 | 力量 21 |
| Terwin III | 1 聖騎士 | 21,10,14,15,15,10 | 力量 21 |
| Sure Valla | 2 弓箭手 | 17,16,8,19,21,12 | 速度 21 |
| Gene Eric | 3 牧師 | 12,10,20,11,18,18 | 性格 20 |
| Cassandra | 4 巫師 | 12,21,7,20,20,8 | 智力 21 |
| The Hermit | 5 盜賊 | 18,15,6,15,17,21 | 準確 21 |

六個全中。單看一個可能是巧合，六個同時對上才是證據。
寫成 `TestStatOrderMatchesClass`。

三條獨立的合理性檢驗一起通過，欄位位置才站得住：屬性都落在 3–25、
六人的 HP 都等於上限、當前屬性都等於基礎屬性（預設角色不該帶增減益）、
年齡都在 14–60。錯開一個位元組就會踩到其中一條。

### 性別、陣營、種族怎麼定的

- **性別**：`+0x0C` 為 1 的正好是 Sure Valla 與 Cassandra 兩位。
- **陣營**：`+0x0D` 為 0 的是遊俠 Terwin III 與牧師 Gene Eric，
  而手冊說**遊俠必須是善良陣營** —— 所以 0 是善良。
- **種族**：`+0x0E` 的值域 0–4，順序照手冊第 23–24 頁的選單。
  定錨靠手冊的屬性修正：半獸人「+1 力量耐力、−1 智慧人格運氣」，
  而值為 4 的 Sir Felgar 正是力量 21、智慧 10、人格 9；
  精靈「+1 智慧準確度」，值為 1 的 Cassandra 智慧 21、The Hermit
  準確度 21。六個角色的修正方向都對得上。

### SP 怎麼定的

`+88`/`+90` 只有牧師與巫師非零（各 7 點），武士、遊俠、弓箭手、賊都是 0 ——
手冊說遊俠與弓箭手要到高經驗等級才有法力，而預設角色都是第一級。

### 未解

`+0x16`–`+0x26`、
`+0x28` 之後的大片區域（技能、裝備、道具欄、經驗值、金錢）。
`Character.Raw` 原樣保留整筆 130 bytes，未解的欄位寫回時不會掉。

## 6. MONSTERS.DAT — 怪物表

解壓後 6,656 bytes = **26 × 256**。

| 偏移 | 長度 | 內容 |
|---|---|---|
| +0x00 | 14 | 名稱，空格填充 |
| +0x0E | 12 | 數值，語意未解 |

### 名稱每個位元組加了 0x80

檔案裡存的不是 `Goblin` 而是 `c7 ef e2 ec e9 ee` —— 每個位元組都加了
`0x80`。所以直接 grep 怪物名什麼都找不到，`MONSTERS.DAT` 一度被當成
「沒有字串的純數值檔」。減掉 `0x80` 之後 256 筆全部是乾淨的 ASCII，
一筆不漏。

stride 取 26 而不是 52 或 64（都能整除），依據是名稱欄位要在每筆的
同一個位置對齊：換成 52，一筆裡就會出現兩個名字。

### 排序

前幾筆是雜兵，最後五筆是四位元素領主與最終首腦：

```
[  0] Creepy Crawler   [  3] Kobold        [ 17] Orc
[251] Shalwend         [252] Pyrannaste    [253] Acwalandar
[254] Gralkor          [255] Sheltem
```

`Shalwend`／`Pyrannaste`／`Acwalandar`／`Gralkor` 正是四元素位面的
領主（事件文字裡各自喊「竟敢闖進我的位面」），`Sheltem` 是最終首腦。
排序與劇情一致，寫成 `TestMonsterAnchors`。

### 未解

+0x0E 之後那 12 個位元組。已知 +0x15 在前幾筆是遞增的小數字
（1、2、4、5…），很可能是 `MONSTERS.16` 的影像索引，待驗。
HP、攻擊力、防禦、抗性、經驗值、掉落金錢都應該在這一段。

## 7. 隨機數產生器

`sub_11C88` 是全遊戲共用的亂數來源，種子在 `ds:4A14h`（16-bit）。

```asm
mov     ax, ds:4A14h
add     ax, 9248h
ror     ax, 1  ×3
xor     ax, 9248h
add     ax, 11h
mov     ds:4A14h, ax
and     ax, 7FFFh
...
sub     cx, bx          ; cx = hi - lo
inc     cx
xor     dx, dx
idiv    cx              ; dx = 餘數
add     dx, bx          ; + lo
```

介面是 `rand(lo, hi)`，兩端都含。三個邊界處理：`hi` 為 0 時當成 1、
`lo` 大於 `hi` 時對調、範圍大小是 `hi-lo+1`。

播種在 `sub_11CCC`：`int 21h` AH=2Ch 取 DOS 時間，把 DX（秒與百分秒）
與 CX（時與分）加進種子。緊接 `sub_11C88` 之後還有一個只做
`mov ds:4A14h, ax` 的小程序，那是直接設種子用的。

**這是能重播原版行為的前提** —— 同一顆種子必然給出同一串數列，
所以 remake 用同一套算法，戰鬥、遭遇、寶物的隨機結果就與原版一致，
存檔把種子一併寫進去也能重播。實作在 `internal/game/rng.go`。
