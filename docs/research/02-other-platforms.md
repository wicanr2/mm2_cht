# 其他平台的素材：Amiga、Mega Drive、MSX

目標是讓 remake 能切換不同平台的貼圖與精靈。這一份記錄**開工前的盤點**：
每個平台的素材藏在什麼結構裡、拿得到拿不到、卡在哪。

三個平台之間沒有任何共通點 —— 檔案系統、壓縮、圖形編碼、CPU 全都不同，
所以是**三個獨立的逆向工程**，不是一件事做三次。

輸入檔的 SHA-256 見 [`docs/inventory.md`](../inventory.md)。

## 一句話結論

| 平台 | 檔案系統 | 素材拿得到嗎 | 主要障礙 |
|---|---|---|---|
| Amiga | ✅ OFS，兩片共 128 個檔（含 `libs/`）| **✅ 解完**：26 個 `.32`（388 張）＋ 72 個 `.anm` | — |
| Mega Drive | 無（ROM） | **✅ 解完**：62 個區塊、10,120 個 tile、含各自的調色盤 | — |
| MSX | **無**（自訂格式） | 未定 | 連檔案邊界都要自己找 |

## Amiga（1989，`MM2Boot`）

`Might and Magic II - Gates to Another World_Disk1.adf`，901,120 bytes
＝ 標準 880K 磁片，檔案系統是 **OFS**（開頭 `DOS\0`），根區塊在 block 880。
用 Python 直接解得開，45 個檔全部抽得出來。

### 根目錄

	程式    mm2 (181,524)  playmm2  play  run  assign  type  iconx  endcli
	圖形    intro.32 (33,228)  endgame.32 (22,473)  throw.32 (14,639)
	        book.32 (14,035)  nwcp.32 (7,977)  sky.32 (6,535)
	        introclips.32 (6,023)  globe.32 (3,034)
	動畫    23 個 `.anm`，編號 02 05 07 09 15 23 25 28 30 32 36 42 45 47
	        49 51 53 57 59 65 70 72 73
	資料    items.dat (5,120)  roster.dat (8,320)  spells.dat (256)  str.dat (7,808)
	系統    c/ devs/ fonts/ libs/ s/  diskfont.library  mm2.font

**`.16` → `.32` 是同一套命名換成 32 色**（Amiga 的 5 個位元平面）。
DOS 有 `nwcp.16`／`sky.16`／`book.16`／`globe.16`／`throw.16`／`endgame.16`，
Amiga 一個不差都在，只是副檔名換了。

### 資料檔與 DOS 的關係

| 檔 | Amiga | DOS | 關係 |
|---|---|---|---|
| `spells.dat` | 256 | 192 | **前 192 bytes 逐位元組相同**，Amiga 版在後面多接 64 |
| `roster.dat` | 8,320 | 8,293 | 60% 相同 —— 記錄結構一樣，存的角色不同 |
| `items.dat` | 5,120 | 5,120 | 長度相同、內容只有 7% 相同。兩邊都以 `Ruby Amulet ` 開頭 |
| `str.dat` | 7,808 | 4,700 | 完全不同。DOS 那份有 `1B 1E 00 00` 的位移層，Amiga 沒有 |

`spells.dat` 前 192 bytes 完全相同這一條最有價值：**兩個版本共用資料佈局**，
所以 DOS 這邊解出來的記錄結構可以直接拿去讀 Amiga 的檔，不必重解。

### Disk 2（`MM2Play`，75 個檔）

	圖形    town.32 (57,125)  cave.32 (57,205)  castle.32
	        townf/townt/townb.32、cavef/cavet.32、castlef/castlet.32
	        outdoor1-3.32、outb/outf.32、desert/ocean/swamp/tundra.32
	動畫    49 個 `.anm`
	資料    map.dat (30,720)  event.dat (95,687)  attrib.dat (3,840)
	        monsters.dat (6,656)  roster.dat  str.dat

兩片合起來 **72 個 `.anm`，編號 1–74 只缺 64 與 71**。DOS 的
`MONSTERS.16` 是 75 個槽、其中 16 個空 —— 槽數對得上（75），
但空的位置對不上（DOS 空在 6/22/27/…，Amiga 缺 63/70），
所以兩邊的編號不是同一套。

### 資料檔與 DOS 是不同的東西

| 檔 | Amiga | DOS | 前段逐位元組相同 |
|---|---|---|---|
| `map.dat` | 30,720 | 18,748 | 1% |
| `attrib.dat` | 3,840 | 1,768 | 1% |
| `monsters.dat` | 6,656 | 5,702 | 0% |
| `str.dat` | 7,808 | 4,700 | 0% |

`map.dat` **30,720 = 60 × 512** 看起來像「六十張圖各兩個 256 bytes 的平面、
未壓縮」，但四種擺法（地形在前／屬性在前／兩種交錯）拿去與 DOS 解出來的
六十張逐張比，最佳的單塊相符率只有 62.5%，沒有任何一組超過 90%。
**Amiga 版的地圖不是 DOS 那份的複製**，位元的分配也不同。

remake 用的是 DOS 的地圖，所以這件事不擋路，記著就好。

### 先確認抽對了：舊的抽取程式是壞的

**用 `tools/adf.py`**（會遞迴子目錄，並剝掉 OFS 資料區塊那 24 bytes 的標頭）。

舊的抽取只做了根目錄，而且沒有剝資料區塊標頭 —— 抽出來的檔案
**長度正確、內容從第 1 個位元組就錯**。判準是與內容無關的外部條件：
抽對的 `mm2` 開頭是 `00 00 03 F3`（Amiga hunk 檔的 magic）。

**壞掉的資料看起來完全像「壓縮過的資料」**：熵 6.4–6.7 合理、
畫成位元平面看得到疑似結構、自相關量得到穩定週期。於是那份垃圾撐得住
好幾輪的解壓實驗而不露餡。教訓寫成規則：**拿到抽出來的檔案，
先驗一個與內容無關的外部判準**（執行檔 magic、已知檔頭、
另一份獨立來源的長度），不要直接開始解格式。

被它帶偏的結論全部作廢，紀錄在 `CONTEXT.md` §5。

### `.32` 的容器：目錄在檔頭

	uint16  count      張數
	uint16  ?          場景檔是 3、sky 是 0
	count × { uint16 width, uint16 height, uint16 flag }   ← big-endian，每筆 6 bytes
	32    × uint16     調色盤，Amiga 的 12-bit RGB（0x0RGB）
	<像素資料，壓縮，編碼未解>

副檔名的 `32` 是**色數**不是張數。`tools/amiga32.py` 解得開。

尺寸與 DOS 的同名檔逐張對得起來（同一批美術），高度少 1–3：

| | 正牆深度 0–3 | 左側牆 | 右側牆 | 補牆 |
|---|---|---|---|---|
| DOS `TOWN.16` | 160×92 96×56 48×28 16×10 | 24×120 32×94 24×56 16×28 | 同左 | 24×92 ×2、56×56 ×2 |
| Amiga `town.32` | 160×92 96×55 48×27 16×10 | 24×118 32×91 24×54 16×26 | 同左 | 24×92 ×2、56×55 ×2 |

`sky.32` 是兩張 208×60，與 DOS 的 `SKY.16` 完全一致。
32 筆是 16 張 × 兩種變體（石牆／門），旗標欄正牆與補牆是 0、側牆是 3。

### 像素：nibble RLE 包住 5 個位元平面 —— 已解

解碼常式是 `mm2` 的 **`sub_33EF2`**；載入器 `sub_33322`（命令 16）。
`tools/amiga32.py` 的 `unrle()` 是逐行重寫，`--dump` 整批解成 PNG。

每張影像獨立編碼，輸出長度由目錄算得：

	每列字數 = ceil(width / 16)          ← 字組對齊
	每張字數 = height × 每列字數 × 5     ← 平面數在程式裡寫死 5（32 色）
	平面是**逐平面連續**，不是逐列交錯

RLE 只有兩條規則：

	高 nibble 是 0 或 F  →  重複那個 nibble（低 nibble + 1）次
	其他                 →  這個位元組就是兩個字面 nibble

**只有 0 與 15 有 run**，因為位元平面裡連續的 0 位元與 1 位元最多。
先前量到「nibble 0 與 15 各佔兩成」正是這件事的影子 —— 那個統計一直
擺在眼前，但被讀成「看起來像點陣圖所以沒壓縮」。

26 個 `.32` 全部解得開，共 388 張。**72 個 `.anm`（怪物動畫）用同一套 RLE**：
容器不同（`sub_19A30` 開檔後讀 48 bytes 標頭、1 byte 計數、再讀 `計數−1` bytes
的動畫表），但像素完全一樣。影格寬高在 `d[2]`／`d[3]`，72 個檔全部是 84×86 ——
與 DOS `MONSTERS.16` 的基準影格尺寸相同。

調色盤不在 `.anm` 裡：**場景檔的 32 格只有前 16 格有色，後 16 格是黑的**，
那 16 格留給怪物在執行時另外設。`throw.32`（戰鬥用）那份 31 格有色，
用它畫出來的顏色是對的。

`globe.32` 例外：它是防拷貝轉盤，
讀進來之後先用 `A4−0x7675` 那把 **5 bytes 的循環金鑰逐位元組 XOR**
（`sub_37D32`），解密後也不是標準容器，程式自己切割。

### 怎麼找到的（可重跑）

	tools/adf.py amiga/…Disk1.adf workplace/amiga/disk1   # 先抽對
	tools/ida.sh analyze amiga_mm2_ok                     # IDA 認得 hunk 格式

錨點鏈：`dos.Read` 的 stub（`jmp -$2A(a6)`）→ `sub_354D4` → `sub_346FE`
→ … → `sub_3117E(檔名, 緩衝, 偏移, 長度)`。**A4 = 0x3D93E**，定法是
「所有 `jsr (d16,a4)` 的目標都必須落在 DATA 段開頭那張 6 bytes 一格的
thunk 表上」—— 這個條件把候選收到只剩三個（相差 6 的倍數），
再用呼叫端推了幾個位元組的參數去分辨（`lea $C(sp),sp` 對上四個參數）。

定出 A4 之後，檔名表（`DATA:0x360F0`）的每一格就變成具名的全域變數：
`-$781A(a4)` 是 `town.32`、`-$784A(a4)` 是 `globe.32`。場景載入器
`sub_1173C` 對每個場景載四個檔，走 `sub_11622` → `sub_31F9E` →
`sub_32C24` 命令 16 → `sub_33322`。

### 反 68000：`mm2` 是標準的 Amiga hunk 檔

	tools/ida.sh analyze amiga_mm2_ok      # IDA 自己認得 hunk 格式

IDA 解出 **884 個函式**，段配置 CODE ／ DATA（`0x35940` 起）／ BSS。

**A4 = 0x3D938**：DATA 段開頭就是連結器的 thunk 表（每格 `4EF9` 加
32 位元位址），起點 `0x35940`，而 `jsr (d16,a4)` 的位移最小值是 `−0x7FF8`
—— 3,229 條呼叫的位移全部落在 6 的倍數上，與表對齊。

檔案 I/O 的整條鏈已經追出來：

	sub_3117E(檔名, buf, len, ?)   開檔→seek→讀→關檔
	  → sub_312A8  → sub_34314(C open) → sub_354BE → dos.Open
	  → sub_31302  → …               → sub_346FE  → sub_354D4 → dos.Read

`sub_346FE` 用 `muls.w #6` 索引一張 6 bytes 一筆的檔案描述子表。
`sub_357A8` 是 `LoadRGB4` 的包裝。**全程沒有 `udos.library` 的痕跡** ——
那個字串只是 `dos.library` 前面多一個 `u`（`udiskfont.library` 同理）。

還沒追到的是**誰載 `.32` 並解碼**。`sub_3117E` 的 thunk 目前只找到一個
呼叫點（存檔用的名冊寫入），與「它是唯一的開檔路徑」矛盾，
所以 thunk 與位移的對應還有一格沒對準，下一輪要先把那個對應釘死。

## Mega Drive（1991，USA/Europe）

`Might and Magic - Gates to Another World (USA, Europe).md`，786,432 bytes。
標頭正常（`SEGA GENESIS`，國內名與海外名都是 `MIGHT & MAGIC`）。

ROM 沒有檔案系統，圖形的位置與壓縮法都要自己找。做了一次熵的粗掃
（每 8 KB 算 nibble 為 0 的比例，未壓縮的 4bpp tile 通常零很多）：

	0x000000–0x032000   零 24–37%   偏向未壓縮／程式碼混雜
	0x034000–0x0A4000   零 12–18%   偏向壓縮過
	0x0A6000–0x0AA000   零  0%，只用到 8–12 種 nibble   ← 文字或表
	0x0AC000–0x0BC000   零 25–30%

**「數 nibble 為 0 的比例」這個判準在這片 ROM 上分不出東西**（整片都落在
12–37%），因為 68000 的指令裡本來就有很多 0 nibble。換一個判準才有效：

### 列相似度：找未壓縮 tile 的判準

真正的 4bpp tile 美術，同一個 tile 裡**相鄰兩列的位元組常常相同**
（色塊、漸層、平坦區）；程式碼與壓縮流不會。隨機資料的期望值約 6%。
`tools/mdscan.py` 拿這個掃，MM2 這片最高到 56.6%：

	0x0A9000  56.6%    0x097000  53.5%    0x0AC000  49.2%
	0x06D000  43.7%    0x0A8000  39.5%    0x09B000  34.7%

高分的區塊集中在 **`0x095000`–`0x0AE000`** 與 **`0x06D000`** 附近。

### `0x06DA00`：確定是未壓縮的 4bpp tile 美術

畫出來讀得到「Might」「and」「plague」這幾個字。

**判準是 ROM 裡沒有這些字串** —— `plague` 整片找不到、`Might` 只出現在
`0x00B577`（標頭區），而 `0x06D000`–`0x06E400` 抽不出任何可讀的 ASCII。
所以那是真的字形，不是 ASCII 位元組被當成像素畫出來的錯覺。

### 圖形區塊：靠調色盤找到入口，區塊頭已解

ROM 沒有圖形指標表（全檔遞增的 32-bit 位址表只有一處、10 筆，指向它自己
後面），所以入口不是指標而是**調色盤**。

Mega Drive 的色是 9-bit BGR 塞在 16-bit 裡：`0000 BBB0 GGG0 RRR0`，
也就是 `值 & 0x0EEE == 值`。隨機資料連續 16 個字全中這個遮罩的機率是
`(1/128)^16`，**命中就是真的**，不必再找旁證。`0x30000`–`0x72000` 掃出 74 組。

調色盤後面接著 16 bytes 的區塊頭：

	uint16  id           1–75 的稀疏編號（另有一個 158）
	uint32  compSize     壓縮後大小
	uint32  rawSize      解壓後大小 ＝ tiles × 32 + 2
	uint32  flagTiles    高位元組 flag（0x27/0x47/0x87/0xC7）、
	                     中間兩個位元組 tile 數、最低位元組 0
	uint16  0xF0FF       magic

`flagTiles` 是一個長字。**不能把 tile 數讀成 `+11` 的字** —— 那是奇數位址，
68000 讀字會位址錯誤，原版不可能那樣做。兩種讀法算出來的數字一樣，
錯的那個要靠「這台機器做不到」才排除得掉。

**驗收條件是 `(rawSize − 2) / 32 == tiles`**：兩個獨立欄位互相印證，
74 組裡 62 組通過，而且那 62 組的 magic 全部是 `F0FF`。這不是
「長度剛好對」那種弱證據 —— 欄位位移與換算關係要同時成立才會過。

62 組合計 **10,120 個 tile、解壓後 323,964 bytes**（壓縮後 167,828），
那就是整套 Mega Drive 素材。`tools/mdgfx.py` 列得出完整清單。

`id` 落在 **1–75**（外加一個 158），而 DOS 的 `MONSTERS.16` 正好是 75 個槽 ——
所以這批多半是怪物圖、`id` 就是槽號。等級：**強推論**，要等解得開才能逐張比對。

### 壓縮：LZSS，4096 環形緩衝，初值 0x20 —— 已解

解壓常式在 **ROM `0x29954`**，由 `jsr $C(a5)` 呼叫（A5 = `0x312`，那裡是一張
6 bytes 一格的 `jmp abs.l` 跳躍表）。`tools/mdgfx.py` 的 `lzss()` 是逐行重寫。

	ring = 0x20 × 4096      r = 0xFEE
	旗標位元組，LSB 先，1 = 字面值
	match: lo, hi 兩個位元組
	       off = lo | ((hi & 0xF0) << 4)     ← 環形緩衝的**絕對位置**
	       len = (hi & 0x0F) + 3

呼叫慣例 `decompress(src, dest)`，`src` 指的是 **`compSize` 那個欄位**。
常式讀 `4(a0)` 當輸出長度、`8(a0)` 起是位元流。解出來是
`uint16 tileCount` 接 `tileCount × 32` bytes 的 4bpp tile；DMA 進 VRAM 時
從 `dest+2` 開始搬，那 2 bytes 不進 VRAM。

**62 個區塊全部解得開**：輸出長度精確等於 `rawSize`，而且輸出的第一個字
等於區塊頭宣告的 tile 數 —— 兩個獨立來源互相印證。合計 10,120 個 tile。

	tools/mdgfx.py 'workplace/genesis/*.md' --dump workplace/gfx/md/tiles

畫出來全部是彩色的怪物精靈。

### 為什麼猜了那麼多輪都沒中

三件事，每一件都會讓「參數搜尋」全滅而且症狀看起來像「還沒試對」：

  - **偏移是環形緩衝的絕對位置，不是「往回幾個位元組」。** 兩者在資料中段
    等價，開頭不等價 —— 緩衝預先填了 `0x20`，所以串流一開始就能引用
    「還沒輸出過」的內容。用回退距離實作會在第一個 match 就越界。
  - **輸出長度在 `src+4`、位元流在 `src+8`。** 先前把 `+8` 的 16-bit 讀成
    rawSize（值一樣，因為 `+4..5` 是零），位元流起點整整差了 6 bytes。
  - **`F0FF` 不是 magic，是位元流本身。** 程式碼裡從來沒有比較過它 ——
    「全檔沒有一條指令碰這個常數」當時就已經是證據，但被當成「還沒找到」。

排除清單（每一項的驗收條件都是「輸出長度 == `rawSize`」）：Kosinski、
`MONSTERS.16` 的 nibble RLE、旗標式 LZSS 家族 192 種組合、PackBits 式
位元組 RLE 96 種、位元層級 LZSS 96 種、DOS 那套 LZW 48 種。**全滅。**
真正有效的一步是**去讀 68000**，而進入點是「哪一個 `sub_2DBA` 呼叫的來源
是 `0xFFFF0002`」—— 那個 `+2` 正好對上 `rawSize = tiles × 32 + 2`。

### 反 68000 的路徑（可重跑）

	tools/ida.sh m68k md_mm2                              # 初始 PC 在 0x200
	tools/ida.sh script ida_func.idc md_mm2.i64 29954 180  # 解壓常式

`sub_2DBA(region, vramAddr, byteLen, srcPtr)` 是 VRAM 傳輸（`region` 0/1/2 →
VRAM 0x4000／0xC000／0x104000），`sub_2D12` 是 VDP 初始化。
**IDA 會把 `0x312` 那張跳躍表解錯**（把 `jmp` 的位址切成 `ori.b` 之類），
要直接讀原始位元組：每格 `4E F9` 加 32 位元位址。

## MSX（1989，Starcraft 日版）

四個 `.dsk`，每片 737,280 bytes（Disk 1／2 各含一個 `[a]` 版本）。

**這片磁碟沒有檔案系統。** 開機磁區有看似 BPB 的欄位
（512 bytes/磁區、2 磁區/叢集、FAT 2 份 × 3 磁區、根目錄 112 項），
但照那組參數算出來的根目錄位置（`0xE00`）**整段是 0**，
而且整片磁碟 grep 不到任何 `XXXX.BIN` 形狀的檔名。

所以那組 BPB 是裝樣子的，實際是**自訂格式**：開機磁區載入自己的載入器，
資料按裸磁區位置讀。要取素材就得先反 Z80 的載入器，把「哪個磁區放什麼」
整張表找出來。三個平台裡最貴的一個。

## 難度排序與前置條件

1. **Amiga** —— 兩片的檔案系統都已解，117 個檔全部抽得出來。
   只缺一件事：`.32` 的編碼（反 `mm2` 的 68000 碼，IDA 載得進去）。
2. **Mega Drive** —— `0x06DA00` 那一段確定是未壓縮的 4bpp tile
   （`tools/mdscan.py` 的列相似度判準找到的）。其餘要在 768 KB 裡找到
   圖形表與解壓程序，全靠反 68000。沒有前置條件，但沒有捷徑。
3. **MSX** —— 連「檔案在哪裡」都要先解出來。

## 不要重複走的路

- **不要拿 `tools/mm2lzw.py` 去試 `.32` 或 ROM。** DOS 的 LZW 有明確的
  檔頭與 CLEAR 起始碼，兩者都沒有；試了會得到「解不出來」這個沒有資訊的結果。
  **改成 MSB-first 也一樣**（大端機器會這樣寫是合理的猜測，但實測不成立）。
- **不要再拿新的位元組擺法去猜 `.32` 的像素編碼。** 已經排除的清單見
  §「像素的編碼」那張表，涵蓋 LZW 兩種位元序、nibble RLE、chunky 4bpp、
  3/4/5 平面 × 兩種對齊 × 兩種交錯 × 24 個起點。**回饋迴圈是「畫出來看」，
  每一輪都便宜，所以很容易一直試 —— 但那是抽樣不是實驗。** 缺的是解碼器。
- **不要用「熵不夠高」推論「沒壓縮」。** `.32` 的熵是 6.4–6.7 bits/byte，
  看起來像點陣圖，實際是壓縮流 —— 位元組對齊的 LZ／RLE 本來就達不到 8。
  判準要用**壓縮率隨素材浮動**（`town.32` 4.84 bit/px、`globe.32` 遠低於此），
  那是固定位元深度給不出來的。
- **不要靠「A4 相對定址命中字串」去驗證 A4 的值。** 定址窗有 64 KB，
  隨便一個 A4 都會有一堆位移落在某個字串裡；看起來像「逐字精確命中」。
  要驗就驗**結構**：`jsr (d16,a4)` 的位移全是 6 的倍數、最小值定出表頭，
  再回檔案裡找那張 `jmp abs.l` 表。
- **不要假設 Amiga 的 `map.dat` 是 DOS 那份的未壓縮版。** 大小剛好是
  60 × 512 很誘人，但四種擺法都對不上（最佳 62.5%，無一超過 90%）。
- **不要用 `.16`／`.32` 的副檔名去推格式相同。** 命名是同一套，容器不是。
- **不要假設 MSX 的 BPB 有效。** 那組參數看起來合法但指向空白。
- **不要用「nibble 為 0 的比例」找 Mega Drive 的美術。** 68000 的指令裡
  本來就有很多 0 nibble，整片 ROM 都落在 12–37%，分不出東西。用列相似度。
- **參數搜尋全滅時，先懷疑「框架」不是「參數」。** Mega Drive 那套花了
  五族、四百多種組合都沒中，原因不在演算法選錯（就是最普通的 LZSS），
  而在三個框架級的誤解：偏移是環形緩衝的絕對位置不是回退距離、輸出長度
  的欄位位置差了 4 bytes、被當成 magic 的 `F0FF` 其實是位元流。
  **「全檔沒有一條指令碰這個常數」當時就已經是證據**，卻被讀成「還沒找到」。
- **LZSS 這類解碼器不會失敗**，餵什麼都吐得出東西，而且因為輸出來自環形
  緩衝，統計上看起來永遠像點陣圖（熵低、有長 run）。所以**不能拿「輸出
  看起來合理」當驗證**，要有宣告長度之類的獨立條件。Amiga 的 `.32` 就是
  這樣：用 Mega Drive 那套 LZSS 解得出 104,580 bytes 的低熵資料，
  但那個長度對不上任何平面配置，所以不是。
- **不要用「列相似度高」推論「未壓縮」。** `0x095000`–`0x0AE000` 在這個判準上
  拿 22–56%，實際是壓縮流裡的長平坦段。列相似度**只能拿來排序候選**，
  下結論要用能驗收的東西（能不能解出宣告的長度、畫出來認不認得）。
- **判讀函式庫呼叫前先確認基底暫存器裝的是誰。** 同一個 LVO 位移在不同
  函式庫是不同的函式（`-552` 配 ExecBase 是 `OpenLibrary`、配 graphics 是
  `LoadRGB4`）。認錯會往整個錯的方向追一輪。
- **看到 ROM 裡「畫出來像文字」的東西，先確認那不是 ASCII。** 位元組被當成
  像素畫出來時人眼很會腦補；`0x06DA00` 那一段之所以確定是字形，
  是因為 `plague` 這個字在整片 ROM 的位元組裡找不到。
