# Mega Drive 的音樂驅動：命令介面與觸發點

這份記錄音樂驅動的機制：命令介面、播放入口、曲目資料格式與防竄改。
「哪一首配哪一個場景」在 [`md-music-scenes.md`](md-music-scenes.md)。
通用方法論（含其他遊戲也適用的找法與坑）在
`~/.claude/knowledge-base/retro/megadrive-vgm-music-extraction.md`。

輸入：`Might and Magic - Gates to Another World (USA, Europe).md`，786,432 bytes，
SHA-256 `d86b6d7381ef67ecb5391eddb6857bf9d15b1e402da6bfc42cb003186599cbff`。
位址是 IDA Pro 9.4 載入 `md_mm2` 後的 ROM 位址空間（`tools/ida.sh m68k md_mm2`）。

## 架構：68000 指揮、Z80 演奏

68k 搶下 Z80 匯流排（寫 `$100` 到 `$A11100`）、動 Z80 RAM（`$A00000` 起）、
再放掉（寫 `0`）。取匯流排的兩支常式：

| 位址 | 做什麼 |
|---|---|
| `sub_AF2C0` | `sr = $2700`（關中斷）→ 請求匯流排 → `a0 = $A00000` |
| `sub_AF296` | 同上的另一個版本（`AF2DA`／`AF2FA`／`AF316`／`AF326` 呼叫）|

所以程式碼裡的 `$A(a0)`／`$B(a0)` 就是 Z80 RAM 的 `$A0000A`／`$A0000B`。

## 命令介面（已證實）

| 位址 | 語意 | 證據 |
|---|---|---|
| `$A0000A` | 參數／曲目編號。`$FF` = 停止 | `AF2E2` 寫變數 `d1`；`AF2FC` 寫 `#$FF` |
| `$A0000B` | 命令。`$0D` = 播放剛上傳的資料、`$12` = 另一種播放、`$00` = 停 | `AF264`／`AF31A`／`AF338` |
| `$A000DA` | 資料上傳的頁號，實測固定 `$16` | `AF3E4` |
| `$A000E6` | 每次 vblank 遞增的同步計數器，**不是曲目編號** | `AF154`，值來自 `-$37D2(a5)` 的高位元組 |
| `$A01600` | 曲目資料的上傳目的地，每次 `0x400` bytes | `AF3E4` 的 `a2` 與 `move.w #$3FF,d0` |

## 真正的播放入口是 `sub_AF23A`

```
AF23A  bsr.s  sub_AF1C2          ; d0 ← 曲目資料指標
AF240  move.l d0,-$37C8(a5)
AF252  bsr.w  sub_AF3E4          ; 把 0x400 bytes 搬進 Z80 RAM $A01600
AF264  move.b #$D,$B(a0)         ; 命令：播放你手上那份
AF26A  move.b #0,$A(a0)
AF27E  st     -$37DA(a5)         ; 標記「正在播」
```

**這個遊戲換曲是「上傳資料」不是「傳編號」。** 命令位元組只說「播放剛送過去的那份」，
所以**選曲發生在 `sub_AF1C2` 回傳的指標**，不在命令介面。

`sub_AF23A` 的六個呼叫端（IDA xref）：

	06CB1C  06CB42  06CB94  06CBE2   level_6_interrupt_autovector_entry（vblank）
	0AF55E  0AF574                   驅動內部

`sub_AF136` 是 vblank 的音樂更新（遞增 `$A000E6`、每 16 次呼叫 `sub_AF378`），
指標放在 `0x6CBF0`。

## 負面結果：五個 API 入口沒有任何呼叫者

| 位址 | 做什麼 | 呼叫者 |
|---|---|---|
| `AF2D4` | 寫 `d1` 到 `$A0000A`（不設命令） | **0** |
| `AF2F6` | 寫 `$FF`（停止） | **0** |
| `AF310` | 設命令 `$12` 再寫 `d1` | **0** |
| `AF322` | 設命令 `$12` 再寫 `$FF` | **0** |
| `AF332` | 設命令 `$00` | **0** |

零命中同時經過兩種獨立方法確認：IDA 的 xref 圖（`tools/ida_xrefs.idc`），
以及對整片 ROM 掃 `bsr.s`／`bsr.w`／`jsr (d16,pc)`／`jsr abs.l`／`jmp abs.l` 五種呼叫形式。
四個位址的 32-bit 值在整片 ROM 裡連出現一次都沒有。

**正對照通過**：同一支掃描器對 `sub_AF296` 與 `sub_AF2C0` 各掃出 4 筆，
與 IDA 的 xref 完全相同。所以零是真的零，不是掃描器有洞。

推論：這五支是**連結進來的音樂函式庫的 API，這個遊戲沒有用到**。
等級 `強推論` —— 「函式庫帶了沒用到的入口」解釋得通，但沒有獨立證據。

## 曲目資料：18 首，靠結束指標自我描述

**每首曲子的前 4 bytes 是它的結束指標**（`sub_AF23A` 的 `move.l -4(a0),-$37C4(a5)`）。
這條結構條件足以在整片 ROM 裡把曲目掃出來：起點 `S` 要滿足 `u32[S-4] = E`、
`S < E`、大小合理，而且開頭是聲部設定樣式 `00 Cn ...`。

掃出來的 18 首全部落在 `0x0AF59C`–`0x0BF438`：

| 曲目 | 大小 | 曲目 | 大小 |
|---|---|---|---|
| `0x0AF59C` | 7,680 | `0x0B9718` | 512 |
| `0x0B1370` | 4,096 | `0x0B9888` | 512 |
| `0x0B2290` | 9,984 | `0x0B9A04` | 3,072 |
| `0x0B48D4` | 6,144 | `0x0BA608` | 2,304 |
| `0x0B60CC` | 512 | `0x0BAE7C` | 1,792 |
| `0x0B61DC` | 512 | `0x0BBF68` | 2,816 |
| `0x0B8224` | 1,792 | `0x0BC990` | 1,792 |
| `0x0B885C` | 768 | `0x0BD078` | 4,608 |
| `0x0B8AE0` | 3,328 | `0x0BE238` | 4,608 |

另有 `0x06CC00`（1,280 bytes），內容是八個聲部設定後接連續的 `80`（休止）——
**音樂關閉時播的空曲**，`sub_AF340` 回報驅動閒置時也會重新送它。

四首 512 bytes 的短曲（`0x0B60CC`、`0x0B61DC`、`0x0B9718`、`0x0B9888`）
是提示音。**用途由反組譯定出來，不是由長度猜的**：見
[`md-music-scenes.md`](md-music-scenes.md)。

## 選曲：一支分派函式，不是指標表

18 首**全部**由 `0x0B680`–`0x0B830` 這一段設定，慣用句是：

```
1B 7C 00 01 C8 48    move.b #1,-$37B8(a5)        ; 要求淡出
59 8F                subq.l #4,sp
2E BC 00 0B 82 24    move.l #$000B8224,(sp)      ; 這一首
2B 5F C8 50          move.l (sp)+,-$37B0(a5)     ; 寫進「要播哪一首」
60 00 01 96          bra.w  <共同出口>
```

`move.l (sp)+,-$37B0(a5)`（`2B 5F C8 50`）在整片 ROM 出現 **18 次**，
每一次前面都是 `move.l #<曲目位址>,(sp)`，**零例外**；每個位址的 `-4`
都有合法的結束指標。兩個獨立條件同時成立，所以這 18 個就是完整的曲目集合。

vblank 的音樂管理（`0x6CB22` 起）比較 `-$37B0`（要播）與 `-$37B4`（正在播），
不同就先寫 Z80 驅動裡的兩個音量欄位（`$A0086E`、`$A007A7`）做淡出，
再呼叫 `sub_AF23A` 換曲。

**這 18 首是本專案自己解出來的**，不依賴 VGMRips 那份 16 首的外部清單。
兩邊數字不同（18 vs 16）的原因也解出來了：其中兩首（`0x0BAE7C`、`0x0B60CC`）
在整片 ROM 裡沒有任何呼叫端，這個移植版沒有用到。

### 呼叫端：直接呼叫只佔四分之一

`sub_B620` 是 `link a6,#0` 的 C 風格函式，參數在 `$8(a6)`（`move.w $A(a6),d0`
取的是那個長字的低位字）。呼叫端的樣式是 `moveq #N,d0` 接 `move.l d0,-(sp)`，
所以 case 值讀得出來。

**全部 39 個呼叫端：11 個直接 `jsr`／`bsr`，28 個走 a5 thunk（位移 558）。**
只掃直接呼叫會得到「21 個 case 只有 7 個被用到」這個錯誤結論。
完整的 case → 曲目 → 場景見 [`md-music-scenes.md`](md-music-scenes.md)。

### case 19 的分支變數：`-$4C6(a5)`（RAM `$FFFE4C`）

case 19 依它在四首之間分支，而它的值是 **`sub_FB86(地圖編號)`** ——
一張地圖編號的區間查表（`0x0FB86`）。所以 case 19 是**區域音樂**。

窮盡掃描（任何指令只要延伸字是 `0xFB3A`）得 **22 個讀取、3 個寫入**：

	0x00455A、0x004754   move.b #7,-$4C6(a5)
	0x010F14             move.b d6,-$4C6(a5)   ← d6 = sub_FB86(地圖編號)

`0x010F14` 與 case 19 的呼叫端 `0x010FDA` 在同一支函式（`sub_10E56`，進入地圖）裡：
先算區域類型，函式結尾才要求音樂。

**只掃 `move.b dN,X` 這幾種形式會得到「零個寫入」**，
一定要掃「延伸字等於該位移的所有指令」。

### 一個被推翻的誤讀

`sub_AF1C2` 不是選曲，是**驅動初始化** —— 偵測 PAL/NTSC（`($A10001)` bit 6，
結果寫 `-$37D4(a5)`，`AF13A` 據此每幀多加 `$33` 補時脈差），然後把 ROM `0x0ADBDA`
起的 **5,513 bytes Z80 驅動程式**搬進 `$A00000`。那段 blob 開頭是
`21 FF 1F` `F9` `C3 7D 01`（`ld hl,$1FFF` / `ld sp,hl` / `jp $017D`）接一串
`ED 4D`（`reti`）中斷向量，是貨真價實的 Z80 程式。它會還原 `d0`，
所以曲目指標是**呼叫端傳給 `sub_AF23A`** 的，不是它算出來的。

## 對擷取的意義

**記錄與轉檔那一半已經完成並驗證**（見 [`../music.md`](../music.md)）：
`tools/blastem_run.sh` 從 ROM 一路走到音樂包可以直接吃的 WAV，
四個環節各有獨立的量測面。

觸發點本身很清楚：vblank 的音樂管理只看 `-$37B0(a5)`，把它寫成任一個曲目位址，
下一次 vblank 就會淡出舊曲、換播新曲。

	a5 = 0x312，所以 -$37B0(a5) 的實體位址是 RAM $FFCB62（32-bit）

**但不能靠改 ROM 達成 —— 這片有防竄改停機。** 見下一節。

## 防竄改：改 ROM 就開不了機（已證實）

實測矩陣，全部同一個 timeline（開機 5–8 秒後截圖，錄 15–20 秒）：

| ROM | 畫面 | VGM |
|---|---|---|
| 原版（複製到另一個檔名） | 8 秒有畫面（8,995 bytes PNG） | 126,817 bytes |
| 只改 `0x0BFFFF`（尾端 padding 的最後一個位元組） | 正常 | 126,823 bytes |
| 只改 `0x0B5E1`（`Initialize Game` 字串的一個字母） | **5 秒起全黑** | 711 bytes |
| 只改 `0x0BE300`（曲目資料中間一個位元組） | **全黑** | 711 bytes |
| 只改 `0x06CB10`（vblank 閒置路徑的立即值，4 bytes） | **全黑** | 711 bytes |
| 改 18 處選曲立即值 | **全黑** | 711 bytes |

**一個純文字位元組不可能讓遊戲當掉**，所以這不是「改壞了某段邏輯」，
是**開機時的完整性檢查**。補正檔頭 checksum（`0x18E`，原值 `0xDB5E`）沒有用，
所以它不是檢查那個欄位。尾端 padding 改了沒事，代表檢查範圍不涵蓋 ROM 最末端。

711 bytes 的 VGM 是驅動初始化時送出的聲部設定，不是音樂 ——
**「有 VGM 產出」不等於「遊戲有在跑」**，要看截圖才分得出來。

檢查本身還沒找到。掃過「循序讀 ROM 累加」的迴圈（`add.w (aN)+,dM`、
`move.w (aN)+,dM` 配 `dbf`，字組對齊）只有 6 個候選，逐一看過都是繪圖或堆疊操作，
不是校驗。所以它可能不是單純的加總（CRC、抽樣比對、或分散在多處）。

## 逐首觸發：走 GDB stub，ROM 一個位元組都不改（已實作）

BlastEm 的原生除錯器在容器裡用不了：它靠 `/opt/blastem/termhelper` 另開一個
終端機視窗，headless 環境沒有終端機，於是 `-d` 靜默地不進除錯器
（stdin 餵命令沒有任何回應，管道與 pty 都試過）。

可行的是 **GDB remote stub**：`blastem ROM -D` 直接在 stdio 上講 GDB RSP，
不需要終端機。實作在 `docker/blastem/music_dump.py`，流程：

1. stub 停在進入點（`?` 回 `S05`，PC = `0x200`）。
2. `Z0,6cb02,2` 在 vblank 的音樂管理下軟體中斷點。
3. 每次命中就 `M ffcb62,4:<曲目位址>`，連壓 40 幀 ——
   原版每幀把音量減 2、從 `$B0` 降到 `$58` 要 44 幀，壓不夠換曲不會完成。
4. **趁還停著讀回 `$FFCB5E`（正在播）驗證已經切過去**，不符就中止。
5. `z0` 移除中斷點、送 `$c#63` 放行，這時才用 `m` 熱鍵錄 VGM。

四個實作上的坑（每一個都會靜默失敗）：

- **第一次 `cont` 要等 8.5 秒**（開機到第一次 vblank 音樂管理），
  之後每幀約 0.1 秒。逾時設 5 秒會在第一幀就放棄。
- **放行要送合法封包 `$c#63`，不能寫裸的 `c` 位元組** ——
  裸位元組被 stub 忽略，模擬器一直停著，症狀是熱鍵沒反應。
- **BlastEm 的 stub 不回應 raw `0x03` 非同步中斷**，送了會永遠等不到回覆。
  所以驗證只能在放行前做。
- **停在中斷點時模擬器不處理視窗事件**，`m` 熱鍵送不進去，
  一定要先移除中斷點再錄。

另一條沒走的路是找出並停用完整性檢查；不需要了，因為不改 ROM 就不會觸發它。

**18 首全部錄出來並確認場景對照之前，不得宣稱已有完整包。**
