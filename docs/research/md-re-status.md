# Mega Drive 逆向：現況與缺口盤點

這份是 Mega Drive 版逆向的**單一狀態入口**。細節分散在
[`02-other-platforms.md`](02-other-platforms.md)（圖形與畫面）、
[`md-music-driver.md`](md-music-driver.md)（音樂機制）、
[`md-music-scenes.md`](md-music-scenes.md)（曲目與場景）。

輸入：`Might and Magic - Gates to Another World (USA, Europe).md`，786,432 bytes，
SHA-256 `d86b6d7381ef67ecb5391eddb6857bf9d15b1e402da6bfc42cb003186599cbff`。

**這個版本在專案裡的定位是「素材與音樂來源」，不是要重現的行為 oracle**
（DOS 版才是，見 `CLAUDE.md` §1 的裁決順序）。所以下面的缺口都不阻擋交付，
排序依據是「補起來能讓 remake 多出什麼」。

## 已解出的

| 領域 | 狀態 |
|---|---|
| ROM 結構、標頭 | 產品碼 `T-50`（Electronic Arts），1991.JUL |
| 基底暫存器 `a5 = 0x312` | 已證實。148 筆 `jmp abs.l` 的 thunk 表 |
| 壓縮 | LZSS（常式在 `0x29954`），4096 環形緩衝、初值 `0x20` |
| 圖形區塊 | **334 個 LZSS 區塊**（`tools/mdlzss_scan.py`，不靠任何前綴）：79 個是 tile（12,682 個），其餘是 blitter 用的點陣圖。舊方法只找到 72 個 |
| 未壓縮美術 | `0x06DA00` 起的 4bpp tile（含字型）|
| VDP 與畫面結構 | plane A/B 位置、sprite 表、64×64 cell；開機用 CPU 寫、遊戲中走 DMA |
| 畫面更新方式 | **換的是 tile 的圖案不是 tilemap** —— nametable 開機擺好就不動 |
| 第一人稱繪製鏈 | `sub_FC38(區域類型)` 建表 → `sub_3DE2` 逐格 blit 進 `0xFF0000` → DMA |
| 三個 RAM 組合緩衝區 | `0xFF0000`（DMA 來源）、`0xFF3400`、`0xFF4400`（64 word 一列的格子陣列）|
| 音樂驅動 | Z80 blob 在 `0x0ADBDA`（5,513 bytes）；命令介面 `$A0000A`／`$A0000B`；串流環形緩衝 `$A01600` |
| 曲目資料 | 18 首，靠「起點前 4 bytes 是結束指標」自我描述 |
| 選曲 | `sub_B620` 跳表 switch，21 個 case，39 個呼叫端（28 個走 thunk）|
| 曲目 → 場景 | 16 個音樂角色全部對應完成，對到 16 首不同曲子；11 個已證實（四個區域主題 ＋ 五個設施 ＋ 旅店 ＋ 戰鬥）|
| 動態追蹤 | GDB stub 下中斷點 ＋ 真實時間按鍵腳本 ＋ 截圖（`tools/md_trace.sh`）；走法由 `tools/md_town_route.py` 從 DOS 版地圖 BFS 算出；長路徑用 `md-walk` 依 SP 判斷狀態自動清 modal |
| 逐首擷取 | GDB stub 指定曲目、錄 VGM、轉標準 PCM WAV，18 首零失敗 |
| 隊伍狀態（RAM）| X `0xFFF3A4`、Y `0xFFF3A6`、朝向 ASCII `0xFFF3B4`；`0xFFF3A8`–`B2` 是 `sub_F5CE` 那四組牆遮罩／位移 |
| 角色記錄（RAM）| `0xFFCE9F` 起、每筆 **134 bytes**；`+00` 目前 HP、`+02` 生命上限、`+16` 另一個上限 |
| 防竄改 | `sub_BFC28`：ROM `0`–`0xBFC28` 的 32-bit 長字加總要等於 `0x3ACE1FBA`，跳過 `0x18C`（標頭 checksum 欄位）。不符就進死迴圈 |

## 缺口（依「補起來的價值」排序）

**下面五項在 2026-08-14 全部解完，這份清單目前沒有未解項目。**
保留內容是因為每一項的「為什麼先前走不通」比結論本身更容易重犯。

剩下標**強推論**而非已證實的，是戰鬥結算的五個音樂角色
（`victory`／`enemy_killed`／`member_killed`／`defeat`／`treasure`）。
`battle` 已經在地城拿到了；擋住其餘五個的是「要把仗打完」——
戰鬥驅動與無敵都做好了，卡在**選擇標記移不到 `Attack`**，見第 6 節。

### 1. 第一人稱視角的繪製鏈 —— 已解完

整條鏈從地圖資料一路接到畫面：

	地圖位元組 ──sub_F5CE 依朝味取 2-bit 欄位──▶ -$F48(a5) 每格要畫什麼
	                                              │
	sub_FC38(區域類型) 建表 $FFCD40 ──────────────┤
	                                              ▼
	                             sub_3DE2 逐格 blit 進 0xFF0000
	                                              ▼
	                                   sub_42FC / DMA 進 VRAM

- **選牆的貼圖與選音樂是同一個變數**（`sub_FB86(地圖編號)` 算出的區域類型）。
- 朝向用 ASCII `'N'`／`'S'`／`'E'`／`'W'`，四組遮罩位移
  `(0xC0,6)`／`(0x30,4)`／`(0x0C,2)`／`(0x03,0)` 與 DOS 版完全相同。
- 視野貼圖是 LZSS 壓縮的**點陣圖不是 tile**，檔頭在 `src-4`（寬）與 `src-2`（高），
  驗收條件是 `寬 × 高 == rawSize`。`tools/mdview.py` 85 張全部解得開，
  畫出來是磚牆，每個區域類型固定 8 張（正面全景／近側牆／中距／遠距）。

細節見 [`02-other-platforms.md`](02-other-platforms.md)。

**這一項不再是缺口。** 要把 MD 的第一人稱接進 remake 只剩工程工作
（照 `-$F48(a5)` 的規則選圖、按尺寸貼），不需要再逆向。

### 2. 設施的場景對照 —— 已解完（走進去量的）

在 Middlegate 逐一走到每個設施的入口格，`sub_B620` 下中斷點，
記下 `d0`（case）與回傳位址（呼叫端），每一筆都配一張店內截圖：

| 設施 | 入口格 | case | 呼叫端 |
|---|---|---|---|
| Middlegate Inn | (7, 3) | 11 | `0x18BCA` |
| S. J. Blacksmith | (4, 4) | 13 | `0x189B8` |
| Slaughtered Lamb（酒館）| (4, 6) | 14 | `0x1AA48` |
| Gateway Temple | (7, 7) | 15 | `0x1B94A` |
| Sleepy's Mage Guild | (7, 14) | 15 | `0x19D26` |
| Turkov's Training | (10, 7) | 16 | `0x1966C` |

神殿與法師公會共用 case 15，兩個不同呼叫端 —— 靜態字串錨點
（`been healed!` 與 `Learn which?` 混在一起）看起來曖昧就是這個原因。

事件腳本的 `0e NN` 是設施編號，Middlegate 六個入口把 `0e 01`–`0e 06` 用滿。
`0e 07` 以上（技能商店、Brain Detoxification）實測都不換曲。

同一輪也確認了印字函式的參數格式：

	md-trace rom.md --break 0x73FC:印字 --arg-str 0
	→ '\x0cLicensed by:'   '\x19New World Computing, Inc.'

**文字是 Pascal 式長度前綴**：第一個位元組是長度。先前的統計只中 14%，
是因為比對的是 NUL 前一個位元組而不是字串的第一個位元組。

#### 動態追蹤的四個坑（都靜默失敗，畫面一切正常）

1. **送鍵要走 XTEST，不能加 `--window`。** `xdotool key --window <id>` 是
   XSendEvent 合成事件，BlastEm 的**手把輸入**收不到（UI 熱鍵如 `m` 反而收得到
   —— 所以「VGM 錄得到」不能拿來證明按鍵有效）。
2. **按住的時間要落在窄區間。** `xdotool key` 的按下與放開幾乎同時，
   遊戲每幀只 poll 一次就整個漏掉；按 ≥0.15 秒又會被選單當成長按重複觸發，
   勾選被切兩次等於沒按。**0.08 秒**實測穩定。
3. **確認鍵是 C 鈕（`d`）不是 Start。** 而 `z` 不是 A 鈕，是 `ui.sms_pause`
   —— 按下去畫面照樣跑，看起來像「按了沒反應」，實際上按到了模擬器的暫停。
   按鍵對應要看 `/opt/blastem/default.cfg`，別憑印象。
4. **按鍵腳本靠計時推進，在 GDB stub 底下會漂移**（停在中斷點時模擬器時間凍結）。
   所以導航只走一次、用 `key:grave` 存成模擬器狀態檔，之後每次追蹤
   用 `key:l` 載回來 —— 開機到城鎮從 75 秒降到 9 秒，而且完全可重現。
   查詢型 case（每幀都呼叫）要用 `--ignore-d0` 濾掉，否則每次停下都是一輪
   RSP 往返，會把模擬拖慢到按鍵腳本失準。

判準：送 `Down` 看選單游標有沒有移動，而且**只移動一格**。

#### 為什麼靜態走不通（記錄，不必重試）

`sub_73FC(字串, x, y, 旗標)` 是印字函式，326 個呼叫端（133 直接、193 走 thunk
位移 474）。四項掃描結果：

| 檢查 | 結果 |
|---|---|
| 全 ROM 有沒有字串指標表（連續 ≥3 個 32-bit 字串位址）| **0 張** |
| 32-bit 字串位址在整片 ROM 出現幾次 | **14 次** |
| 散文字串被 `(d16,PC)` 定址直接引用（窮盡掃所有該定址模式）| **33 / 377（9%）** |
| 呼叫 `sub_73FC` 前一個指令 | 146 個是 `move.l d0,-(sp)` —— 指標是算出來的 |

多數印字走的是「先把文字格式化進 RAM 緩衝區，再印那個緩衝區」，
所以「這支函式引用了這條字串」的靜態關係不存在。

### 3. 完整性檢查在哪 —— 已解完：`sub_BFC28`

**是硬體初始化之後的第一個 `jsr`。** reset 進入點 `0x200` 跑完 Sega 的標準
開機序列，`0x2FA` 起就是：

	0002FA  tst.w   ($C00004).l
	000300  jsr     sub_BFC28        ← 完整性檢查
	000306  nop
	000308  jmp     loc_6C9AA        ← 通過才進遊戲

常式本體只有 36 bytes：

	BFC28  moveq   #0,d0            ; 累加值歸零
	BFC2A  suba.l  a0,a0            ; 從 ROM 位址 0 開始
	BFC2C  move.l  #$2FF0A,d1       ; 196,362 個長字
	BFC32  cmpa.w  #$18C,a0         ; 走到 0x18C？
	BFC36  bne.s   loc_BFC3C
	BFC38  addq.w  #4,a0            ;   是 → 跳過不計
	BFC3A  bra.s   loc_BFC3E
	BFC3C  add.l   (a0)+,d0         ;   否 → 加進累加值
	BFC3E  subq.l  #1,d1
	BFC40  bgt.s   loc_BFC32
	BFC42  cmpi.l  #$3ACE1FBA,d0    ; 期望值
	BFC48  bne.s   loc_BFC4C
	BFC4A  rts                      ; 相符 → 正常開機
	BFC4C  …                        ; 不符 → 設 VDP、填色、bra 自己（死迴圈）

三件事一次解釋了先前所有的觀察：

- **涵蓋範圍是 ROM `0x000000`–`0x0BFC28`**（196,362 × 4 = 785,448 = `0xBFC28`）
  —— 剛好到檢查常式自己為止。**尾端 padding 不在裡面**，所以改它沒事。
- **`0x18C` 那個長字被跳過**，它的後半就是 MD 標頭的 checksum 欄位
  （本片是 `DB5E`）。所以**補正標頭 checksum 沒有用** —— 它根本不參與。
- 不符時走的是 `bra.s` 自己的死迴圈，主迴圈永遠不會開始，畫面全黑。

**三層驗證**（每一層互相獨立）：

| 層 | 做法 | 結果 |
|---|---|---|
| 離線計算 | 用 Python 照同一套規則掃 ROM | `0x3ACE1FBA`，與常式裡的立即值逐位元相同 |
| 執行時觀察 | 在 `0xBFC42` 下中斷點 | `d0=3ACE1FBA`、`d1=0`、回傳位址 `0x306`（正是 `jsr` 的下一行）|
| 正對照 | `--poke 1000=<原值+1>` 只改**模擬器記憶體**，ROM 檔不動 | `d0=3ACE1FBB`（差 1）→ 走死迴圈 → 截圖全黑 |

重跑：

```bash
tools/ida.sh script ida_func.idc md_mm2.i64 BFC28 200      # 靜態
tools/md_trace.sh /out/crc.txt --break 0xBFC42:比對 --max-hits 1
tools/md_trace.sh /out/crc.txt --break 0xBFC42:比對 --max-hits 2 \
  --poke 1000=<原值+1> --keys "wait:20;shot:crc-bad"       # 正對照
```

#### 為什麼先前掃不到（記錄，不必重試）

先前掃的樣式是「循序讀 ROM 累加」的迴圈：`add.w (aN)+,dM` 或
`move.w (aN)+,dM` 配 `dbf`，字組對齊。**兩個前提都錯**：實際是
**長字**累加（`add.l`），而且迴圈終結用的是 `subq.l #1,d1` ＋ `bgt`
**不是 `dbf`**（`dbf` 的計數上限是 16-bit，這裡要數 196,362 次，用不了）。

真正走通的路不是樣式掃描，是**從 reset 進入點往下讀**。
那是有界的工作量（第一個 `jsr` 就是），而樣式掃描的搜尋空間沒有邊界。

### 4. case 11（`0x0BA608`）是哪一個設施 —— 已解完：**旅店**

走進 Middlegate (7,3) 的旅店入口，`sub_B620` 命中 `d0=0x0B`、呼叫端 `0x18BCA`
（與靜態預測的位址完全吻合），畫面是「A jolly old innkeeper... Will you sign
the registry?」。離開時 `0x17468` 送 case 19 把區域音樂放回去。

這同時推翻了「原版進旅店不換曲」：那個結論的依據是「`Leave the Inn` 字串
所在的 `0x28xxx` 一區沒有選曲呼叫端」，但那一區是**旅店的名冊畫面**，
從城裡走進旅店入口跑的是設施處理區的另一段。
**「某個字串附近沒有呼叫端」推不出「這個場景不換曲」** —— 字串與呼叫端
本來就可以在不同的函式裡。

### 5. 野外導航 —— 已解完：狀態驅動的走路器

城鎮那六個設施走得完，是因為路徑短（最長 18 個按鍵）而且**中途不會跳訊息**。
野外不一樣：幾乎每走幾格就有招牌、事件或旁白，一跳出來後面的按鍵全被吃掉。
而**沒有一個按鍵在兩種狀態下都安全**：

| 狀態 | 按 `d`（C）| 按 `s`（B）|
|---|---|---|
| 有對話框（`"C" to Continue`）| 清掉，繼續 | 沒有作用 |
| 沒有對話框 | **開啟指令選單** | 沒有作用 |

選單一開，後續方向鍵變成選單導航、`d` 變成選項確認。實測跑 30 次 `Up;d`
的結果是隊伍一步沒走，最後停在 View Char 的改名對話框。指令選單也**不是按
`s` 關掉的**，要選到最後一項 `Cancel`。所以盲打的巨集必然發散。

**判斷狀態用堆疊指標，不是 RAM 裡的旗標。** 對話框與選單都是在主迴圈裡再進
一層巢狀迴圈，SP 明顯更低：

| 狀態 | SP |
|---|---|
| 野外／城裡，可移動 | `FFCA00`–`FFCACA` |
| 純文字訊息（招牌、`"C" to Continue`）| `FFC94C`–`FFC9D8` |
| 指令選單 | `FFC784`–`FFC84E` |
| 設施選單（神殿等）| `~FFC5xx` |
| 圖片事件與旅店名冊 | `~FFBAxx` |

**SP 給的是深度，不是語意。** Corak 的圖片事件與旅店的「是否登記」提示
落在同一段（`FFBA20`）—— 在前者盲送確認鍵是安全的，在後者等於答「是」
而走進名冊畫面，再按下去就把角色移出隊伍了。實測也真的發生過：
一次把整隊的錢捐給神殿，一次把 Sir Felgar 移出隊伍。

所以 `md-walk` 的規則是保守的：**只有落在「純文字訊息」那一段才自動送確認鍵**，
其餘一律停下來報位置。要放寬得自己明確指定 `--dialog-sp`。

`docker/blastem/md_walk.py`（image 內叫 `md-walk`）照這個判準走路：每一步先
取樣 SP，落在野外區間就送方向鍵，否則送確認鍵剝掉一層再回來看。
節拍器是 vblank 中斷點（stub 不回應非同步中斷，只能用「命中 → 讀 → 放行」
當單步），代價是模擬速度掉到約 1/6。

```bash
MD_PROG=md-walk tools/md_trace.sh /out/unused --load \
  --route "$(python3 tools/md_town_route.py --map 11 --outdoor --from 7,3 --to 2,5 \
             --wait 0 | tr ';' '\n' | grep key: | sed 's/key://' | paste -sd,)" \
  --break 0xB620:選曲 --ignore-d0 0,1,9,c,11,12 --shot walk
```

實測野外 48 步的路線一路走完，途中兩次自動清掉招牌訊息，
也照路徑規劃器算的 13 步準確走到指定座標。

**閉迴路已經補上。** 隊伍座標在 `0xFFF3A4`（X）／`0xFFF3A6`（Y）、
朝向 ASCII 在 `0xFFF3B4`（`'N'`=78、`'E'`=69）。`md_town_route.py --cells`
產生逐鍵對齊的期望座標，`md-walk --expect` 每走一步就核對，對不上當場停。
實測從城裡走 19 步到 (8,0) 的地城入口，**每一步都對上**。

座標是這樣找出來的：`md-walk --dump-ram` **只在確實走了一步之後**才拍 RAM 快照
（盲打的腳本分不出「走了」與「被對話框吃掉」，所以先前用 `md-ram-diff` 找
「每走一步 +1」零命中）。七張快照的 X 序列 `7,7,7,8,9,10,11` 與 Y 序列
`4,5,5,5,5,5,5` 在整塊 64 KB 裡各只有**一個**位址命中。
旁邊那幾個欄位隨轉向而變，值正好是 `sub_F5CE` 的四組遮罩／位移
（`C0,6` → `30,4`），朝向欄位是 ASCII —— 與靜態結論對得上。

另一個已知的坑：**路線起點差一格，整條路線會走進別的設施**，而且看起來順暢。
剛「離開旅店」時是 (7,3)，走一步北觸發 Corak 之後才是 (7,4)；
`md_town_route.py` 的預設起點是 (7,3)。

**先前找旗標的路是死路，記錄下來不必重試。** 用 RAM 快照差分（`md-ram-diff`）
比對「野外／對話框／選單」三態，扣掉畫面組合緩衝區後還有 196 個候選位元組，
其中 `0xFFCA3E`／`0xFFCA40` 看起來完美（野外 `00`、對話框與選單都 `80`）——
**但那一帶是堆疊**，逐位元組比對出來的「一致」只是呼叫深度剛好相同。
真正的訊號就是深度本身。

### 6. 戰鬥自動化：只有 `Attack` 能盲送

原廠 Mega Drive 說明書（[Internet Archive 的美版掃描](https://archive.org/details/might-and-magic-gates-to-another-world-md-us-manual)）把
可自動化的那一條講得很清楚：

> **Attack**: Character attacks the first monster, using whatever weapon they
> have equipped. If the first monster dies as a result of this attack,
> all the monsters behind it move up one position.

八個戰鬥指令裡 **只有 `Attack` 沒有後續提示**（`Fight`／`Shoot`／`Use` 要選哪一隻怪、
`Cast` 要選等級與法術）。這解釋了先前「連按 60 次確認鍵、回合數還停在 1」——
盲送確認鍵會掉進那些子選單再被取消，繞回原地。

Mega Drive 版**沒有** DOS 版的快速戰鬥（`Ctrl+A`）。按鍵是 **C 選擇、B 取消**，
選擇標記用十字鍵上下移動 —— 與本專案先前實測的結果一致。

`docker/blastem/md_fight.py`（image 內 `md-fight`）已經能**把仗打起來、
讓隊伍不會死、把回合推進**（實測推到第 2 回合，70 次行動全程滿血）。

**還沒解決的是「怎麼把選擇標記移到 `Attack`」**，三條路都試過：

| 做法 | 結果 |
|---|---|
| 完全不按方向鍵 | 標記**跨回合保留**，停在 `Cast` 就每次都進法術面板 |
| 方向鍵按住撞到頂 | 選單是**環狀**的，繞過頭跑進 `Controls` 子選單 |
| 找出「停在第幾項」那個變數 | 按兩次 `Down` 做等差搜尋，8 個候選全是計時器 |

標記大概不是存成單純的索引位元組 —— 可能是指標，或只存在 sprite 屬性表裡
（那在 VRAM，`m` 封包讀不到）。下一步要嘛從印選單的常式反推它讀哪個變數，
要嘛改讀 VDP。

#### 不會被打死：每隔幾幀把 HP 寫回上限

角色記錄在 `0xFFCE9F` 起、**每筆 134 bytes**（DOS 版是 130）：

| 位移 | 欄位 |
|---|---|
| `+00` | **目前 HP** |
| `+02` | 生命上限 |
| `+16` | 另一個上限（滿血時三者相等）|

`--invincible` 每 8 幀把 `+00` 寫回 `+02`。**改的是模擬器記憶體不是 ROM**
（這片有開機完整性檢查）。

找法要記一下：用「等於全隊 HP 的位元組序列」搜整塊 RAM，
間距 134 只中三個位址 —— 但**滿血時目前值與上限相等，三個都符合**。
要挨了打才分得出來：`+00` 掉到 6 而另外兩個還是 11，目前 HP 就是 `+00`。
先前直接挑第一個當「目前 HP」，看起來一切正常（讀出 `16/16`），
實際上讀的是上限，寫回去等於什麼都沒做。

### 7. 剩下的：戰鬥結算的五個音樂角色

`battle` 已經拿到了（case 2、呼叫端 `0x21730`，配戰鬥畫面截圖）。

## 不要重複走的路

`02-other-platforms.md` 的「不要重複走的路」那一節仍然有效，
Mega Drive 相關的三條：

- **不要用「nibble 為 0 的比例」找美術** —— 68000 指令本來就一堆 0 nibble，
  整片 ROM 都落在 12–37%。用列相似度。
- **不要用「列相似度高」推論「未壓縮」** —— 壓縮流裡的長平坦段一樣拿得到高分。
  它只能排序候選。
- **參數搜尋全滅時先懷疑框架不是參數** —— LZSS 那次試了五族四百多種組合，
  演算法從頭到尾沒選錯，錯的是三個框架級的前提。

這一輪新增的：

- **掃呼叫端要連 thunk 一起掃** —— 直接呼叫只佔四分之一。
- **改 ROM 前先確認有沒有防竄改** —— 改一個字串裡的字母來試，
  純文字位元組不可能讓遊戲當掉。
- **「有輸出」不等於「有在跑」** —— 停機時 VGM 照樣產出 711 bytes 的驅動初始化。
- **「附近沒有 X」推不出「不存在 X 這件事」** —— 用字串位置當錨點時，
  它只說明資料排在哪，不說明哪一支函式會執行。
- **導航不要盲走** —— 牆的資料在地圖檔裡，BFS 算最短路一次就到；
  盲走每一次嘗試都要重開模擬器。
- **但算得出路徑不等於走得完。** 只要中途會跳訊息，盲打的按鍵腳本就會發散：
  沒有一個按鍵在「有對話框」與「沒有對話框」兩種狀態下都安全。
  路徑長到會跳訊息時，腳本必須**判斷狀態**再決定下一個按鍵。
- **要判斷「現在卡在哪一層 UI」，先看堆疊指標，不要去 RAM 裡找旗標。**
  modal 是巢狀迴圈，深度本身就是訊號，`g` 一次就拿得到。
  在堆疊區做逐位元組差分會找到一堆「完美」的假旗標 —— 那只是呼叫深度剛好相同。
- **停在中斷點時模擬器時間是凍結的，按住手把要用「模擬幀數」算。**
  真實時間按住 0.08 秒等於**零個模擬幀**，遊戲每幀 poll 一次永遠看到「沒按」。
  同一個坑在 `md-trace`（模擬器多半在跑）與 `md-ram-diff`／`md-walk`
  （模擬器多半凍著）需要兩種不同的寫法。
- **`m` 封包一次最多回 255 bytes。** 要更多不會報錯，就只回 255。
  一次 64 KB 的快照因此變成 32,640 bytes 的碎片拼盤，而差分照樣跑得出
  「合理」的結果。讀多少要驗多少。
- **「格子上有遭遇 opcode」不等於「踩上去會打」** —— 那五格的樣式是
  `2b 01 12 …`，`2b` 是條件跳躍。
- **存狀態檔之前先看一眼截圖。** 存到「選單開著」的狀態，之後每一次載入的
  第一個方向鍵都在移動游標而不是走路 —— 而畫面看起來完全正常。
- **靜態到頂不等於問題無解** —— 換成動態，一次量測就把五個「強推論」變成
  「已證實」。判斷「這條路走不通」時，要說清楚是**哪一條**路走不通。
- **有進入點就別做樣式掃描。** 完整性檢查掃了六個候選都不是，
  而它其實是 reset 之後的第一個 `jsr` —— 從進入點往下讀是有界的，
  樣式掃描的搜尋空間沒有邊界，而且前提猜錯（字組 vs 長字、`dbf` vs `bgt`）
  不會有任何症狀。
- **做「改一個位元組會怎樣」的實驗，改模擬器記憶體不要改 ROM 檔**
  （`md-trace --poke`）。同樣得到答案，而且不必冒著把唯一那份原版弄髒的風險。
