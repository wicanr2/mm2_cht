# Mega Drive 逆向：現況與缺口盤點

這份是 Mega Drive 版逆向的**單一狀態入口**。細節分散在
[`02-other-platforms.md`](02-other-platforms.md)（圖形與畫面）、
[`md-music-driver.md`](md-music-driver.md)（音樂機制）、
[`md-music-scenes.md`](md-music-scenes.md)（曲目與場景）。

輸入：`Might and Magic - Gates to Another World (USA, Europe).md`，786,432 bytes，
SHA-256 `d86b6d7381ef67ecb5391eddb6857bf9d15b1e402da6bfc42cb003186599cbff`。

**這個版本在專案裡的定位是「素材與音樂來源」，不是要重現的行為 oracle**
（DOS 版才是，見 `CLAUDE.md` §1 的裁決順序）。所以下面的缺口都不阻擋交付，
排序依據是「補起來能讓 remake 多出什麼」。

## 已解出的

| 領域 | 狀態 |
|---|---|
| ROM 結構、標頭 | 產品碼 `T-50`（Electronic Arts），1991.JUL |
| 基底暫存器 `a5 = 0x312` | 已證實。148 筆 `jmp abs.l` 的 thunk 表 |
| 壓縮 | LZSS（常式在 `0x29954`），4096 環形緩衝、初值 `0x20` |
| 圖形區塊 | **334 個 LZSS 區塊**（`tools/mdlzss_scan.py`，不靠任何前綴）：79 個是 tile（12,682 個），其餘是 blitter 用的點陣圖。舊方法只找到 72 個 |
| 未壓縮美術 | `0x06DA00` 起的 4bpp tile（含字型）|
| VDP 與畫面結構 | plane A/B 位置、sprite 表、64×64 cell；開機用 CPU 寫、遊戲中走 DMA |
| 畫面更新方式 | **換的是 tile 的圖案不是 tilemap** —— nametable 開機擺好就不動 |
| 第一人稱繪製鏈 | `sub_FC38(區域類型)` 建表 → `sub_3DE2` 逐格 blit 進 `0xFF0000` → DMA |
| 三個 RAM 組合緩衝區 | `0xFF0000`（DMA 來源）、`0xFF3400`、`0xFF4400`（64 word 一列的格子陣列）|
| 音樂驅動 | Z80 blob 在 `0x0ADBDA`（5,513 bytes）；命令介面 `$A0000A`／`$A0000B`；串流環形緩衝 `$A01600` |
| 曲目資料 | 18 首，靠「起點前 4 bytes 是結束指標」自我描述 |
| 選曲 | `sub_B620` 跳表 switch，21 個 case，39 個呼叫端（28 個走 thunk）|
| 曲目 → 場景 | 16 個音樂角色全部對應完成，四個區域主題已證實 |
| 逐首擷取 | GDB stub 指定曲目、錄 VGM、轉標準 PCM WAV，18 首零失敗 |
| 防竄改 | 已證實存在：改動任何一個位元組（尾端 padding 除外）就開不了機 |

## 缺口（依「補起來的價值」排序）

### 1. 第一人稱視角的繪製鏈 —— 大致解開，剩兩小塊

**已解**：`sub_FC38(區域類型)` → `sub_3DE2` 逐格 blit → DMA 進 VRAM。
選牆的貼圖與選音樂**是同一個變數**（`sub_FB86(地圖編號)` 算出的區域類型）。
細節與慣用句見 [`02-other-platforms.md`](02-other-platforms.md)。

視野貼圖是 **LZSS 壓縮的點陣圖不是 tile**（首字 `0xAAAA`，長度多半不是 32 的
倍數），由 thunk `0x66` 的 blitter 畫進 `0xFF0000` 的固定位置。

**剩下**：`-$F48(a5)`（每一格要畫什麼的編號）由誰依地圖與朝向算出來；
以及八個來源各自對應視野的哪一個位置。後者把它們 render 出來就分得清。

**補起來能拿到什麼**：`F6` 切到 Mega Drive 素材時第一人稱與 MD 原版一致。
仍屬可選 polish，不阻擋交付。

### 2. 把場景對照從「強推論」升級成「已證實」—— 靜態證據已到頂

**原本的計畫（解出文字索引表，改用精確引用）已經證實走不通。**

`sub_73FC(字串, x, y, 旗標)` 是印字函式，**326 個呼叫端**（133 個直接、
193 個走 thunk 位移 474）。字串怎麼傳進去，掃出來的答案是：

| 檢查 | 結果 |
|---|---|
| 全 ROM 有沒有字串指標表（連續 ≥3 個 32-bit 字串位址）| **0 張** |
| 32-bit 字串位址在整片 ROM 出現幾次（含指令運算元與資料）| **14 次** |
| 散文字串被 `(d16,PC)` 定址直接引用（窮盡掃所有 EA=`(d16,PC)` 的指令）| **33 / 377（9%）** |
| 呼叫 `sub_73FC` 前一個指令 | 146 個是 `move.l d0,-(sp)` —— 指標是算出來的 |

**這片 ROM 根本沒有字串指標表。** 多數印字走的是「先把文字格式化進 RAM
緩衝區，再印那個緩衝區」，所以拿不到「這支函式引用了這條字串」的靜態關係，
不論怎麼掃都拿不到。

**所以要升級證據等級，只剩動態一條路**：用已經可用的 GDB stub 在
`sub_73FC` 或 `sub_B620` 下中斷點，實際走到各設施時記錄「當下請求哪個 case、
同時印出什麼字」。工具鏈已經有（`docker/blastem/music_dump.py` 的 RSP 客戶端），
缺的是「headless 走到每個設施」的按鍵時間軸。

**現況已經夠用**：16 個角色全部有對應，四個區域主題是已證實，
其餘強推論的依據（字串錨點整批一致、設施函式離開時全部復原區域音樂）
彼此獨立且互相支持。**升級是精度問題，不是正確性問題。**

### 3. 完整性檢查在哪

**現況**：已證實存在，但沒找到。掃過「循序讀 ROM 累加」的迴圈
（`add.w (aN)+,dM`、`move.w (aN)+,dM` 配 `dbf`，字組對齊）只有 6 個候選，
逐一看過都是繪圖或堆疊操作。所以它可能不是單純加總（CRC、抽樣比對、或分散在多處）。

**影響**：目前**不影響任何工作** —— 擷取走 GDB stub 不改 ROM。
只有在需要「改 ROM 做實驗」時才會擋路。

**下一步**：它在開機早期執行（畫面全黑代表沒進主迴圈），
從 reset 進入點往下追是有界的工作量。

### 4. case 11（`0x0BA608`）是哪一個設施

**現況**：有呼叫端（`0x018BCA`），而且同一支函式在 `0x018BB6` 也請求 case 19，
是設施的進出樣式。但字串錨點離得太遠（`Identify Item` ±953），不足以定案。

**影響**：這首曲子沒有對應到音樂包的任何角色。16 個角色已經齊了，所以不缺。

**下一步**：與第 2 項同一條路 —— 要動態證據，靜態掃描已經到頂。

### 5. `0x0BAE7C`（case 4）與 `0x0B60CC`（case 20）

**已證實沒有任何呼叫端** —— 這個移植版沒有用到。
這也解釋了本專案數到 18 首而 VGMRips 只列 16 首。**這不是缺口，是結論。**

## 不要重複走的路

`02-other-platforms.md` 的「不要重複走的路」那一節仍然有效，
Mega Drive 相關的三條：

- **不要用「nibble 為 0 的比例」找美術** —— 68000 指令本來就一堆 0 nibble，
  整片 ROM 都落在 12–37%。用列相似度。
- **不要用「列相似度高」推論「未壓縮」** —— 壓縮流裡的長平坦段一樣拿得到高分。
  它只能排序候選。
- **參數搜尋全滅時先懷疑框架不是參數** —— LZSS 那次試了五族四百多種組合，
  演算法從頭到尾沒選錯，錯的是三個框架級的前提。

這一輪新增的：

- **掃呼叫端要連 thunk 一起掃** —— 直接呼叫只佔四分之一。
- **改 ROM 前先確認有沒有防竄改** —— 改一個字串裡的字母來試，
  純文字位元組不可能讓遊戲當掉。
- **「有輸出」不等於「有在跑」** —— 停機時 VGM 照樣產出 711 bytes 的驅動初始化。
